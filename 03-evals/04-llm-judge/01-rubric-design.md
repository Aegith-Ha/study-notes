# LLM judge 설계: 채점 기준과 프롬프트 (Rubric Design)

LLM judge가 일관되게 판정하도록 판정 과제, 등급 기준(rubric), 프롬프트, 판정 방식, judge 모델을 정하는 방법을 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 설계한 judge를 사람 판정과 맞춰 검증하는 방법은 [02-human-agreement](./02-human-agreement.md) 참고

## 1. 판정 과제 정의

judge 프롬프트 하나에는 **판정 과제 하나**만 맡긴다. "관련성과 충실성과 완결성을 1~10점으로" 같은 묶음 판정은 무엇 때문에 점수가 깎였는지 알 수 없고, 사람과 맞춰 보기도 어렵다.

| 과제 | 입력 | 출력 | 쓰는 지표 |
| --- | --- | --- | --- |
| 청크 관련성 | 질문 + 청크 1개 | 0 / 1 / 2 | Context Relevance, Judge nDCG, 골든셋 pooling 1차 판정 |
| 컨텍스트 충분성 | 질문 + top-k 전체 | 0 / 1 | Context Sufficiency, Refusal Appropriateness |
| 주장 분해 | 답변 | 주장 목록 | Faithfulness, Claim Recall의 전처리 |
| 주장 검증 | 주장 1개 + 컨텍스트 | 지지 / 모순 / 근거 없음 | Faithfulness |
| 정답 비교 | 질문 + 답변 + 정답 답변 | 0 / 1 / 2 | Answer Correctness |
| 답변 관련성 | 질문 + 답변 | 0 / 1 / 2 | Answer Relevance |
| 두 답변 비교 | 질문 + 답변 A, B | A / B / 동점 | Pairwise Preference |

- 주장 분해는 판정이 아니라 변환이다. 분해 결과가 달라지면 Faithfulness의 분모가 바뀌므로 분해 프롬프트도 버전을 관리한다.

## 2. 등급 기준(rubric) 작성

### 작성 원칙

- 등급마다 **정의 + 판정 질문 + 예시**를 둔다. 정의만 있으면 judge와 사람이 각자 다르게 해석한다.
- **경계 사례**(1과 2 사이, 0과 1 사이) 예시를 반드시 넣는다. 판정이 갈리는 곳은 경계다.
- 골든셋 판정 기준과 **같은 문장**을 쓴다. judge 기준과 골든셋 기준이 다르면 두 계열 지표를 맞춰 볼 수 없다. 등급 정의 원본은 [03-golden-set README](../03-golden-set/README.md)의 판정 기준이다.
- 판정에 영향을 주면 안 되는 요소(길이, 문체, 확신에 찬 어조)를 명시적으로 적는다.

### 예시: 청크 관련성 (0 / 1 / 2)

정의와 판정 질문은 골든셋 판정 기준 원본을 그대로 옮긴 것이다. 예시 청크만 이 노트에서 추가한다.

질문: 비밀번호 재설정 링크는 얼마 동안 유효한가?

| 등급 | 정의 | 판정 질문 | 예시 청크 |
| --- | --- | --- | --- |
| 2 관련 | 이 자료만으로 질문에 답할 수 있다 (핵심 근거) | 이 자료를 읽으면 답을 쓸 수 있는가? | "재설정 링크는 발송 후 24시간 동안 유효하다." |
| 1 부분 관련 | 답의 일부나 필요한 조건을 담고 있지만 이것만으로는 답할 수 없다 (부수 근거) | 답을 쓰는 데 도움은 되지만 다른 자료가 더 필요한가? | "만료된 재설정 링크는 앱에서 다시 요청해야 한다." |
| 0 무관 | 같은 주제어가 나와도 질문에 답하는 데 쓸 수 없다 | 이 자료가 없어도 답에 영향이 없는가? | "비밀번호는 8자 이상이어야 한다." |

경계 사례
- 주제어(재설정, 비밀번호)만 겹치고 유효 시간 정보가 없으면 **0**이다. 단어 겹침으로 1을 주지 않는다.
- 구버전 문서("12시간 동안 유효")는 질문에 답하는 형태이므로 관련성은 **2**다. 최신성은 관련성과 별개로 문서 버전(`doc_version`)으로 점검한다.

### 예시: 주장 검증 (지지 / 모순 / 근거 없음)

| 판정 | 정의 |
| --- | --- |
| 지지 | 컨텍스트에 같은 내용이 있거나, 컨텍스트에서 바로 따라 나온다 |
| 모순 | 컨텍스트와 반대되거나 수치·조건이 다르다 |
| 근거 없음 | 컨텍스트에 관련 내용이 없다. 일반 상식이어도 컨텍스트에 없으면 근거 없음 |

- "일반 상식이어도 근거 없음"은 설계 결정이다. 상식을 허용하면 judge마다 상식의 범위가 달라 판정이 흔들린다. 허용하려면 허용 범위를 예시로 정한다.

### 예시: 정답 비교 (0 / 1 / 2)

| 등급 | 정의 |
| --- | --- |
| 2 맞음 | 정답의 핵심 주장을 모두 담고, 정답과 모순되는 내용이 없다 |
| 1 부분 맞음 | 핵심 주장은 맞지만 부가 조건을 빠뜨렸다. 모순은 없다 |
| 0 틀림 | 핵심 주장이 빠졌거나, 정답과 모순되는 내용이 하나라도 있다 |

- 정답에 없는 추가 내용은 정답과 모순되지 않으면 감점하지 않는다. 환각 여부는 Faithfulness로 따로 본다.

## 3. 프롬프트 구조

```text
[역할]     당신은 검색 결과의 관련성을 판정하는 평가자다.
[과제]     질문과 청크가 주어진다. 청크가 질문에 답하는 데 얼마나 쓸모 있는지 판정한다.
[기준]     등급 정의, 판정 질문, 예시, 경계 사례 (2장 rubric 그대로)
[주의]     길이, 문체, 단어 겹침은 판정에 반영하지 않는다.
[입력]     질문: {question}
           청크: {chunk}
[출력]     {"reason": "<판정 근거 한두 문장>", "grade": 0 | 1 | 2}
```

- **근거를 먼저, 등급을 나중에** 쓰게 한다. 등급을 먼저 쓰면 근거가 등급을 정당화하는 문장이 된다.
- 출력은 JSON처럼 파싱 가능한 형식으로 고정한다. 파싱 실패율도 기록한다.
- 검색 순위, 검색기 이름, 어느 시스템 결과인지는 입력에 넣지 않는다.
- few-shot 예시는 등급별로 고르게 넣는다. 한 등급 예시만 많으면 그 등급으로 쏠린다.

## 4. 판정 방식

| 방식 | 내용 | 장점 | 단점 | 쓰는 곳 |
| --- | --- | --- | --- | --- |
| Pointwise | 결과 하나에 절대 등급 | 점수를 기준선으로 쌓을 수 있음 | 등급 경계가 흔들림 | 대부분의 지표 |
| Pairwise | 두 결과 중 더 나은 쪽 | 사람 판단과 잘 맞음, 미세한 차이 구분 | 절대 점수 없음, 위치 편향 | 두 시스템 비교 |
| Reference-guided | 정답을 함께 주고 판정 | 가장 안정적 | 정답이 필요 | Answer Correctness |
| Listwise | top-k 전체를 한 번에 | 호출 수가 적음 | 앞쪽 결과에 쏠림, 긴 입력 | 충분성 판정만 |

## 5. judge 모델 선택

| 고려 사항 | 기준 (초안) |
| --- | --- |
| 성능 | 평가 대상 생성 모델과 같거나 더 강한 모델 |
| 계열 | 가능하면 생성 모델과 다른 계열 (자기 선호 편향 회피) |
| 비용 | 대량 판정은 작은 모델을 쓰되, 사람 일치도 검증을 통과한 경우에만 |
| 고정 | 모델 버전을 고정한다. "최신" 별칭은 쓰지 않는다 |

- 큰 모델과 작은 모델을 같은 검증 세트로 비교해서, 일치도 차이가 작으면 작은 모델을 쓴다.

## 6. 편향과 설계상 대응

| 편향 | 내용 | 설계상 대응 | 측정 방법 |
| --- | --- | --- | --- |
| 위치 편향 | pairwise에서 먼저 나온 쪽 선호 | 순서를 바꿔 두 번 판정, 결과가 다르면 동점 | [02-human-agreement](./02-human-agreement.md) 5장 |
| 길이 편향 | 긴 청크·답변을 더 좋게 봄 | 기준에 "길이는 반영하지 않음" 명시 | 같은 내용에 무관한 문장을 덧붙여 점수 변화 확인 |
| 단어 겹침 편향 | 질문과 단어가 겹치면 관련으로 봄 | 경계 사례에 "주제어만 겹치면 0" 예시 | 겹침이 적은 정답 청크, 겹침이 많은 오답 청크로 확인 |
| 자기 선호 | 자기 계열 모델의 답변 선호 | 다른 계열 judge | 같은 답변을 계열이 다른 judge로 비교 |
| 관대함 | 애매하면 높은 등급 | 경계 사례 예시, 근거 먼저 쓰기 | 사람 대비 등급별 정밀도 |
| 어조 편향 | 확신에 찬 답변을 맞다고 봄 | 기준에 "어조는 반영하지 않음" 명시 | 같은 내용을 확신형·유보형으로 바꿔 비교 |
| 순위 누출 | 상위 결과를 관대하게 판정 | 순위 정보를 입력에서 제외 | - |

## 7. 재현성과 비용

재현성
- temperature 0, 모델 버전 고정, 프롬프트 버전 기록
- temperature 0이어도 결과가 완전히 같지는 않을 수 있다. 같은 입력을 두 번 판정해 바뀌는 비율(자기 일치율)을 한 번 재 둔다.

비용
- 청크 관련성은 질의당 k번 호출한다. 같은 (질문, 청크) 쌍은 결과를 캐시한다.
- 운영 모니터링은 질의를 샘플링한다.
- 주장 분해 + 주장별 검증은 답변이 길수록 비싸다. 답변 길이 분포와 함께 비용을 기록한다.

## 8. 확인할 점

- rubric을 바꾸면 judge 판정도, 골든셋 판정도 의미가 바뀐다. rubric은 골든셋과 같은 버전으로 관리한다.
- 프롬프트를 고칠 때마다 검증 세트로 다시 잰다. 고친 프롬프트를 같은 검증 세트에서만 계속 맞추면 그 세트에 과적합된다 ([02-human-agreement](./02-human-agreement.md) 6장).

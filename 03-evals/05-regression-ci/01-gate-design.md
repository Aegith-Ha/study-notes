# 회귀 테스트 설계: 무엇을 어떤 기준으로 막는가 (Gate Design)

배포 전에 평가셋을 자동으로 돌려 품질이 떨어진 변경을 막으려면, 무엇을 검사하고 어느 정도 떨어지면 막을지를 먼저 정해야 한다. 이 노트는 테스트 계층, 사용할 평가셋, 통과 기준, 노이즈 처리를 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- CI에서 실제로 돌리는 흐름은 [02-ci-pipeline](./02-ci-pipeline.md) 참고

## 1. 회귀 테스트가 일반 평가와 다른 점

| 항목 | 일반 평가 (01~04) | 회귀 테스트 |
| --- | --- | --- |
| 질문 | 얼마나 좋은가 | **이전보다 나빠졌는가** |
| 비교 대상 | 다른 기법, 다른 설정 | 직전 기준선(main 브랜치) |
| 실행 시점 | 실험할 때 | 변경할 때마다 자동 |
| 결과 | 수치와 분석 | **통과 / 경고 / 차단** |
| 비용 제약 | 비교적 느슨함 | 매번 돌리므로 빠르고 싸야 함 |

- 회귀 테스트는 새 지표를 만들지 않는다. `01`~`04`에서 정한 지표를 **자동으로, 기준선과 비교해서** 돌린다.

## 2. 테스트 계층

빠르고 싼 검사를 자주, 느리고 비싼 검사를 드물게 돌린다.

| 계층 | 검사 내용 | LLM 호출 | 소요 (예) | 실패 시 |
| --- | --- | --- | --- | --- |
| L0 지표 코드 단위 테스트 | 지표 계산이 손계산 예시와 같은가 | 없음 | 초 | 차단 |
| L1 형식·규칙 검사 | 출력 JSON 파싱, 인용 형식, 구버전 문서 반환율, 권한 밖 문서 | 생성 출력만 | 분 | 차단 |
| L2 필수 통과 질문 | 반드시 맞혀야 하는 핵심 질문 소수 (예: 10건) | 있음 | 분 | 차단 |
| L3 검색 회귀 | dev 표본으로 Recall@5, MRR 등 정답 기반 검색 지표 | 없음 (검색만) | 분 | 기준에 따라 |
| L4 생성 회귀 | dev 표본으로 Answer Correctness, Faithfulness, 거절 정확도 | 생성 + judge | 수십 분 | 기준에 따라 |
| L5 배포 확인 | test 세트 전체로 L3 + L4 | 생성 + judge | 수십 분~ | 차단 |

- **L0**: [01-reference-based](../01-retrieval-metrics/01-reference-based.md) 2장, [02-human-agreement](../04-llm-judge/02-human-agreement.md) 4장 같은 손계산 예시를 그대로 테스트 케이스로 쓴다. 지표 코드가 바뀌어 점수가 달라지는 것을 시스템 회귀로 착각하지 않게 한다.
- **L1**: 정답 없이 규칙으로 확인할 수 있는 실패다([검색 지표 정답 없음](../01-retrieval-metrics/02-reference-free.md)). 싸고 결정적이라 차단 기준으로 쓰기 좋다.
- **L2**: 평균이 올라도 핵심 질문을 틀리면 막는다. 서비스에서 가장 많이 묻는 질문, 틀리면 피해가 큰 질문(기한, 금액 등)을 고른다. 여기에 두 종류를 더 넣는다.
  - **보안 케이스**: 프롬프트 인젝션이 든 문서, 권한 밖 문서를 노리는 질문, 개인정보를 끌어내려는 질문. 모델이나 프롬프트를 바꾸면 방어 수준이 달라지므로 매번 돌린다([06-llmops/03-security](../../06-llmops/03-security/README.md)). 품질 평균과 섞지 않고 전부 통과해야 한다.
  - **운영 버그 회귀 케이스**: 운영에서 발견해 고친 실패 사례. 고친 뒤 이 목록에 넣어 다시 깨지지 않게 한다([06-llmops/04-feedback-loop](../../06-llmops/04-feedback-loop/README.md)). 일반 소프트웨어에서 버그를 고칠 때 테스트를 추가하는 것과 같다.

## 3. 어떤 평가셋을 쓰나

골든셋의 dev / test 분리([04-update-loop](../03-golden-set/04-update-loop.md) 5장)를 CI에서도 지킨다.

| 용도 | 평가셋 | 결과 공개 범위 | 이유 |
| --- | --- | --- | --- |
| PR마다 (L3, L4) | dev 세트 표본 (예: 50건) | 질의별 결과까지 | 개발자가 실패 원인을 보고 고쳐야 하므로 |
| 배포 전 (L5) | test 세트 전체 (50건) | **집계 수치만** | 질의별 실패를 보고 고치면 test 세트에 맞춘 튜닝이 된다 |
| 필수 통과 (L2) | 별도 핵심 질문 목록 | 질의별 결과까지 | 개수가 적고 목적이 명확함 |

- test 세트에서 실패하면 원인 분석은 dev 세트에서 한다. test 세트 질의를 직접 열어 보지 않는다.
- dev 표본은 소스(A~D)와 답변 유형 비율을 유지해서 고정한다. 매번 다르게 뽑으면 기준선과 비교할 수 없다.
- 다만 PR마다 같은 50건의 실패를 보고 고치다 보면 그 50건에 맞춰진다. 정해진 주기(예: 분기)에 dev 표본 일부를 교체하고, 교체한 날 기준선을 다시 계산한다.

## 4. 통과 기준

### 4.1 기준의 종류

| 종류 | 내용 | 예 | 잡는 것 |
| --- | --- | --- | --- |
| 절대 하한 | 이 값 아래면 무조건 실패 | Faithfulness ≥ 0.85 | 기준선 자체가 낮아지는 것 (조금씩 떨어지는 누적 하락) |
| 기준선 대비 하락 | 기준선보다 δ 이상 떨어지면 실패 | Recall@5 하락 ≤ 0.03 | 이번 변경으로 생긴 하락 |
| 질의별 회귀 | 기준선에서 맞던 질의가 틀린 개수 | 새로 틀린 질의 ≤ 2건 | 평균에 가려지는 개별 질의 하락 |
| 필수 통과 | 핵심 질문 전부 통과 | L2 10건 모두 정답 | 핵심 기능 고장 |
| 릴리스 기준선 대비 누적 하락 | 마지막 배포 버전보다 δ_누적 이상 떨어지면 실패 | Recall@5 누적 하락 ≤ 0.05 | 유의하지 않은 작은 하락이 여러 PR에 걸쳐 쌓이는 것 |

- 기준선 대비 기준만 쓰면 매번 조금씩 떨어지는 것을 못 막는다. 직전 main 기준선은 병합마다 갱신되므로, 경고로 통과한 0.02 하락이 세 번 쌓이면 0.06이 떨어져도 매번 "0.02 하락"으로만 보인다. 그래서 **두 기준선**과 비교한다. 직전 main(이번 변경의 영향)과 마지막 배포 버전(누적 영향)이다. 절대 하한도 함께 둔다.
- 평균만 쓰면 "5건 좋아지고 5건 나빠진" 변경이 통과한다. 질의별 회귀를 함께 본다.

### 4.2 차단과 경고

| 결과 | 조건 (초안) | 처리 |
| --- | --- | --- |
| 통과 | 모든 기준 충족 | 병합 가능 |
| 경고 | 기준선 대비 하락이 있지만 통계적으로 유의하지 않음 (5장) | 병합 가능, PR에 표시 |
| 차단 | 절대 하한 미달, 필수 통과 실패, 유의한 하락 | 병합 불가. 의도한 변경이면 사유를 남기고 승인 후 기준선 갱신 |

## 5. 노이즈 처리

### 5.1 왜 노이즈가 생기나

- **표본이 작다.** 50건이면 질의 1건이 2%p다. 0.80 → 0.78은 질의 1건 차이일 수 있다.
- **생성과 judge가 비결정적이다.** temperature 0이어도 결과가 조금씩 달라질 수 있다([02-generation-metrics](../02-generation-metrics/01-reference-based.md) 3.6).
- **검색도 완전히 결정적이지 않을 수 있다.** 근사 최근접 탐색(ANN) 색인은 다시 만들거나 설정이 조금 바뀌면 결과 순서가 달라질 수 있다. L3는 LLM 호출이 없어도 노이즈가 0이라고 가정하지 않는다.
- 그래서 "떨어졌다"를 바로 실패로 처리하면 아무 변경도 없는데 실패하는 테스트(flaky)가 된다.

### 5.2 대응

| 방법 | 내용 |
| --- | --- |
| 비결정성 줄이기 | 생성·judge 모두 temperature 0, 모델 버전 고정, judge 결과 캐시 |
| 자기 반복 측정 | 변경 없이 같은 설정을 몇 번 돌려 점수가 흔들리는 폭을 잰다. δ는 이 폭보다 크게 잡는다 |
| 같은 질의끼리 비교 | 평균 차이가 아니라 질의별로 기준선과 짝지어 비교한다 (paired) |
| 유의성 검정 | 이진 결과(맞음/틀림)는 McNemar 검정, 연속 점수는 paired bootstrap |
| 여러 지표 동시 검정 | 지표를 많이 볼수록 우연히 하나는 "유의한 하락"이 나온다. 지표 8개를 각각 p < 0.05로 보면 아무 변화가 없어도 한 번 이상 걸릴 확률이 약 34%다. **차단 기준 지표는 소수**(예: Recall@5, Answer Correctness)로 두고 나머지는 경고로만 쓰거나, Holm 보정처럼 지표 수만큼 기준을 엄격하게 한다 |

### 5.3 손계산 예시: McNemar 검정

dev 표본 50건에서 Answer Correctness(맞음/틀림)를 기준선과 새 변경으로 비교

| | 새 변경 맞음 | 새 변경 틀림 |
| --- | --- | --- |
| 기준선 맞음 | 38 | **b = 3** |
| 기준선 틀림 | **c = 1** | 8 |

```text
기준선 정답률 = (38 + 3) / 50 = 0.82
새 변경 정답률 = (38 + 1) / 50 = 0.78       → 평균 0.04 하락

McNemar는 결과가 바뀐 질의(b + c = 4건)만 본다.
변경이 영향이 없다면 b와 c는 반반이어야 한다 (이항분포, n = 4, p = 0.5)
양측 p값 = 2 × P(X ≤ 1) = 2 × (1 + 4) / 16 = 0.625
```

읽는 법
- 평균은 0.04 떨어졌지만 실제로 바뀐 질의는 4건뿐이고, 3 : 1은 우연으로도 충분히 나온다(p = 0.625).
- 이 결과는 **경고**다. 차단하지 않고 새로 틀린 3건을 PR에 표시해 사람이 확인하게 한다.
- b = 6, c = 0(평균 0.12 하락)이면 p = 2 × (1/64) ≈ 0.031로 유의하다. 이때는 **차단**한다.
- 반대로 질의 50건으로는 2~3건 차이를 유의하게 잡기 어렵다. 작은 하락까지 막아야 한다면 L5의 test 세트를 키우거나 dev 표본을 늘린다.
- 그래서 기준선 대비 하락 기준은 "평균이 δ 이상 떨어졌고, 유의하다"를 함께 본다.

## 6. 품질 외 기준

| 항목 | 예 | 이유 |
| --- | --- | --- |
| 지연 시간 | 응답 p95가 기준선 대비 20% 이상 증가하면 경고 | 리랭커, 긴 컨텍스트 추가 시 |
| 비용 | 질의당 토큰 수가 기준선 대비 30% 이상 증가하면 경고 | top-k 증가, 프롬프트 확장 시 |
| 출력 형식 | JSON 파싱 실패율 > 0이면 차단 | 형식이 깨지면 서비스가 멈춤 |

- 품질이 올라도 비용과 지연이 크게 늘면 배포 판단이 달라진다. 품질 지표와 같은 리포트에 둔다.

## 7. 확인할 점

- 통과 기준은 처음부터 정확할 수 없다. 처음 몇 주는 차단 대신 경고로만 돌려 오탐(괜찮은 변경을 막음)과 미탐(나쁜 변경을 통과시킴)을 기록하고, 그 뒤 기준을 정한다.
- 판정에 judge를 쓰는 기준(Faithfulness 등)은 judge가 검증을 통과한 경우에만 차단 기준으로 쓴다([04-llm-judge](../04-llm-judge/02-human-agreement.md) 7장). 미검증이면 경고로만 쓴다.

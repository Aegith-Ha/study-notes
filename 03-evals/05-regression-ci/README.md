# 회귀 테스트와 CI 연결 (Regression Testing in CI)

배포 전에 평가셋을 자동으로 돌려, 검색이나 생성 품질을 떨어뜨리는 변경을 막는 방법을 정리한다. 새 지표를 만드는 것이 아니라 `01`~`04`에서 정한 지표와 골든셋, judge를 **변경할 때마다 자동으로, 기준선과 비교해서** 돌린다. 이 README에는 전체 구조와 메인 결정을 두고, 설계와 파이프라인 설명은 하위 노트에 둔다.

- 검색 지표는 [01-retrieval-metrics](../01-retrieval-metrics/README.md), 생성 지표는 [02-generation-metrics](../02-generation-metrics/README.md) 참고
- 평가셋(dev / test)은 [03-golden-set](../03-golden-set/README.md), judge 검증은 [04-llm-judge](../04-llm-judge/README.md) 참고

## 하위 노트

- [01-gate-design](./01-gate-design.md): 회귀 테스트 설계. 테스트 계층(L0~L5), 사용할 평가셋, 통과 기준(절대 하한, 기준선 대비, 질의별 회귀), 노이즈 처리와 McNemar 검정 손계산
- [02-ci-pipeline](./02-ci-pipeline.md): CI 파이프라인. 변경 종류별로 돌릴 계층, 기준선 관리, PR 리포트, 비용 줄이기, 실패 처리, 도입 순서

## 평가 체계에서의 위치

```text
01 검색 지표 ─┐
02 생성 지표 ─┼─▶ 05 회귀 테스트: 변경마다 자동 실행, 기준선과 비교, 통과 / 경고 / 차단
03 골든셋   ─┤                       │
04 judge   ─┘                        ▼
                         배포 ──▶ 06-llmops 운영 모니터링 (골든셋 밖 질의)
```

| 구분 | 회귀 테스트 (이 폴더) | 운영 모니터링 ([06-llmops](../../06-llmops/README.md)) |
| --- | --- | --- |
| 시점 | 배포 **전** | 배포 **후** |
| 평가셋 | 골든셋 (dev 표본, test) | 실제 운영 질의 샘플 |
| 주된 지표 | 정답 기반 + Faithfulness, 규칙 검사 | 정답 없는 지표, 사용자 피드백 |
| 목적 | 나빠진 변경을 막기 | 나빠진 상태를 빨리 알기 |

## 테스트 계층 요약

| 계층 | 검사 | 언제 | 실패 시 |
| --- | --- | --- | --- |
| L0 지표 단위 테스트 | 지표 코드가 손계산 예시와 같은가 | 지표 코드 변경 | 차단 |
| L1 형식·규칙 | JSON 파싱, 인용 형식, 구버전·권한 밖 문서 | 시스템 변경 | 차단 |
| L2 필수 통과 | 핵심 질문 소수 전부 정답, 보안 케이스, 운영 버그 회귀 케이스 | 시스템 변경 | 차단 |
| L3 검색 회귀 | dev 표본 Recall@5, MRR | 검색 변경 | 기준에 따라 |
| L4 생성 회귀 | dev 표본 Answer Correctness, Faithfulness, 거절 | 검색·생성 변경 | 기준에 따라 |
| L5 배포 확인 | test 세트 전체 L3 + L4, 집계만 공개 | 배포 전 | 차단 |

## 메인 결정 (초안)

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| PR용 평가셋 | dev 표본 50건 고정 (소스·답변 유형 비율 유지) | 기준선과 같은 질의로 비교해야 함 |
| 배포 전 평가셋 | test 세트 50건, 집계 수치만 공개 | 질의별 실패를 보고 고치면 test에 맞춘 튜닝이 됨 |
| 통과 기준 | 절대 하한 + 기준선 대비 하락 + 질의별 회귀 + 필수 통과 | 각각 누적 하락, 이번 하락, 평균에 가려진 하락, 핵심 고장을 잡음 |
| 기준선 | 직전 main 기준선 + 마지막 배포(릴리스) 기준선 두 개 | 경고로 통과한 작은 하락이 여러 PR에 걸쳐 쌓이는 것 방지 |
| 차단 지표 수 | 차단은 소수 지표(Recall@5, Answer Correctness 등)만, 나머지는 경고 | 지표가 많으면 우연한 "유의한 하락"이 늘어남 |
| 하락 판정 | 평균이 δ 이상 떨어지고 McNemar(이진) / paired bootstrap(연속)으로 유의할 때만 차단, 아니면 경고 | 50건에서 질의 1건 = 2%p라 노이즈가 큼 |
| judge 기반 기준 | judge 검증 통과 전에는 경고 전용 | 미검증 judge로 병합을 막지 않음 |
| 변경 종류별 실행 | 바뀐 부분에 맞는 계층만 실행 + 매일 밤 전체 실행 | 비용, 외부 API 변화 감지 |
| 평가 도구 변경 | 골든셋·judge·지표 코드 변경은 시스템 변경과 다른 PR로 분리, 병합 후 기준선 재계산 | 점수 변화의 원인을 구분 |
| 재실행 | 노이즈 의심 시 1회만 | "통과할 때까지 재실행" 방지 |
| 도입 | 처음 몇 주는 경고 전용으로 돌리고 오탐·미탐을 보고 기준 확정 | 기준을 처음부터 정확히 정할 수 없음 |

### 통과 기준 값 (초안)

| 지표 | 절대 하한 | 기준선 대비 최대 하락 (δ) | 비고 |
| --- | --- | --- | --- |
| Recall@5 | - | 0.03 | 하한은 기준선 확정 후 설정 |
| MRR | - | 0.03 | |
| Answer Correctness | - | 0.04 | |
| Faithfulness | 0.85 | 0.03 | judge 검증 통과 후 차단 |
| 과잉 거절률 | - | +0.05 (증가) | |
| 질의별 회귀 (새로 틀린 질의) | - | 2건 | |
| 릴리스 기준선 대비 누적 하락 (Recall@5, Answer Correctness) | - | 0.05 | 직전 main 대비 δ와 따로 본다 |
| 보안 케이스 | 전부 통과 | - | 예외 없음 |
| 필수 통과 질문 | 전부 | - | |
| JSON 파싱 실패율 | 0 | - | |
| p95 지연 | - | +20% (경고) | |
| 질의당 토큰 | - | +30% (경고) | |

- δ는 변경 없이 같은 설정을 여러 번 돌렸을 때 흔들리는 폭보다 크게 잡는다. 이 폭을 잰 뒤 값을 확정한다.

# 회귀 테스트 파이프라인: CI에서 언제 어떻게 돌리나 (CI Pipeline)

[01-gate-design](./01-gate-design.md)에서 정한 검사를 CI에 연결하는 방법을 정리한다. 어떤 변경에 어떤 계층을 돌릴지, 기준선을 어떻게 관리할지, 결과를 어떻게 보여 줄지 다룬다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 실제 CI 설정 파일과 스크립트는 프로젝트 쪽에 둔다 (README 관련 코드 참고)

## 1. 전체 흐름

```text
PR 생성 / 커밋 push
   │
   ▼
변경 파일 확인 ──▶ 돌릴 계층 결정 (2장)
   │
   ▼
L0 지표 단위 테스트 ─▶ L1 형식·규칙 ─▶ L2 필수 통과 ─▶ L3 검색 회귀 ─▶ L4 생성 회귀
   (실패하면 뒤 단계를 건너뛰고 바로 실패 처리)
   │
   ▼
기준선(main)과 비교 ──▶ 통과 / 경고 / 차단 판정 (01-gate-design 4장)
   │
   ▼
PR에 리포트 게시 (4장)

main 병합 후 ──▶ 기준선 갱신 (3장)
배포 전      ──▶ L5 test 세트 확인 ──▶ 배포 승인
```

- 앞 계층이 실패하면 뒤 계층은 돌리지 않는다. 형식이 깨졌는데 judge 비용을 쓸 필요가 없다.

## 2. 변경 종류별로 돌릴 계층

모든 PR에 L4(생성 + judge)를 돌리면 느리고 비싸다. 바뀐 부분에 맞춰 계층을 고른다.

| 변경 | L0 | L1 | L2 | L3 검색 | L4 생성 | 비고 |
| --- | --- | --- | --- | --- | --- | --- |
| 지표 계산 코드 | ● | | | | | 점수 정의가 바뀌면 기준선 재계산 |
| 검색 코드, 인덱스 설정, 청킹 | ● | ● | ● | ● | ● | 검색이 바뀌면 생성 입력도 바뀜 |
| 임베딩·리랭커 모델 | ● | ● | ● | ● | ● | |
| 생성 프롬프트, 생성 모델 | ● | ● | ● | | ● | 검색 결과는 캐시 재사용 |
| 문서 추가·개정 (색인 재구축, 코드 변경 없음) | | ● | ● | ● | ● | 코드가 그대로여도 검색 결과가 바뀜. 골든셋 노후화 점검도 함께 ([04-update-loop](../03-golden-set/04-update-loop.md) 6장) |
| 의존성 업데이트 (벡터 DB, 토크나이저, 파서 라이브러리) | ● | ● | ● | ● | ● | 버전만 올려도 색인·토큰화·파싱 결과가 바뀔 수 있음 |
| judge 프롬프트·모델 | | | | | | judge 검증(04) 먼저. 통과 후 기준선 재계산 |
| 골든셋 | | | | | | 회귀 판정 대상 아님. 기준선 재계산 |
| 문서만 수정 (노트, README) | | | | | | 돌리지 않음 |
| 정기 실행 (예: 매일 밤) | ● | ● | ● | ● | ● | 외부 모델 API 변화 감지 |

- **정기 실행**이 필요한 이유: 코드가 그대로여도 외부 LLM API의 동작이 바뀔 수 있다. 버전을 고정해도 제공자 쪽 변경이 있을 수 있으므로 하루 한 번 같은 설정을 돌려 기준선과 비교한다.

## 3. 기준선 관리

### 3.1 기준선이란

- main 브랜치의 특정 커밋에서 같은 평가셋, 같은 judge로 돌린 결과다.
- 질의별 결과까지 저장한다. 질의별 회귀와 McNemar 검정에 필요하다.

### 3.2 기준선을 다시 계산하는 경우

| 바뀐 것 | 기준선 | 이유 |
| --- | --- | --- |
| 시스템 (검색, 생성) 변경이 병합됨 | 새 결과로 교체 | 다음 PR의 비교 대상 |
| 배포 (릴리스) | 릴리스 기준선을 이 버전으로 교체 | 누적 하락 기준의 비교 대상 ([01-gate-design](./01-gate-design.md) 4.1). 직전 main 기준선과 따로 보관 |
| 골든셋 버전 | 같은 시스템으로 다시 계산 | 정답이 바뀌면 점수를 비교할 수 없음 ([04-update-loop](../03-golden-set/04-update-loop.md) 4장) |
| judge 모델·프롬프트 | 같은 시스템으로 다시 계산 | judge가 바뀌면 점수가 바뀜 |
| 지표 계산 코드 | 같은 시스템으로 다시 계산 | 점수 정의가 바뀜 |
| 통과 기준(δ, 하한) | 그대로 | 판정 규칙만 바뀜 |

- 평가 도구(골든셋, judge, 지표 코드)가 바뀐 PR과 시스템이 바뀐 PR은 **분리**한다. 한 PR에서 둘 다 바뀌면 점수 변화가 어느 쪽 때문인지 알 수 없다.

### 3.3 기록할 것

기준선마다 다음을 함께 저장한다.

- 시스템 커밋 해시
- 골든셋 버전, dev 표본 ID 목록
- 생성 모델·프롬프트 버전, judge 모델·프롬프트 버전
- 지표 코드 버전
- 질의별 결과, 집계 결과, 비용, 지연 시간

기준선 결과를 날짜순으로 쌓아 지표별 추이를 본다. 매번은 기준을 통과해도 몇 주에 걸쳐 한 방향으로 움직이면 추이에서 먼저 보인다. 정기 실행(2장) 결과도 같은 추이에 넣는다.

## 4. 결과 리포트

PR마다 다음 내용을 게시한다.

| 섹션 | 내용 |
| --- | --- |
| 판정 | 통과 / 경고 / 차단, 실패한 기준 |
| 지표 표 | 지표별 기준선, 현재 값, 차이, 유의성(p값) |
| 질의별 회귀 | 기준선에서 맞고 지금 틀린 질의 목록 (dev, L2만. test는 개수만) |
| 질의별 개선 | 기준선에서 틀리고 지금 맞은 질의 목록 |
| 비용·지연 | 질의당 토큰, p95 지연, 이번 실행의 judge 호출 비용 |
| 실행 조건 | 기준선 커밋, 골든셋 버전, judge 버전 |

- 질의별 회귀 목록이 가장 쓸모 있다. 평균 숫자보다 "어떤 질문이 새로 틀렸나"가 원인을 빨리 찾게 한다.

## 5. 비용과 시간 줄이기

| 방법 | 내용 |
| --- | --- |
| 검색 결과 캐시 | 검색 설정이 그대로면 이전 검색 결과를 재사용하고 생성만 다시 돌린다 |
| judge 결과 캐시 | (judge 모델, 프롬프트 버전, 입력 해시)가 같으면 이전 판정을 재사용한다 |
| 계층별 조기 종료 | 앞 계층 실패 시 뒤 계층 생략 |
| dev 표본 크기 | PR용은 작게(예: 50건), 정기 실행과 배포 전은 크게 |
| 실행 예산 | 1회 실행 judge 비용 상한을 두고, 넘으면 경고 |

- 캐시 키에 버전이 빠지면 judge를 바꿨는데도 이전 판정이 재사용된다. 캐시 키에 모델·프롬프트 버전을 반드시 넣는다.

## 6. 실패 처리

| 상황 | 처리 |
| --- | --- |
| 의도하지 않은 하락 | 질의별 회귀 목록으로 원인 분석 후 수정 |
| 의도한 변경 (예: 비용을 줄이려고 품질을 조금 양보) | PR에 사유를 적고 승인자가 확인한 뒤 병합. 병합 후 기준선 갱신 |
| 노이즈로 의심되는 실패 | 재실행은 한 번만. 재실행으로 통과하면 경고로 기록하고, 같은 테스트가 반복되면 δ나 표본 크기를 다시 본다 |
| 외부 API 장애 | 품질 실패와 구분해서 "실행 실패"로 표시 |
| 운영에서 발견한 실패 | 고친 PR에 그 사례를 L2 운영 버그 회귀 케이스로 추가한다. test 세트에는 넣지 않는다 |
| 보안 케이스 실패 | 품질 기준과 관계없이 차단. 의도한 변경이라는 예외를 두지 않는다 |

- "통과할 때까지 재실행"은 금지한다. 노이즈를 이용해 하락을 통과시키게 된다.

## 7. 도입 순서

| 단계 | 내용 |
| --- | --- |
| 1 | L0 지표 단위 테스트, L1 형식 검사를 CI에 연결 (LLM 비용 없음) |
| 2 | L3 검색 회귀를 **경고 전용**으로 연결, 기준선 저장 시작 |
| 3 | L2 필수 통과 질문 목록 작성 후 차단 기준으로 사용 |
| 4 | judge 검증 통과 후 L4 생성 회귀를 경고 전용으로 연결 |
| 5 | 몇 주간 오탐·미탐을 보고 통과 기준 확정, 차단으로 전환 |
| 6 | 배포 전 L5 test 세트 확인 연결 |

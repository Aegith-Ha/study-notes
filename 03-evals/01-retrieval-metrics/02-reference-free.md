# 정답 없는 검색 지표 (Reference-free)

정답 문서 목록(qrels) 없이, 질문과 검색 결과만으로 검색 품질을 판정하는 지표를 정리한다. 판정은 LLM judge가 맡는다.

- 폴더 요약과 메인 지표는 [README](./README.md) 참고
- 정답 기반 지표는 [01-reference-based](./01-reference-based.md) 참고
- judge 프롬프트 설계, 사람 판정과의 일치도 검증은 [04-llm-judge](../04-llm-judge/README.md)에서 다룬다

## 1. 개념

정답 기반 지표는 "미리 정해 둔 정답과 비교"하고, 정답 없는 지표는 "검색된 결과를 그 자리에서 판정"한다.

```text
정답 기반:  질문 + 검색 결과 + 정답 목록(qrels)  →  계산
정답 없음:  질문 + 검색 결과                     →  LLM judge 판정  →  계산
```

- 골든셋이 없는 질의(운영 트래픽, 새 도메인)에도 적용할 수 있다.
- 대신 **가져온 것만 판정할 수 있다.** 가져오지 못한 정답이 무엇인지는 알 수 없다.

## 2. 지표 정의

판정 등급은 골든셋과 같은 기준(0 = 무관, 1 = 부분 관련, 2 = 관련)을 쓴다. 기호는 [01-reference-based](./01-reference-based.md)와 같다. `j(i)`는 i번째 결과에 대한 judge 등급이다.

| 지표 | 판정 단위 | 정의 | 대응하는 정답 기반 지표 |
| --- | --- | --- | --- |
| Context Relevance@k | 청크별 | top-k 중 judge가 관련(`j(i) ≥ 1`)으로 판정한 비율 | Precision@k |
| Judge Hit@k | 청크별 | 관련 판정이 하나라도 있으면 1 | Hit Rate@k |
| Judge MRR | 청크별 | 1 / (첫 관련 판정의 순위) | MRR |
| Judge nDCG@k | 청크별 | judge 등급으로 계산한 nDCG. IDCG는 **검색된 k개를 다시 정렬**해서 구한다 | nDCG@k (의미가 다름, 아래 참고) |
| Context Sufficiency@k | 집합 | top-k 전체로 질문에 답할 수 있는가 (0/1 또는 0/1/2) | Recall@k의 근사 |

### Judge nDCG가 정답 기반 nDCG와 다른 점

- 정답 기반 nDCG의 IDCG는 **모든 정답**으로 만든다. 놓친 정답이 있으면 점수가 깎인다.
- Judge nDCG의 IDCG는 **검색된 결과 안에서만** 만든다. 놓친 정답은 반영되지 않는다.
- 그래서 Judge nDCG는 "가져온 것들을 잘 정렬했는가"만 본다. 리랭커 효과를 볼 때는 쓸 만하지만, 1차 검색기끼리 비교할 때는 쓰지 않는다.

### Context Sufficiency: Recall 대신 쓰는 근사

- 청크를 하나씩 보는 대신 top-k를 한꺼번에 주고 "이것만으로 답할 수 있는가"를 묻는다.
- 정답 목록 없이 "필요한 근거가 다 들어왔는가"에 가장 가깝게 접근하는 지표다.
- 한계: judge가 질문에 필요한 근거를 모두 알고 있어야 정확하다. 도메인 지식이 필요한 질문(법률·의료·사내 규정 해석 등)에서는 "충분하다"고 과대 판정하기 쉽다.

### 언제 쓰나, 장단점

지표별로 정리한다. 상황별(검색 기법 비교, 운영 모니터링 등)로 쓸지 말지는 8장 참고.

| 지표 | 언제 쓰나 | 장점 | 단점 |
| --- | --- | --- | --- |
| Context Relevance@k | 컨텍스트에 잡음이 얼마나 섞이는지 볼 때, k를 줄일지 정할 때, 운영 모니터링 | 정답 없이도 바로 잴 수 있음, 청크별 판정이라 어떤 청크가 문제인지 보임 | 놓친 정답은 모름, judge가 관대하면 높게 나옴, 비용이 k배 |
| Judge Hit@k | 쓸 만한 청크가 하나도 없는 질의를 찾을 때 | 완전 실패 질의를 세기 쉬움 | 다중 근거 질의에서 일부만 찾아도 1 |
| Judge MRR | 리랭커 전후로 쓸 만한 청크가 위로 올라왔는지 볼 때 | 순서 변화가 바로 보임 | 첫 관련 청크만 봄, judge의 관련/무관 경계에 민감 |
| Judge nDCG@k | 같은 후보 집합을 다시 정렬하는 단계(리랭커) 비교 | 등급과 순서를 함께 반영 | 검색된 것 안에서만 IDCG를 만들어 놓친 정답을 벌주지 않음, 1차 검색기 비교에는 못 씀 |
| Context Sufficiency@k | 근거가 다 들어왔는지 정답 없이 가늠할 때, 답변 품질 문제를 검색 탓인지 나눌 때 | Recall에 가장 가까운 정답 없는 지표, 호출이 질의당 1번이라 쌈 | 도메인 지식이 필요한 질문에서 과대 판정, 어떤 근거가 빠졌는지는 알려 주지 않음 |

### 이렇게 본다

지표별
- **Context Relevance@k**: 정답 기반 Precision@k보다 **높게 나오는 것이 보통**이다. 절대값 대신 같은 judge로 잰 설정 간 차이로 본다. 낮은 질의는 청크별 판정 근거를 열어 어떤 청크가 잡음인지 확인한다.
- **Judge Hit@k**: 0인 질의 수를 센다. 운영 질의에서 이 수가 늘면 인덱스 누락, 필터 오류, 새 유형의 질문을 의심한다.
- **Judge MRR**: 리랭커 전후 같은 후보에서 비교한다. 1차 검색기끼리 비교하면 놓친 정답이 반영되지 않아 판단이 틀릴 수 있다.
- **Judge nDCG@k**: "가져온 것을 잘 정렬했나"로만 읽는다. 1.0에 가까워도 좋은 검색이라는 뜻이 아니다.
- **Context Sufficiency@k**: 1인 비율보다 **0인 질의**를 본다. 0은 "근거가 확실히 부족하다"는 신호라 비교적 믿을 만하고, 1은 과대 판정이 섞여 있다.

조합해서 보기

| 보이는 패턴 | 뜻 | 다음에 할 것 |
| --- | --- | --- |
| Relevance 높고 Sufficiency 0 | 관련 청크는 왔지만 핵심 근거가 빠짐 (다중 근거 질의) | 질의 분해, k 늘리기, 정답 기반 Recall로 확인 |
| Relevance 낮고 Sufficiency 1 | 근거는 있지만 잡음이 많음 | k 줄이기, 리랭커로 걸러 넣기 |
| Judge Hit 0 | 쓸 만한 청크가 하나도 없음 | 검색 실패. 골든셋 질의면 원인 분석, 골든셋 밖 질의면 새 질문 후보 (7장) |
| Judge nDCG만 오름 | 정렬만 좋아짐 | 1차 검색은 그대로. 리랭커 효과로만 해석 |
| Sufficiency 1인데 답변이 틀림 | 생성 문제이거나 judge 과대 판정 | 생성 지표(Faithfulness)와 함께 보고 표본을 사람이 확인 |
| judge 지표는 오르고 정답 기반 지표는 그대로 | judge가 새 검색기 결과에 관대하거나, qrels가 새 문서를 놓침 | 불일치 문서를 사람이 확인 (6장, 7장) |

- 정답 기반 지표가 있는 질의에서는 그쪽이 기준이다. 정답 없는 지표는 골든셋 밖 질의, 불일치 문서 찾기, 운영 추이에 쓴다.

## 3. 손계산 예시

[01-reference-based](./01-reference-based.md)의 q1과 같은 검색 결과를 judge로 판정한 경우

```text
검색 결과 top-5:   d3,  d2,  d7,  d5,  d1
qrels 등급:         -    2    -    1    -     (d9 = 1은 검색 못 함)
judge 등급 j(i):    0    2    1    1    0
Sufficiency@5:     1 (judge: "d2, d5로 답할 수 있다")
```

| 지표 | 계산 | judge 값 | 정답 기반 값 |
| --- | --- | --- | --- |
| Context Relevance@5 / Precision@5 | 3 / 5 | 0.600 | 0.400 |
| Judge MRR / MRR | 첫 관련 d2가 2위 | 0.500 | 0.500 |
| Judge nDCG@5 / nDCG@5 (선형) | DCG = 2/log2(3) + 1/log2(4) + 1/log2(5) = 2.193<br>IDCG = 검색된 등급 [2,1,1,0,0] 정렬 = 2 + 0.631 + 0.5 = 3.131 | 0.700 | 0.541 |
| Sufficiency@5 / Recall@5 | judge 판정 | 1 | 0.667 |

읽는 법
- **d7 차이**: judge는 관련(1)으로 봤지만 qrels에는 없다. judge가 관대하거나, qrels가 d7을 놓쳤거나 둘 중 하나다. 이런 문서는 골든셋 재정비 후보다. 확인과 반영은 7장 참고.
- **nDCG 차이**: judge 쪽 IDCG에는 검색하지 못한 d9가 빠져 있어서 점수가 높게 나온다.
- **Sufficiency = 1, Recall@5 = 0.667**: judge는 d9 없이도 답할 수 있다고 봤다. 정말 그런지, judge가 과대 판정했는지는 정답 기반 결과와 비교해야 알 수 있다.

정답 없는 지표는 정답 기반 지표보다 **높게 나오는 경향**이 있다. 두 계열의 절댓값을 섞어서 비교하지 않는다.

## 4. 판정 설계 (요약)

자세한 설계와 검증은 [04-llm-judge](../04-llm-judge/README.md)에서 다루고, 여기서는 지표 계산에 영향을 주는 결정만 적는다.

| 항목 | 선택지 | 기본값 |
| --- | --- | --- |
| 판정 단위 | 청크별(pointwise) / 집합(top-k 한꺼번에) | Relevance는 청크별, Sufficiency는 집합 |
| 등급 | 이진 / 0·1·2 | 골든셋과 같은 0·1·2 |
| 입력 | 질문 + 청크 본문 (+ 문서 제목, 메타데이터) | 질문 + 청크 본문 + 문서 제목 |
| 출력 | 등급만 / 등급 + 근거 한 줄 | 등급 + 근거 한 줄 (오판 분석용) |
| 재현성 | judge 모델, 프롬프트 버전, temperature 고정 | temperature 0, 프롬프트 버전 기록 |

- 순위 정보(몇 위인지)는 judge에게 주지 않는다. 위쪽 결과를 더 관대하게 판정하는 편향이 생긴다.
- 청크별 판정은 k번 호출하므로 비용이 k배다. 운영 모니터링에서는 질의를 샘플링한다.

## 5. 한계

- **Recall을 측정할 수 없다.** Sufficiency는 근사일 뿐이다.
- **judge 품질이 곧 지표 품질이다.** 검증하지 않은 judge 점수는 기준선으로 쓰지 않는다.
- **judge 편향**
  - 질문과 단어가 많이 겹치는 청크를 관련으로 판정하기 쉽다 (BM25 결과에 유리할 수 있음)
  - 긴 청크를 더 관련 있다고 판정하기 쉽다
  - 도메인 지식이 부족하면 부분 관련과 관련을 구분하지 못한다
- **비용과 지연**: 검색 한 번에 judge 호출이 k번 추가된다.
- **모델이 바뀌면 점수가 바뀐다.** judge 모델을 바꾸면 이전 결과와 비교할 수 없으므로 기준선을 다시 잰다.

## 6. 정답 기반 지표와 맞춰 보기

정답 없는 지표를 쓰기 전에, 골든셋이 있는 질의에서 두 계열이 같은 결론을 내는지 확인한다.

| 확인 | 방법 | 기준 (예시) |
| --- | --- | --- |
| 판정 일치도 | 골든셋 질의에서 judge 등급과 qrels 등급 비교 (판정된 문서만) | 일치율, Cohen's kappa. 기준은 [04-llm-judge 통과 기준](../04-llm-judge/02-human-agreement.md) 참고 |
| 검색기 순위 일치 | 여러 검색기를 두 계열 지표로 각각 순위 매기기 | Kendall's tau. 순위가 뒤집히면 judge 지표로 비교하지 않는다 |
| 불일치 문서 분석 | judge와 qrels가 엇갈리는 문서 | 골든셋 재정비 후보로 넘김 (7장) |

- 절댓값이 아니라 **순위와 방향이 같은지**를 본다. "A 검색기가 B보다 낫다"는 결론이 두 계열에서 같으면 judge 지표를 골든셋 밖에서도 쓸 수 있다.

## 7. 골든셋 재정비

정답 없는 지표를 골든셋과 함께 돌리면, judge 판정과 qrels가 엇갈리는 곳이 생긴다. 이 엇갈림이 골든셋을 고칠 후보다. 이 절은 **어떤 신호를 후보로 뽑는지**까지 다루고, 사람 확인부터 버전 갱신까지의 절차는 [04-update-loop](../03-golden-set/04-update-loop.md)를 따른다.

```text
골든셋 질의에 정답 기반 + 정답 없는 평가를 함께 실행
        │
        ▼
신호 찾기 (아래 표) ──▶ 후보 목록
        │
        ▼
사람이 판정 기준대로 확인 ──▶ 진짜 정답 → qrels 반영 (골든셋 버전 올림)
                          └─▶ judge 오판 → judge 개선 (04-llm-judge)
        │
        ▼
기준선 다시 계산
```

### 7.1 후보로 뽑는 신호

| 신호 | 뜻할 수 있는 것 | 후보 종류 | 확인 후 조치 |
| --- | --- | --- | --- |
| judge ≥ 1, qrels에 없음 (미판정 문서) | 골든셋이 정답을 놓침, 또는 judge가 관대함 | 정답 추가 후보 | 진짜 정답이면 등급을 매겨 qrels에 추가 |
| judge = 0, qrels ≥ 1 | judge 오판, 또는 qrels 오류 (판정 실수, 문서 개정) | 정답 수정 후보 | qrels가 틀렸으면 수정·삭제, judge가 틀렸으면 judge 오판 사례로 기록 |
| judge 등급 ≠ qrels 등급 (2 vs 1) | 핵심/부분 관련 경계가 흔들림 | 등급 재검토 후보 | 우선순위 낮음. 같은 패턴이 반복되면 판정 기준 문장을 보강 |
| 골든셋 질의인데 Recall@k = 1이고 Sufficiency = 0 | qrels 정답만으로는 답이 안 됨 (필요한 문서가 qrels에 빠짐) | 정답 추가 후보 | 답에 필요한 문서를 찾아 qrels에 추가 |
| 골든셋 밖 운영 질의에서 Judge Hit = 0 또는 Sufficiency = 0이 반복 | 골든셋이 다루지 않는 질문 유형 | 새 질문 후보 | 질문 소스 규칙대로 정답 단계를 거쳐 추가 ([01-query-sources](../03-golden-set/01-query-sources.md)) |

- 후보가 많으면 **여러 검색기가 공통으로 상위에 가져온 문서**, **judge 등급 2인 문서**부터 본다. 비교 결과를 뒤집을 가능성이 큰 순서다.
- 새 검색기를 붙였을 때 Judged@k가 떨어지면 첫 번째 신호(미판정 문서)가 몰려 있다는 뜻이다([02-pooling](../03-golden-set/02-pooling.md)).

### 7.2 손계산 예시: d7을 반영하면

3장의 q1에서 d7은 judge = 1, qrels = 없음이었다. 사람이 판정 기준대로 확인한 결과에 따라 갈린다.

| 확인 결과 | 골든셋 | q1 Recall@5 | q1 Precision@5 | 다음 할 일 |
| --- | --- | --- | --- | --- |
| 진짜 부분 관련 → d7 = 1 추가 | v1.0 → v1.1, 정답 {d2, d5, d9, d7} | 2/3 = 0.667 → 3/4 = 0.750 | 2/5 = 0.400 → 3/5 = 0.600 | 모든 검색기의 기준선을 v1.1로 다시 계산 |
| 무관 → 추가 안 함 | 그대로 | 0.667 그대로 | 0.400 그대로 | judge 오판 사례로 기록, 같은 유형이 쌓이면 judge 프롬프트 개선 |

- d7을 추가하면 q1의 정답 기반 점수가 바뀐다. 그래서 **같은 버전의 골든셋으로 잰 점수끼리만** 비교하고, 버전을 올리면 기준선을 다시 잰다.
- d7을 가져온 검색기만 점수가 오른다. 한 검색기 결과만 보고 추가하면 그 검색기에 유리한 골든셋이 되므로, 비교하는 검색기 전부의 미판정 문서를 함께 확인한다.

### 7.3 지킬 것 (요약)

- judge 판정을 그대로 qrels에 넣지 않는다. 사람이 확인한다. 그대로 넣으면 judge가 자기 판정으로 채점하게 된다.
- 판정 기준은 [03-golden-set](../03-golden-set/README.md)의 등급 원본을 그대로 쓴다.
- 최종 확인용(test) 질문은 정해진 주기에만 고친다. 재정비는 튜닝용(dev)에서 한다.
- 버전 규칙, 변경 이력 형식, 진행 상태 지표는 [04-update-loop](../03-golden-set/04-update-loop.md) 4장, 7장, 8장 참고

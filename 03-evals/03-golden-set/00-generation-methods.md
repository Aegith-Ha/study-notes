# 골든셋 생성 방법 목록 (Generation Methods)

평가 데이터(골든셋)를 만드는 일반적인 방법을 **구축 단계별로** 정리한다. 골든셋 하나는 단계마다 방법을 하나 이상 골라 조합해서 만든다. 이 프로젝트에서 실제로 쓰는 조합과 사양은 [README](./README.md)에 둔다.

- 질문 소스(A~D)별 구체적인 방법은 [01-query-sources](./01-query-sources.md) 참고
- 정답 후보를 모으는 Pooling은 [02-pooling](./02-pooling.md) 참고
- 판정 절차와 검수 대상 고르기의 구체적인 방법은 [03-judging-and-review](./03-judging-and-review.md) 참고

## 1. 단계별 방법 목록

골든셋 구축은 네 단계로 나뉜다. 각 방법은 그중 한 단계를 맡는다.

```text
질문 만들기 ──▶ 정답 후보 모으기 ──▶ 판정 ──▶ 골든셋
                                     ▲
                          검수 대상 고르기 (사람 검수를 어디에 쓸지)
```

| 단계 | 만드는 것 | 방법 | 핵심 원리 | 특징 |
|---|---|---|---|---|
| 질문 만들기 | 평가 질문 | Synthetic Data Generation | LLM이 문서를 기반으로 질문과 정답 생성 | 대량 자동 생성 가능 |
| | | Known-Item | 정답 문서를 먼저 선택하고 질문 생성 | 문서 검색 성공 여부 평가 |
| | | User Log 기반 | 실제 사용자 질문 및 피드백 활용 | 실서비스 환경 반영 |
| 정답 후보 모으기 | 질문별 후보 문서 | Pooling | 여러 검색 모델의 결과를 통합하여 정답 후보 수집 | 검색 모델 비교에 적합 |
| | | Weak Supervision | 규칙 및 메타데이터를 기반으로 정답 추정 | 저비용 대량 생성 |
| 판정 | 후보별 등급 (qrels) | Human Annotation | 사람이 질문과 문서의 관련성을 직접 판정 | 높은 신뢰도, 높은 비용 |
| | | LLM-as-a-Judge | LLM이 문서의 관련성을 판정 | 자동 판정에 적합 |
| 검수 대상 고르기 | 사람이 볼 항목 목록 | Active Learning | 판정이 어렵거나 정보 가치가 높은 데이터 우선 검수 | 검수 비용 최적화 |

- 질문은 사람이 직접 쓸 수도 있다(이 프로젝트의 소스 C 상황 시나리오). 별도 기법이 아니라서 표에는 넣지 않았다.
- 단계가 다르면 서로 대신하지 않는다. 예를 들어 Synthetic으로 질문을 만들어도 정답 후보와 판정 단계는 따로 필요하다.

## 2. 질문 만들기

평가에 쓸 질문을 만드는 방법이다. 어떤 방법을 쓰느냐가 골든셋의 **질문 분포**(실제 사용자와 얼마나 비슷한가)를 정한다.

### 2.1 Synthetic Data Generation (합성 데이터 생성)

LLM이 기존 문서를 분석하여 평가 질문과 정답 데이터를 자동 생성하는 방법이다.

**처리 과정**

```text
기존 문서
   ↓
LLM 문서 분석
   ↓
평가 질문 생성
   ↓
정답 문서 연결
   ↓
정답 답변 생성
   ↓
질문 및 정답 검증
   ↓
Golden Set 생성
```

**예시**

원본 문서:

> 연차휴가는 사내 인사시스템에서 신청하며 부서장의 승인을 받아야 한다.

생성 결과:

| 항목 | 내용 |
|---|---|
| 질문 | 연차휴가는 어디에서 신청하나요? |
| 정답 문서 | DOC_001 |
| 정답 답변 | 사내 인사시스템에서 신청합니다. |

**장점**
- 대규모 평가 질문 자동 생성
- 정답 문서와 질문 연결이 쉬움
- 다양한 질문 유형 생성 가능
- 사람의 작성 비용 감소

**단점**
- 실제 사용자 질문과 분포가 다를 수 있음
- 비현실적이거나 지나치게 단순한 질문 생성 가능
- LLM의 잘못된 질문 또는 정답 생성 가능
- 다른 문서에도 정답이 존재할 수 있음 → 출발 문서만 정답으로 두지 말고 3장의 후보 모으기와 4장의 판정을 거친다

**적합한 목적:** 평가 질문 대량 생성 및 초기 Golden Set 구축

---

### 2.2 Known-Item 방식

특정 문서를 정답으로 먼저 선택한 다음, 해당 문서를 검색할 수 있는 질문을 생성하는 방법이다.

**처리 과정**

```text
정답 문서 선택
       ↓
문서 내용 분석
       ↓
해당 문서를 찾는 질문 생성
       ↓
질문과 정답 문서 연결
       ↓
Golden Set 생성
```

**장점**
- 질문과 목표 문서 연결이 명확함
- 자동 평가 데이터 구축이 쉬움
- 특정 문서 검색 가능 여부 검증에 유용

**단점**
- 실제 사용자 질문과 차이가 발생할 수 있음
- 다른 문서에도 정답이 존재할 수 있음
- 원본 문서만 정답으로 설정하면 Recall 왜곡 가능

**적합한 목적:** 특정 문서의 검색 성공 여부 평가

※ Synthetic Data Generation과 결합하여 구현할 수 있는 방식이다. 출발 문서는 정답 후보의 seed가 된다.

---

### 2.3 User Log 기반 생성

실제 서비스에서 발생한 사용자 질문, 검색 결과, 클릭 및 피드백을 활용하여 평가 데이터를 생성하는 방법이다. 질문을 얻는 것이 주목적이고, 클릭 기록은 정답 후보를 보태는 데 쓴다.

**처리 과정**

```text
실제 사용자 질문 로그
          ↓
     질문 정제
          ↓
 검색 결과 및 피드백 수집
          ↓
     정답 후보 추출
          ↓
     관련성 판정
          ↓
      Golden Set
```

**장점**
- 실제 사용자 질문 분포 반영
- 실서비스 성능 평가에 적합
- 실제 검색 실패 사례 분석 가능

**단점**
- 서비스 운영 데이터 필요
- 클릭과 실제 정답이 일치하지 않을 수 있음
- 개인정보 보호 및 로그 정제 필요
- 사용자 행동에 따른 편향 발생 가능

**적합한 목적:** 운영 중인 RAG 시스템의 실사용 성능 평가

---

## 3. 정답 후보 모으기

질문마다 정답일 수 있는 문서를 모으는 방법이다. 여기서 빠진 문서는 판정 단계에 올라가지 못하므로, 이 단계가 골든셋의 **누락**을 정한다.

### 3.1 Pooling

여러 검색 시스템의 상위 검색 결과를 통합하여 정답 문서 후보를 생성하는 방법이다.

**처리 과정**

```text
평가 질문
   ↓
Dense / BM25 / Hybrid 검색
   ↓
각 검색 결과 Top K 수집
   ↓
검색 결과 통합
   ↓
중복 문서 제거
   ↓
관련성 판정 (4장)
   ↓
Golden Set 생성
```

**장점**
- 다양한 검색 방식의 정답 후보 확보
- 특정 검색 모델에 대한 편향 감소
- 검색 모델 간 성능 비교에 적합

**단점**
- 모든 검색 모델이 찾지 못한 정답 문서 누락 가능
- 검색 모델 구성에 따라 Pool 편향 발생 가능
- 관련성 판정 비용 발생

**적합한 목적:** Dense, BM25, Hybrid 등 검색 시스템 성능 비교

---

### 3.2 Weak Supervision (약지도 학습 기반)

문서의 메타데이터, 분류 정보, 업무 코드, 규칙 등을 활용하여 정답 후보를 자동 추정하는 방법이다.

**처리 과정**

```text
질문 + 문서 메타데이터
          ↓
       규칙 적용
          ↓
    정답 문서 자동 추정
          ↓
     Silver Set 생성
          ↓
    선택적 검수 및 확정
```

**예시**

- 질문의 업무 코드와 문서의 업무 코드가 일치
- FAQ 질문과 연결된 답변 문서 사용
- 문서 카테고리 및 키워드 일치
- 기존 업무 시스템의 질문-문서 연결 정보 활용

**장점**
- 대량 데이터 자동 생성
- LLM 없이도 구현 가능
- 기존 시스템의 메타데이터 활용 가능

**단점**
- 규칙의 정확도에 의존
- 정답 누락 및 오탐 가능
- 복잡한 의미 관계 판단에 한계

**적합한 목적:** 초기 Silver Set 구축, Pooling 후보 보충

---

## 4. 판정

모은 후보마다 관련성 등급(0 / 1 / 2)을 매기는 방법이다. 이 단계가 골든셋의 **정확도**를 정한다. 등급 정의는 [README](./README.md)의 판정 기준을 따르고, 사람과 LLM이 같은 기준을 쓴다. 판정을 합치고 최종 등급을 정하는 절차는 [03-judging-and-review](./03-judging-and-review.md) 2장 참고

| | Human Annotation | LLM-as-a-Judge |
|---|---|---|
| 판정자 | 도메인 전문가, 담당자 | LLM |
| 신뢰도 | 높음 (판정자 간 차이는 있음) | 검증 전에는 알 수 없음 |
| 비용 | 높음 | 낮음 |
| 골든셋에서의 역할 | 최종 확정 | 1차 판정 |

### 4.1 Human Annotation (사람이 직접 판정)

도메인 전문가 또는 담당자가 평가 질문에 관련된 문서를 직접 확인하여 정답 데이터를 생성하는 방법이다. 후보 없이 처음부터 할 때는 담당자가 직접 검색해서 후보를 모으는 일까지 겸한다.

**처리 과정**

```text
평가 질문
   ↓
담당자 문서 검색 (후보가 없을 때)
   ↓
관련 문서 검토
   ↓
관련성 점수 부여
   ↓
Golden Set 생성
```

**장점**
- 도메인 지식을 반영한 높은 신뢰도
- 복잡한 질문 및 문서 관계 판정 가능
- 자동 판정 결과의 품질 검증 가능

**단점**
- 시간과 비용이 많이 소요됨
- 평가자 간 판단 차이 발생 가능
- 대규모 데이터 구축에 한계

**적합한 목적:** 고신뢰도 Golden Set 구축 및 자동 판정 검증

---

### 4.2 LLM-as-a-Judge

LLM을 평가자로 사용하여 질문과 문서의 관련성을 판정하는 방법이다. Pooling이나 Weak Supervision으로 모은 후보를 **1차 판정**해서 사람 판정 양을 줄인다.

- 골든셋에서는 judge 판정을 그대로 확정하지 않고 사람이 검수한 것만 넣는다 ([04-update-loop](./04-update-loop.md) 4장).
- 쓰기 전에 사람 판정과의 일치도(kappa)를 확인한다. judge 설계와 검증은 [04-llm-judge](../04-llm-judge/README.md) 참고

## 5. 검수 대상 고르기

사람 검수 예산을 어느 항목에 쓸지 정하는 방법이다. 판정 결과를 바꾸지는 않고, 사람이 볼 순서만 정한다. 우선 검수 신호, 검수 양, 멈추는 기준은 [03-judging-and-review](./03-judging-and-review.md) 3장 참고

### 5.1 Active Learning (능동 학습)

전체 평가 후보를 사람이 검수하는 대신, 판정하기 어렵거나 정보 가치가 높은 데이터만 우선적으로 선택하여 검수하는 방법이다.

**처리 과정**

```text
평가 후보 데이터
        ↓
LLM 또는 판정 모델 평가
        ↓
불확실한 데이터 선별
        ↓
사람이 우선 검수
        ↓
검수 결과 반영
        ↓
추가 검수 대상 선정
```

**장점**
- 사람의 검수 비용 감소
- 어려운 사례에 검수 집중
- 평가 데이터 품질을 효율적으로 개선

**단점**
- 불확실성 판단 기준 필요
- 초기 판정 모델의 품질에 영향받음
- 전체 데이터의 대표성이 부족해질 수 있음 → 무작위 표본 검수를 함께 둔다

**적합한 목적:** 대규모 Pooling 데이터의 검수 비용 최적화

- 이 프로젝트의 "경계 등급(1) + judge 불일치 항목" 검수([README](./README.md) 구축 흐름)가 이 방식의 단순한 형태다. 신호별 우선순위는 [03-judging-and-review](./03-judging-and-review.md) 3.2 참고

## 6. 방법별 비교

| 단계 | 방법 | 자동화 수준 | 사람 검수 비용 | 주요 특징 |
|---|---|---|---|---|
| 질문 만들기 | Synthetic | 높음 | 낮음~중간 | 질문 대량 생성 |
| | Known-Item | 높음 | 낮음~중간 | 정답 문서 기반 질문 생성 |
| | User Log | 중간 | 중간 | 실사용 데이터 반영 |
| 정답 후보 모으기 | Pooling | 높음 | (판정 단계에서 발생) | 다양한 검색 결과 통합 |
| | Weak Supervision | 높음 | 낮음~중간 | 규칙 기반 자동 정답 추정 |
| 판정 | Human Annotation | 낮음 | 높음 | 고신뢰도 판정 |
| | LLM-as-a-Judge | 높음 | 낮음~중간 (검수분) | 관련성 자동 판정 |
| 검수 대상 고르기 | Active Learning | 중간~높음 | 최적화 가능 | 우선 검수 대상 선정 |

※ 자동화 수준과 비용은 일반적인 경향이며, 실제 문서 품질과 검증 기준에 따라 달라진다. 비교는 같은 단계 안에서만 의미가 있다.

## 7. 평가 목적에 따른 조합

| 평가 목적 | 질문 만들기 | 정답 후보 모으기 | 판정 (+ 검수 대상) |
|---|---|---|---|
| Dense vs BM25 vs Hybrid 검색 비교 | 아무 방법 | **Pooling** (비교 대상 검색기 전부) | LLM-as-a-Judge + Human Annotation |
| 평가 질문 대량 생성 | **Synthetic** | 출발 문서 + Pooling | LLM-as-a-Judge + 표본 검수 |
| 특정 문서 검색 성공 여부 평가 | **Known-Item** | 출발 문서 | 출발 문서만 정답으로 보면 Recall 왜곡 주의 |
| 실제 사용자 검색 품질 평가 | **User Log** | Pooling + 클릭 기록 | Human Annotation |
| 신뢰도 높은 정답 데이터 구축 | 아무 방법 | Pooling | **Human Annotation** |
| 판정 비용 절감 | 아무 방법 | Pooling | **LLM-as-a-Judge** + **Active Learning**으로 고른 항목만 사람 검수 |
| 메타데이터 기반 자동 생성 | 기존 FAQ 등 | **Weak Supervision** | 선택적 검수 |
| 여러 문서를 조합하는 추론 평가 | Multi-hop Synthetic | 출발 문서들 + Pooling | Human Annotation |

## 8. 질문 소스(A~D)와의 대응

[01-query-sources](./01-query-sources.md)의 질문 소스는 위 단계별 방법을 조합한 것이다.

| 질문 소스 | 질문 만들기 | 정답 후보 모으기 | 판정 |
| --- | --- | --- | --- |
| A 기존 질의응답 데이터 | 기존 자료 재작성 | 자료가 인용한 근거(seed) + Pooling | LLM-as-a-Judge + Human Annotation |
| B 문서 → 질문 | Synthetic, Known-Item | 출발 문서(seed) + Pooling | LLM-as-a-Judge + Human Annotation |
| C 상황 시나리오 | 사람이 직접 작성 | Pooling | LLM-as-a-Judge + Human Annotation |
| D 실제 사용 로그 | User Log | Pooling (+ 클릭 기록) | LLM-as-a-Judge + Human Annotation |

- Weak Supervision은 메타데이터가 있으면 정답 후보를 늘리는 데, Active Learning은 사람 검수 대상을 고르는 데 덧붙인다.
- 판정 단계는 네 소스 모두 같다. 질문 출처와 관계없이 정답은 같은 방식으로 정한다([01-query-sources](./01-query-sources.md) 공통 정답 단계).

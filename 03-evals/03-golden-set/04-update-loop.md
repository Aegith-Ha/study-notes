# 골든셋 갱신 루프 (Golden Set Update Loop)

골든셋은 한 번 만들고 끝나는 것이 아니라, 정답 기반 평가와 정답 없는 평가를 함께 돌리면서 계속 고쳐 나가는 것이다. 이 노트는 골든셋이 낡는 이유와, judge가 찾은 누락 후보를 골든셋에 반영하는 절차를 정리한다.

- 골든셋을 처음 만드는 방법은 [README](./README.md), [01-query-sources](./01-query-sources.md), [02-pooling](./02-pooling.md), [03-judging-and-review](./03-judging-and-review.md) 참고
- 정답 기반 지표와 정답 없는 지표는 [01-retrieval-metrics](../01-retrieval-metrics/README.md), [02-generation-metrics](../02-generation-metrics/README.md) 참고
- judge 설계와 검증은 [04-llm-judge](../04-llm-judge/README.md)에서 다룬다
- 검색 지표 쪽에서 어떤 신호를 후보로 뽑는지는 [01-retrieval-metrics/02-reference-free](../01-retrieval-metrics/02-reference-free.md) 7장 참고

## 1. 왜 갱신해야 하나

정답 기반 지표의 신뢰도는 골든셋 품질만큼만 높다. 골든셋은 만든 뒤에도 네 가지 이유로 낡는다.

| 문제 | 내용 | 결과 |
| --- | --- | --- |
| **누락** | 정답 문서를 다 찾지 못함 (pooling에 안 걸린 문서) | 새 검색기가 진짜 정답을 가져와도 오답 처리 → **새 방법이 과소평가됨** |
| **대표성** | 질문 분포가 실제 사용자 질문과 다름 | 골든셋 점수는 높은데 운영 체감은 나쁨 |
| **노후화** | 문서가 개정·추가·폐지되는데 골든셋은 그대로 | 예전 정답 기준으로 채점 → 최신 문서를 가져오면 오답 |
| **과적합** | 같은 골든셋으로 계속 튜닝 | 골든셋 점수만 오르고 실제 성능은 그대로 |

예: 골든셋을 BM25 결과로 pooling해서 만들었다면, dense 검색이 찾아온 새 정답은 골든셋에 없어서 오답이 된다. 갱신하지 않으면 [04-advanced-rag](../../04-advanced-rag/README.md)의 BM25 vs dense 비교가 BM25 쪽으로 기운다.

## 2. 갱신 루프

```text
        ┌──────────────────────────────────────────────────┐
        ▼                                                  │
[골든셋 vN] ──▶ 정답 기반 평가 + 정답 없는 평가 동시 실행         │
                       │                                   │
                       ▼                                   │
          불일치 찾기: judge = 관련, qrels = 없음 (또는 반대)    │
                       │                                   │
                       ▼                                   │
              사람이 확인 (판정 기준대로)                     │
                       │                                   │
            ┌──────────┴──────────┐                        │
            ▼                     ▼                        │
     진짜 정답 → qrels 반영     judge 오판 → judge 개선      │
            │                   (04-llm-judge)             │
            ▼                                              │
     [골든셋 vN+1] ──▶ 기준선 다시 계산 ──────────────────────┘
```

- 골든셋과 judge가 서로를 점검한다. 골든셋은 judge 덕분에 누락이 줄고, judge는 골든셋 덕분에 오판 패턴이 드러난다.
- 불일치는 양방향으로 본다.
  - judge = 관련, qrels = 없음 → **골든셋 누락 후보**
  - judge = 무관, qrels = 정답 → **judge 오판 후보** 또는 **골든셋 오류 후보** (정답 판정이 틀렸거나 문서가 개정됨)

## 3. 반영하는 것

| 종류 | 출처 | 예 | 확인 방법 |
| --- | --- | --- | --- |
| 기존 질문에 정답 문서 추가 | judge = 관련, qrels = 없음 | q1에 d7을 정답(1)으로 추가 | 판정 기준대로 사람이 등급 부여 |
| 기존 정답 수정·삭제 | judge = 무관, qrels = 정답 / 문서 개정 | 개정 전 문서를 개정 후 문서로 교체 | 문서 변경 이력과 대조 |
| 새 질문 추가 | 정답 없는 지표가 낮은 운영 질의 | Sufficiency = 0이 반복되는 질문 유형 | 질문 소스 규칙([01-query-sources](./01-query-sources.md))대로 정답 단계 진행 |
| 질문 삭제 | 더 이상 유효하지 않은 질문 | 폐지된 제도에 대한 질문 | 삭제 사유 기록 |

새 질문 추가는 운영 피드백 루프([06-llmops/04-feedback-loop](../../06-llmops/04-feedback-loop/README.md))와 이어진다.

## 4. 지켜야 할 규칙

잘못 돌리면 골든셋이 오히려 오염된다.

| 규칙 | 이유 |
| --- | --- |
| **judge 판정을 그대로 넣지 않는다. 사람이 확인한다** | judge 판정을 정답으로 넣으면 judge가 스스로를 채점하게 된다. 골든셋이 judge 편향을 물려받는다 |
| **비교 대상 검색기 전부의 결과를 함께 판정한다** | 새 검색기 결과만 추가 판정하면 그 검색기에만 유리한 골든셋이 된다 |
| **판정 기준(등급 정의)은 [README](./README.md) 원본을 그대로 쓴다** | 회차마다 기준이 흔들리면 같은 골든셋 안에서 정답의 의미가 달라진다. 기준을 바꿀 때는 버전을 올리고 기존 판정도 다시 본다 |
| **골든셋 버전을 올리고 기준선을 다시 계산한다** | v1과 v2는 정답이 달라 점수를 직접 비교할 수 없다 |
| **최종 확인용 질문은 고정한다** | 계속 바꾸면 "나아졌다"를 확인할 고정된 자가 없어진다 (5장) |
| **변경 이력을 남긴다** | 어떤 문서를 왜 바꿨는지 추적할 수 있어야 판정 기준이 흔들렸는지 알 수 있다 (7장) |

## 5. 튜닝용과 확인용 분리

같은 골든셋으로 튜닝과 최종 확인을 모두 하면 과적합을 알아챌 수 없다.

| 구분 | 비율 (예: 200개) | 용도 | 갱신 |
| --- | --- | --- | --- |
| 튜닝용 (dev) | 150개 | 기법 비교, 파라미터 조정, 불일치 분석 | 갱신 루프로 **자주** 갱신 |
| 확인용 (test) | 50개 | 배포 전 최종 확인, 회귀 테스트 | **정해진 주기**에만 갱신 (예: 분기) |

- 두 세트의 질문 유형 분포를 맞춘다. 무작위로 나누되 유형별로 비율을 유지한다(층화 추출).
- 확인용 질문은 튜닝 중에 들여다보지 않는다. 오답 분석도 튜닝용에서만 한다.
- 튜닝용 점수는 오르는데 확인용 점수가 그대로면 과적합 신호다.

## 6. 노후화 대응

| 상황 | 대응 |
| --- | --- |
| 문서 개정 | 개정된 문서를 정답으로 가진 질문을 찾아 정답 재검수 |
| 문서 추가 | 새 문서가 기존 질문의 정답이 될 수 있는지 pooling으로 확인 |
| 문서 폐지 | 폐지 문서를 정답으로 가진 질문의 정답 교체 또는 질문 삭제 |
| 정기 점검 | 정해진 주기에 Judged@k, judge 불일치율 확인 |

- 문서 ID가 바뀌면 qrels가 깨진다. 문서마다 고정 ID와 버전(개정일)을 따로 둔다.

## 7. 버전과 변경 이력

### 버전 규칙 (초안)

| 변경 | 버전 | 기준선 재계산 |
| --- | --- | --- |
| 정답 문서 추가·수정, 질문 추가·삭제 | 마이너 (v1.0 → v1.1) | 필요 |
| 판정 기준(등급 정의) 변경, 확인용 세트 교체 | 메이저 (v1 → v2) | 필요, 이전 버전과 비교 불가 표시 |

### 변경 이력 기록 형식

| 버전 | 날짜 | 질문 ID | 변경 | 문서 ID | 등급 | 출처 | 근거 | 확인자 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| v1.1 | - | q1 | 정답 추가 | d7 | 1 | judge 불일치 | (judge 근거 한 줄) | - |

- 출처: judge 불일치 / 문서 개정 / 운영 로그 / 사람 검수
- 이 기록은 프로젝트 쪽 골든셋 파일과 함께 관리하고, 노트에는 회차별 요약(8장)만 남긴다.

## 8. 진행 상태

### 보는 지표

| 지표 | 의미 |
| --- | --- |
| 회차별 추가된 정답 문서 수 | 줄어들면 골든셋이 안정되는 중 |
| Judged@10 | 올라가면 판정 안 된 문서가 줄어드는 중 |
| judge-사람 일치율 | 올라가면 judge를 더 믿을 수 있음 |
| judge 오판 비율 | 높으면 judge 프롬프트나 등급 기준을 고칠 차례 |
| 튜닝용 vs 확인용 점수 차이 | 벌어지면 과적합 신호 |

- 추가되는 정답이 거의 없어지면 골든셋이 충분히 완성됐다는 신호다. 그때부터는 문서가 바뀔 때와 새 질문 유형이 생길 때만 갱신한다.

### 회차별 요약

| 회차 | 버전 | 날짜 | 판정한 불일치 | 정답 추가 | 정답 수정·삭제 | 질문 추가·삭제 | judge 오판 | Judged@10 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | v1.0 → v1.1 | - | - | - | - | - | - | - |

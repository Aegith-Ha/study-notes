# 평가 질의 만드는 방법 A~D

평가셋은 **질의**와 **정답 문서** 한 세트로 이루어진다. 질의는 아래 네 가지 소스(A~D) 중 하나로 만들고, 소스를 바꾸거나 섞어 쓸 수 있다. 정답은 소스와 관계없이 **같은 방식**으로 정한다. 검색 결과를 모아 후보를 만들고(pool), 후보마다 등급을 판정한다(judge).

- 소스 비중, 질문 수, 판정 기준 등 이 프로젝트의 결정은 [README](./README.md) 사양 참고
- 각 소스가 어떤 일반적인 생성 방법의 조합인지는 아래 "생성 방법과의 대응" 참고. 방법별 설명은 [00-generation-methods](./00-generation-methods.md)

소스마다 다른 것은 두 가지뿐이다.

- 질의를 어디서 어떻게 얻는가
- 처음부터 정답 후보(seed)가 있는가

기존 질의응답 데이터(A)가 없는 경우에도 B~D와 공통 정답 단계만으로 같은 체계를 쓸 수 있다.

## A. 기존 질의응답 데이터

FAQ, 고객 문의 답변, 전문가 상담 기록처럼 **질문과 근거 문서가 함께 있는 자료**를 가져오는 방법이다.

- **방법:** 질문과 근거가 함께 있는 자료를 가져온다.
  - 질문 원문은 그대로 쓰지 않고 일반 사용자 말투(`user`)와 전문가 말투(`expert`)로 다시 쓴다.
  - 문서 제목, 문서 번호, 원문 구절이 질의에 새지 않았는지 유출 검사를 한다. 새면 검색기가 단어만 맞춰도 정답을 찾아 점수가 부푼다.
- **seed:** 있음. 자료가 근거로 든 문서다(핵심 근거는 2 관련, 부수 근거는 1 부분 관련).
- **장점:** 실제로 나온 질문이고 전문가가 확인한 근거가 있어 정답 신뢰도가 가장 높다.
- **단점:**
  - 자료의 분포를 따라간다. 예를 들어 전문가 상담 기록이면 전문적인 쟁점에 치우치고 일상 질문이 적다.
  - 자료가 근거로 들지 않은 다른 적절한 문서는 놓친다.
  - 공개 자료라면 LLM 학습 데이터에 들어 있을 수 있다. 질문을 다시 써도 내용을 외워 검색 없이 맞힐 수 있으므로, 컨텍스트 없이 LLM만으로 답한 점수를 함께 기록해 둔다.
- **언제 쓰나:** 이런 자료가 있으면 주력 소스로 쓴다.

## B. 문서 → 질문 (문서를 보고 질문 생성)

- **방법:** 문서를 표본으로 뽑고, LLM이나 사람이 그 문서로 답할 수 있는 질문을 만든다.
- **seed:** 있음. 출발한 문서가 seed다.
- **장점:** 자동화가 쉽고 문서 종류(예: 정책, 매뉴얼, 공지)를 고르게 덮을 수 있다.
- **단점:**
  - 문서 표현이 질문에 묻어나 점수가 부풀기 쉽다.
  - 실제 사용자 질문과 거리가 있다.
- **언제 쓰나:** 특정 문서나 문서 종류가 검색되는지 진단할 때 작게 쓴다.

## C. 상황 시나리오 먼저 (문서를 보지 않고 질문 생성)

- **방법:** 주제 목록(예: 환불, 배송 지연, 계정 잠금)과 사용자 유형을 정하고, 문서를 보지 않은 채 실제 겪을 법한 상황 질문을 쓴다.
- **seed:** 없음. 정답은 전적으로 pool + judge로 정한다.
- **장점:**
  - 실제 사용 분포에 가깝다.
  - 질문 쓰는 사람이 정답 문서의 표현을 보지 않으므로 유출이 없다.
- **단점:** pool 편향이 생긴다. 현재 검색기가 못 찾은 정답은 판정 대상에 들지 않는다.
  - 대책: 질의를 바꿔 쓴 검색과 문서 제목·분류 검색 결과를 pool에 추가한다.
  - 남은 누락은 [04-update-loop](./04-update-loop.md)로 고친다.
- **언제 쓰나:** A가 덮지 못하는 질문 유형(일상 질문 등)을 채울 때, 또는 A가 없을 때 주력으로 쓴다.

## D. 실제 사용 로그

- **방법:** 서비스 검색 로그에서 질의를 표본 추출한다. 개인정보를 걸러 내고 중복·무의미 질의를 지운다.
- **seed:** 기본은 없음. 클릭 기록이 있으면 약한 seed로 쓴다.
- **장점:** 진짜 사용자 분포다.
- **단점:**
  - 서비스를 연 뒤에만 쓸 수 있고, 개인정보 처리가 필요하다.
  - C와 같은 pool 편향이 있다.
- **언제 쓰나:** 서비스를 연 뒤 로그가 쌓이면 C를 점차 대체한다.

## 한눈에 비교

| 소스 | 질의 출처 | seed | 현실성 | 정답 신뢰도 | 자동화 | 주로 쓰는 역할 |
|---|---|---|---|---|---|---|
| A 질의응답 데이터 | FAQ, 상담 기록 등 | 있음 | 중 | 높음 | 중 | 주력 (자료가 있을 때) |
| B 문서→질문 | 문서 | 있음 | 낮음 | 중 | 높음 | 진단용 |
| C 상황 시나리오 | 주제 목록 | 없음 | 높음 | pool 의존 | 중 | 보완, A가 없으면 주력 |
| D 사용 로그 | 실제 사용자 | 약함/없음 | 가장 높음 | pool 의존 | 중 | 서비스를 연 뒤 |

## 생성 방법과의 대응

각 소스는 [00-generation-methods](./00-generation-methods.md)의 단계별 방법을 조합한 것이다.

| 질문 소스 | 질문 만들기 | 정답 후보 모으기 | 판정 |
| --- | --- | --- | --- |
| A 기존 질의응답 데이터 | 기존 자료 재작성 | 자료가 근거로 든 문서(seed) + Pooling | LLM-as-a-Judge + Human Annotation |
| B 문서 → 질문 | Synthetic, Known-Item | 출발 문서(seed) + Pooling | LLM-as-a-Judge + Human Annotation |
| C 상황 시나리오 | 사람이 직접 작성 | Pooling | LLM-as-a-Judge + Human Annotation |
| D 실제 사용 로그 | User Log | Pooling (+ 클릭 기록) | LLM-as-a-Judge + Human Annotation |

- 소스마다 다른 것은 질문 만들기와 seed 유무뿐이고, 판정은 네 소스 모두 같다(아래 공통 정답 단계).
- Weak Supervision은 메타데이터가 있으면 정답 후보를 늘리는 데, Active Learning은 사람 검수 대상을 고르는 데 덧붙인다.

## 공통 정답 단계 (모든 소스)

1. **Pool:** 질의마다 계열이 다른 여러 검색기(예: BM25, 서로 다른 임베딩 모델, hybrid)의 상위 결과(예: 20개)를 합치고 seed를 더한다. 바꿔 쓴 질의의 검색 결과도 넣는다. 자세한 내용은 [02-pooling](./02-pooling.md) 참고
2. **Judge:** 후보 문서마다 등급을 매긴다.
   - 등급: 2 관련 / 1 부분 관련 / 0 무관. 정의는 [README](./README.md) 판정 기준을 그대로 쓴다.
   - LLM으로 판정하되, 일부는 사람이 매겨서 일치도(kappa)를 확인한다. 검증 방법은 [04-llm-judge/02-human-agreement](../04-llm-judge/02-human-agreement.md) 참고
3. **판정 단위:** 같은 상황에서 나온 질의(`user`/`expert`)는 판정 결과를 공유한다(`case_id`).
4. **판정 안 된 문항:** 평가에서 뺀다.

## 답 없음 질의 만들기

문서에 근거가 없는 질문은 거절을 제대로 하는지 재는 데 쓴다. 종류를 나눠 만들어야 거절 능력을 제대로 잴 수 있다.

| 종류 | 만드는 법 | 예 (색인 범위: 환불·배송 정책) | 어려움 |
| --- | --- | --- | --- |
| 범위 밖 | 색인에 아예 없는 주제로 질문 | "주식 양도세 신고는 어떻게 하나요?" | 쉬움. 검색 결과가 확실히 무관해서 거절하기 쉽다 |
| 가까운 주제 | 관련 문서는 있지만 질문한 세부 내용은 문서에 없음 | "중고 상품 환불 기한은?" (환불 정책에 중고 상품 기준이 없음) | 어려움. 비슷한 문서를 근거로 그럴듯한 답을 지어내기 쉽다 |
| 시점 밖 | 문서에 아직 반영되지 않은 정보 | "내년부터 바뀌는 환불 정책은?" | 보통 |

- **가까운 주제를 절반 이상** 둔다. 범위 밖만 있으면 거절 정확도가 부풀려진다.
- 만든 뒤에도 일반 질문과 똑같이 pool과 판정을 거친다. **판정 결과 2가 하나도 없어야** `답 없음`으로 확정하고, 2가 나오면 일반 질문으로 돌린다.
- 전제가 틀린 질문(예: "환불 기한이 30일인데 왜 거절됐나요?", 문서상 7일)은 답 없음이 아니다. 전제를 바로잡는 답이 정답이므로 일반 질문으로 둔다.
- 정답 문서가 없으므로 검색 지표(Recall 등) 계산에서는 빠지고, 생성 쪽 거절 정확도에만 쓴다([02-generation-metrics/01-reference-based](../02-generation-metrics/01-reference-based.md) 3.4).

## 운영 원칙

- **점수는 소스별로 따로 본다.** 섞으면 B처럼 쉬운 셋이 평균을 끌어올린다.
- **최종 확인용을 떼어 둔다.** 소스마다 일부를 최종 확인용(test)으로 떼어 두어, 튜닝이 평가셋에 맞춰지는 것을 막는다. 분리 방법은 [04-update-loop](./04-update-loop.md) 5장 참고
- **비중은 주 사용자에 따라 정한다.** 일반 사용자가 많으면 C를, 전문가·실무자가 많으면 A를 늘린다. B는 진단용으로 소량만 둔다(예: A 6 : C 3 : B 1).
- **목표 칸을 먼저 정하고 채운다.** 소스 비중과 별개로 답변 유형·주제·난이도 목표([README](./README.md) 질문 구성)를 정하고, 빈 칸은 그 칸을 채우기 쉬운 소스로 채운다.

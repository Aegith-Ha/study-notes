# 평가 질의 만드는 방법 A~D

평가셋은 **질의**와 **정답 조문** 한 세트로 이루어진다. 질의는 아래 네 가지 소스(A~D) 중 하나로 만들고, 소스를 바꾸거나 섞어 쓸 수 있다. 정답은 소스와 관계없이 **같은 방식**으로 정한다. 검색 결과를 모아 후보를 만들고(pool), 후보마다 등급을 판정한다(judge).

- 소스 비중, 질문 수, 판정 기준 등 이 프로젝트의 결정은 [README](./README.md) 사양 참고
- 일반적인 생성 방법과의 대응은 [00-generation-methods](./00-generation-methods.md) 5장 참고

소스마다 다른 것은 두 가지뿐이다.

- 질의를 어디서 어떻게 얻는가
- 처음부터 정답 후보(seed)가 있는가

해석례 같은 질의응답 데이터가 없는 프로젝트에서도 B~D와 공통 정답 단계만으로 같은 체계를 쓸 수 있다.

## A. 기존 질의응답 데이터 (예: 법령해석례)

- **방법:** 질의와 근거가 함께 있는 공개 자료를 가져온다.
  - 질문 원문은 그대로 쓰지 않고 사용자 말투(`user`)와 전문가 말투(`expert`)로 다시 쓴다.
  - 법령명, 조문 번호, 원문 구절이 질의에 새지 않았는지 유출 검사를 한다.
- **seed:** 있음. 자료가 인용한 조문이다(핵심 인용은 2 관련, 부수 인용은 1 부분 관련).
- **장점:** 실제 쟁점이고 전문가가 확인한 근거가 있어 정답 신뢰도가 가장 높다.
- **단점:**
  - 자료의 분포를 따라간다. 해석례는 행정·기관 쟁점에 치우친다.
  - 인용되지 않은 적절한 조문은 놓친다.
- **lawlens 역할:** 주력. 시범 50건(100문항)을 만들었다.

## B. 문서 → 질문 (조문을 보고 질문 생성)

- **방법:** 조문을 표본으로 뽑고, LLM이나 사람이 그 조문으로 답할 수 있는 질문을 만든다.
- **seed:** 있음. 출발한 조문이 seed다.
- **장점:** 자동화가 쉽고 법령 종류(법률·시행령·시행규칙)를 고르게 덮을 수 있다.
- **단점:**
  - 조문 표현이 질문에 묻어나 점수가 부풀기 쉽다.
  - 실제 사용자 질문과 거리가 있다.
- **lawlens 역할:** 진단용으로 작게만 쓴다.

## C. 상황 시나리오 먼저 (조문을 보지 않고 질문 생성)

- **방법:** 주제 목록(전세, 퇴직금, 교통사고 등)과 사용자 유형을 정하고, 조문을 보지 않은 채 실제 겪을 법한 상황 질문을 쓴다.
- **seed:** 없음. 정답은 전적으로 pool + judge로 정한다.
- **장점:**
  - 실제 사용 분포에 가장 가깝다.
  - 질문 쓰는 사람이 정답 표현을 보지 않으므로 유출이 없다.
- **단점:** pool 편향이 생긴다. 현재 검색기가 못 찾은 정답은 판정 대상에 들지 않는다.
  - 대책: 질의를 바꿔 쓴 검색과 법령명 검색 결과를 pool에 추가한다.
  - 남은 누락은 [03-update-loop](./03-update-loop.md)로 고친다.
- **lawlens 역할:** A의 빈 곳(일상 질문)을 채우는 보완용이다. 아직 생성기가 없다.

## D. 실제 사용 로그

- **방법:** 서비스 검색 로그에서 질의를 표본 추출한다. 개인정보를 걸러 내고 중복·무의미 질의를 지운다.
- **seed:** 기본은 없음. 클릭 기록이 있으면 약한 seed로 쓴다.
- **장점:** 진짜 사용자 분포다.
- **단점:**
  - 서비스를 연 뒤에만 쓸 수 있고, 개인정보 처리가 필요하다.
  - C와 같은 pool 편향이 있다.
- **lawlens 역할:** 아직 쓸 수 없다. 로그가 쌓이면 C를 점차 대체한다. 로드맵의 "실제 사용자 질문 로그 기반 골든셋"이 이 단계다.

## 한눈에 비교

| 소스 | 질의 출처 | seed | 현실성 | 정답 신뢰도 | 자동화 | lawlens 역할 |
|---|---|---|---|---|---|---|
| A 질의응답 데이터 | 해석례 등 | 있음 | 중 | 높음 | 중 | 주력 |
| B 문서→질문 | 조문 | 있음 | 낮음 | 중 | 높음 | 진단용 |
| C 상황 시나리오 | 주제 목록 | 없음 | 높음 | pool 의존 | 중 | 보완 |
| D 사용 로그 | 실제 사용자 | 약함/없음 | 가장 높음 | pool 의존 | 중 | 서비스를 연 뒤 |

## 공통 정답 단계 (모든 소스)

1. **Pool:** 질의마다 hybrid, dense, sparse 검색 결과 상위 20개의 합집합에 seed를 더한다. C와 D는 추가 검색 결과도 넣는다. 자세한 내용은 [02-pooling](./02-pooling.md) 참고
2. **Judge:** 후보 조문마다 등급을 매긴다.
   - 등급: 2 관련 / 1 부분 관련 / 0 무관. 정의는 [README](./README.md) 판정 기준을 그대로 쓴다.
   - LLM으로 판정하되, 일부는 사람이 매겨서 일치도(kappa)를 확인한다. 검증 방법은 [04-llm-judge/02-human-agreement](../04-llm-judge/02-human-agreement.md) 참고
3. **판정 단위:** 같은 상황에서 나온 질의(`user`/`expert`)는 판정 결과를 공유한다(`case_id`).
4. **판정 안 된 문항:** 평가에서 뺀다.

## 운영 원칙

- **점수는 소스별로 따로 본다.** 섞으면 B처럼 쉬운 셋이 평균을 끌어올린다.
- **최종 확인용을 떼어 둔다.** 소스마다 일부를 최종 확인용(test)으로 떼어 두어, 튜닝이 평가셋에 맞춰지는 것을 막는다. 분리 방법은 [03-update-loop](./03-update-loop.md) 5장 참고
- **비중은 주 사용자에 따라 정한다.** 일반인이면 C, 실무자면 A를 늘린다. 현재 잠정안은 A 6 : C 3 : B 1이다.

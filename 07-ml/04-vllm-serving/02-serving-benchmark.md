# 서빙 성능 측정 (Serving Benchmark)

LLM 서빙의 지연과 처리량 지표, 동시 요청 수에 따른 변화, 측정 방법과 API 대비 비용 계산을 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 서빙 원리는 [01-vllm-basics](./01-vllm-basics.md) 참고

## 1. 지표

| 지표 | 뜻 | 주로 영향 주는 것 |
| --- | --- | --- |
| TTFT (time to first token) | 요청부터 첫 토큰까지 | 입력 길이(prefill), 대기열 |
| TPOT (time per output token) | 출력 토큰 하나당 시간 | 동시 요청 수, 모델 크기 |
| 전체 지연 | TTFT + (출력 토큰 수 − 1) × TPOT | 출력 길이 |
| 요청 처리량 | 초당 끝낸 요청 수 | 동시 처리 수 |
| 출력 처리량 | 초당 생성한 토큰 수 (전체 요청 합) | 동시 처리 수 |

- 스트리밍이면 사용자 체감은 TTFT와 TPOT(읽는 속도보다 빠른가)다.

## 2. 지연과 처리량의 맞교환

| 동시 요청 수 | TPOT | 처리량 | 비고 |
| --- | --- | --- | --- |
| 적음 | 짧음 | 낮음 | GPU가 놀고 있음 |
| 늘림 | 조금씩 늘어남 | 크게 늘어남 | 효율 구간 |
| 너무 많음 | 크게 늘어남, TTFT 급증 | 더 늘지 않음 | KV 캐시 부족 → 대기, 밀어냄 |

- 목표 지연(예: TTFT p95 < 2초, TPOT < 50 ms)을 정하고, 그 안에서 처리량이 가장 큰 동시 요청 수를 찾는다.

## 3. 손계산 예시

가정: 동시 요청 16, 출력 300토큰, TTFT 0.4초, TPOT 25 ms

```text
요청 1건 지연 = 0.4 + 299 × 0.025 = 7.875 초
요청 처리량  = 16 / 7.875 ≈ 2.03 req/s
출력 처리량  = 16 × 300 / 7.875 ≈ 610 tok/s
시간당 출력  = 610 × 3,600 ≈ 2.19M 토큰
```

### API와 비용 비교

```text
GPU 시간당 비용 = C
자체 서빙의 출력 100만 토큰당 비용 = C / 2.19
```

- 이 값은 **계속 꽉 찬 부하**를 가정한다. 실제 이용률이 30%면 비용은 1 / 0.3 ≈ 3.3배가 된다.
- API 비용은 입력 토큰도 낸다. RAG는 입력이 출력보다 훨씬 길어서 입력 비용까지 포함해 비교한다([04-advanced-rag/06-long-context-vs-rag/02-cost-latency](../../04-advanced-rag/06-long-context-vs-rag/02-cost-latency.md)).
- 운영 인력, 장애 대응, 모델 품질 차이도 비교에 넣는다. 같은 비용이면 품질이 높은 쪽을 고른다.

## 4. 측정 방법

| 항목 | 방법 |
| --- | --- |
| 입력 | 실제 RAG 입력 길이 분포 (트레이스에서 추출, [06-llmops/01-tracing](../../06-llmops/01-tracing/README.md)) |
| 출력 길이 | 실제 답변 길이 분포, 또는 고정 길이로 맞춰 비교 |
| 부하 | 동시 요청 수를 1, 4, 8, 16, 32...로 늘려 곡선 작성 |
| 준비 | 첫 요청(워밍업)은 제외 |
| 기록 | p50, p95, 오류·시간 초과 수 |

- 짧은 입력만으로 측정하면 TTFT와 동시 처리 수가 실제보다 좋게 나온다.
- 접두어 캐시 효과를 보려면 실제처럼 같은 시스템 프롬프트를 쓰는 요청으로 측정한다.

## 5. 확인할 점

- 속도 설정(양자화, 최대 길이, KV 캐시 양자화)을 바꾸면 품질도 확인한다. 지연만 보고 채택하지 않는다.
- 측정 결과에는 vLLM 버전, GPU, 모델 리비전, 부하 조건을 함께 기록한다. 하나만 달라도 값이 크게 바뀐다.

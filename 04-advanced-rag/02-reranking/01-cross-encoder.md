# cross-encoder 리랭커 (Cross-encoder Reranker)

1차 검색이 가져온 후보를 더 정확한 모델로 다시 정렬하는 리랭커의 원리와 종류, 비용을 정리한다. 기본 RAG 실패 유형 중 F3(정답이 top-20 안에는 있는데 top-5 밖)을 고친다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 1차 후보 수 정하기는 [02-candidate-depth](./02-candidate-depth.md) 참고

## 1. bi-encoder와 cross-encoder

```text
bi-encoder (1차 검색)
  질문 ──▶ [인코더] ──▶ 벡터 q
  문서 ──▶ [인코더] ──▶ 벡터 d      (미리 계산)      점수 = q · d

cross-encoder (리랭커)
  [질문 + 문서] ──▶ [인코더] ──▶ 관련성 점수        (질문마다 문서마다 새로 계산)
```

| 항목 | bi-encoder | cross-encoder |
| --- | --- | --- |
| 질문과 문서를 보는 방식 | 따로 | **함께** (단어끼리 서로 참조) |
| 정확도 | 중간 | 높음 |
| 문서 미리 계산 | 가능 | 불가능 |
| 속도 | 수백만 문서에서도 빠름 | 후보 수에 비례해 느림 |
| 쓰는 곳 | 1차 검색 (수백만 → 수십) | 2차 정렬 (수십 → 5) |

- 그래서 **2단계 검색**을 쓴다. 1차 검색기가 넓게 가져오고, 리랭커가 그중 위쪽을 정한다.

## 2. 리랭커 종류

| 종류 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| cross-encoder 모델 | 질문·문서 쌍마다 점수 | 빠르고 로컬 실행 가능 | 한국어·도메인 성능 확인 필요 |
| LLM 리랭커 (pointwise) | LLM이 쌍마다 관련성 점수 | 지시문으로 기준을 줄 수 있음 | 비용·지연 큼 |
| LLM 리랭커 (listwise) | LLM에 후보 목록을 주고 순서를 정하게 함 | 문서끼리 비교 가능 | 긴 입력, 앞쪽 후보 쏠림 |
| 멀티 벡터 (ColBERT) | 질문·문서 토큰 벡터로 MaxSim 점수 | 문서 토큰 벡터를 미리 저장해 cross-encoder보다 빠름 | 저장량이 수십 배, 정확도는 보통 cross-encoder보다 조금 낮음 ([02-dense-retrieval/02-multi-vector](../../02-retrieval-basics/02-dense-retrieval/02-multi-vector.md) 5장, 7장) |

- 기본은 다국어 cross-encoder 모델(예: `bge-reranker-v2-m3` 계열)로 시작하고, LLM 리랭커는 비용을 감당할 수 있을 때 비교한다.
- LLM 리랭커는 사실상 LLM judge의 청크 관련성 판정과 같은 일을 한다. 판정 기준 문장을 골든셋 기준과 맞추면 결과를 해석하기 쉽다([판정 기준](../../03-evals/03-golden-set/README.md)).

### 2.1 모델 예시

2026년 Hugging Face 기준 한국어에 쓸 수 있는 리랭커다. 라이선스는 모델 카드 기준이며, 도입 전에 다시 확인한다.

| 모델 | 종류 | 라이선스 | 메모 |
| --- | --- | --- | --- |
| `BAAI/bge-reranker-v2-m3` | 다국어 cross-encoder | Apache 2.0 | 기준선으로 많이 쓴다 |
| `dragonkue/bge-reranker-v2-m3-ko` | 위 모델을 한국어로 추가 학습 | Apache 2.0 | 한국어 특화 |
| `Dongjin-kr/ko-reranker` | bge-reranker-large를 한국어로 추가 학습 | MIT | |
| `sigridjineth/ko-reranker-v1.1` | gte-multilingual-reranker-base 기반 한국어 | Apache 2.0 | 모델 카드에 개발 중이라고 적혀 있음 |
| `jinaai/jina-reranker-v2-base-multilingual` | 다국어 cross-encoder | **CC-BY-NC-4.0 (비상업)** | 상용 서비스에는 유료 API를 써야 함 |
| `Qwen/Qwen3-Reranker` (0.6B / 4B / 8B) | LLM 기반 리랭커 | Apache 2.0로 알려짐, 모델 카드 확인 | 정확도가 높은 편이지만 GPU 필요, 지연이 큼 |
| Cohere Rerank, Voyage rerank 등 | 상용 API | 유료 | 데이터 외부 전송 가능 여부 먼저 확인 |

- 후보 2~3개를 같은 1차 결과(캐시)로 비교한다. 한국어 추가 학습 모델이 원래 다국어 모델보다 항상 나은 것은 아니다.
- 도메인에서 약하면 질문-문서 쌍으로 추가 학습할 수 있다. 데이터와 손실은 [07-ml/02-embedding-finetuning/02-loss-and-evaluation](../../07-ml/02-embedding-finetuning/02-loss-and-evaluation.md) 2장 "리랭커 학습" 참고

### 2.2 LLM listwise 리랭커의 동작

후보가 많으면 한 번에 넣지 못해 창을 밀어 가며 정렬한다(RankGPT 방식).

```text
후보 50개, 창 20개, 이동 10개 (뒤에서 앞으로)
1회: 31~50위를 정렬 → 상위 10개가 21~30위 쪽으로 올라감
2회: 21~40위를 정렬
3회: 11~30위를 정렬
4회: 1~20위를 정렬 → 최종 상위 확정
```

- 뒤쪽 정답도 창이 이동하면서 앞으로 올라올 수 있다. 창 크기와 이동 폭이 정확도와 호출 횟수를 정한다.
- **위치 편향:** LLM은 목록 앞쪽 후보를 더 좋게 보는 경향이 있다. 후보 순서를 섞어 두세 번 돌려 순위를 합치면 줄어든다. 대신 비용이 그만큼 늘어난다.
- 출력 형식(`[3] > [1] > [7] …`)이 깨지거나 일부 후보가 빠지는 경우를 처리한다. 빠진 후보는 원래 순위대로 뒤에 붙인다.

## 3. 비용과 지연

```text
리랭크 지연 ≈ 후보 수 N × 쌍당 처리 시간 (배치로 줄일 수 있음)
```

예시 가정: 쌍당 4ms

| 후보 수 N | 리랭크 지연 |
| --- | --- |
| 20 | 80ms |
| 50 | 200ms |
| 100 | 400ms |

- 실제 값은 모델 크기, 문서 길이, 하드웨어, 배치 크기에 따라 크게 다르다. 직접 재서 확인한다.
- 지연은 회귀 테스트의 품질 외 기준(p95 지연)에 걸린다([05-regression-ci](../../03-evals/05-regression-ci/01-gate-design.md) 6장).

### 3.1 LLM 리랭커 비용

```text
pointwise: 후보 50개 × (질문 30 + 문서 300 + 지시문 100) ≈ 21,500 입력 토큰, LLM 호출 50회
listwise:  창 20개 × 300토큰 + 지시문 ≈ 6,200 입력 토큰 × 4회 ≈ 25,000 입력 토큰, 호출 4회(순서대로)
```

- 질의당 입력 토큰이 수만 개라, 답변 생성(약 4,000토큰)보다 리랭킹이 더 비쌀 수 있다. 입력 100만 토큰당 1달러로 가정하면 질의당 약 0.02~0.03달러다.
- listwise는 호출이 순서대로 이어져 지연이 호출 횟수만큼 쌓인다. pointwise는 병렬로 돌릴 수 있다.
- 그래서 LLM 리랭커는 비교용 상한으로 쓰거나, 후보를 cross-encoder로 먼저 20개로 줄인 뒤 마지막 단계에만 쓴다.

### 3.2 CPU 서버와 속도 줄이기

| 방법 | 효과 | 주의 |
| --- | --- | --- |
| 작은 리랭커 (base급) | 쌍당 시간이 크게 줄어듦 | 정확도 하락을 dev 세트로 확인 |
| ONNX 변환, int8 양자화 | CPU에서 수 배 빨라지는 경우가 많음 | 변환 전후 점수가 거의 같은지 확인 |
| 입력 길이 줄이기 | 쌍당 시간은 입력 길이에 비례 | 예외 문장이 잘리지 않게 (4장) |
| 후보 수 N 줄이기 | 지연이 N에 비례 | 상한(1차 Recall@N)이 함께 떨어짐 ([02-candidate-depth](./02-candidate-depth.md)) |
| 쌍 점수 캐시 | 같은 (질문, 문서) 쌍은 다시 계산 안 함 | 문서·모델 버전이 바뀌면 캐시 무효화 |

- CPU에서는 쌍당 수십 ms까지 늘어날 수 있다. N = 20이면 수백 ms~1초 안팎이다. 직접 재서 p95 목표와 비교한다.

## 4. 입력 구성

| 항목 | 주의 |
| --- | --- |
| 최대 길이 | 문서가 길면 잘린다(많은 cross-encoder가 512토큰). 뒷부분의 예외 문장이 잘리지 않는지 확인. 긴 문서는 아래 방식으로 처리 |
| 문서 앞 정보 | 문서 제목·섹션 제목을 본문 앞에 붙이면 맥락이 생긴다 |
| 점수 의미 | 리랭커 점수는 순위용이다. "0.7 이상이면 관련" 같은 절대 기준으로 바로 쓰지 않는다 |

긴 문서 처리

| 방식 | 계산 | 맞는 경우 |
| --- | --- | --- |
| FirstP | 문서 앞부분(최대 길이)만 넣음 | 앞부분에 핵심이 있는 문서. 가장 쌈 |
| MaxP | 문서를 겹치게 여러 구간으로 나눠 각각 점수, **가장 높은 점수**를 문서 점수로 | 정답 문장이 어디 있을지 모르는 긴 섹션 |
| 청크 단위 리랭크 | 1차 검색 단위를 더 작게 하고, 리랭크도 청크 단위로 | 부모-자식 청킹을 쓰는 경우 ([04-chunking](../04-chunking/README.md)) |

- MaxP는 구간 수만큼 쌍이 늘어 지연도 늘어난다. 구간 수를 결과와 함께 기록한다.

점수 임계값

- 기본은 점수와 무관하게 top-5를 넘긴다. 리랭커 점수는 순위용이고, 모델마다 분포가 다르다.
- 답 없음 판정이나 낮은 점수 문서 버리기처럼 임계값이 필요하면, 리랭커 점수는 임베딩 유사도보다 관련/무관을 잘 가르는 경우가 많아 쓸 만하다([02-dense-retrieval/01-embedding-basics](../../02-retrieval-basics/02-dense-retrieval/01-embedding-basics.md) 2장 "점수의 절대값은 믿기 어렵다"). 다만 그대로 쓰지 말고 골든셋으로 보정한다.
  - 많은 cross-encoder는 점수를 시그모이드로 0~1로 바꿀 수 있다. 이 값이 확률처럼 보여도 실제 정답 비율과 맞는지 dev 세트로 확인한다.
  - 답 있는 질문과 답 없는 질문의 top-1 점수 분포를 비교해 임계값을 고르고, 놓치는 정답과 걸러지는 오답의 비율을 기록한다. 모델을 바꾸면 다시 정한다.

## 5. 확인할 점

- 리랭커는 1차 후보에 없는 문서를 살릴 수 없다. 리랭커 효과를 볼 때는 1차 Recall@N을 함께 기록한다.
- 리랭커가 바뀌어도 1차 검색 결과는 같아야 한다. 1차 검색 결과를 캐시해 두면 리랭커 비교가 빠르다.
- 리랭커 모델 이름·버전, 최대 길이, 긴 문서 처리 방식(FirstP / MaxP), 점수 변환(시그모이드 여부)을 결과와 함께 기록한다.

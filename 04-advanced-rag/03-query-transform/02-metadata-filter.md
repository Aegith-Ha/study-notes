# 메타데이터 필터 추출 (Metadata Filter)

질문 속 조건("2024년 개정 후", "환불 정책에서", "매뉴얼 기준")을 LLM으로 뽑아 검색 조건으로 거는 방법을 정리한다. 기본 RAG 실패 유형 중 F5(조건 누락으로 구버전·다른 문서를 가져옴)를 고친다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 벡터 DB의 필터 동작은 [02-vector-db](../../02-retrieval-basics/03-vector-index/02-vector-db.md) 3장 참고

## 1. 구조

```text
질문 ──▶ [LLM: 조건 추출] ──▶ { "doc_title": "환불 정책", "doc_type": null, "effective_after": "2024-01-01" }
                                      │
질문 ──▶ 검색 (조건을 필터로 적용) ◀────┘
```

| 필드 | 예 | 문서 쪽 메타데이터 |
| --- | --- | --- |
| `doc_title` | 환불 정책 | 문서 제목 |
| `doc_type` | 정책 / 지침 / 매뉴얼 | 문서 종류 |
| `effective_after` | 2024-01-01 | 시행일 |
| `section` | 3.2 | 섹션 번호 |

- 질문에 조건이 없으면 모든 필드를 비워 둔다(`null`). **조건이 없는데 만들어 내는 것**이 가장 흔한 실패다.
- 추출 결과는 정해진 형식(JSON)으로 받는다. 형식이 깨지면 필터 없이 검색한다.
- 값이 정해진 필드는 **허용값 목록(enum)을 스키마에 넣는다.** 예: `doc_type`은 `["정책", "지침", "매뉴얼", null]`만 허용하고, `doc_title`은 실제 문서 제목 목록에서 고르게 한다. 구조화 출력(JSON 스키마)을 지원하는 모델이면 목록 밖 값이 아예 나오지 않는다.
- 필드가 적고 표현이 정해져 있으면 정규식·사전으로 먼저 뽑고, 남은 것만 LLM에 맡긴다. 싸고 결정적이다.

### 1.1 날짜 표현 바꾸기

| 질문 표현 | 오늘이 2026-11-27일 때 | 필드 |
| --- | --- | --- |
| "올해 개정된" | 2026-01-01 이후 | `effective_after` |
| "작년" | 2025-01-01 ~ 2025-12-31 | `effective_after`, `effective_before` |
| "최근 3개월" | 2026-08-27 이후 | `effective_after` |
| "최근 개정" | 정의가 없음 → 필터 대신 최신순 가산점 | - |

- 모호한 표현("최근")은 기준을 정해 두거나 필터로 쓰지 않는다.
- 프롬프트에 오늘 날짜를 넣는다. 회귀 테스트에서는 날짜를 고정해야 결과가 같다(6장).

### 1.2 기준 시점 질의

"2023년 당시 기준으로 환불 기한이 얼마였나요?"처럼 **그 시점에 유효했던 문서**를 찾는 질문이다. "그 날짜 이후에 개정된 문서"와 다르다.

```text
문서마다 유효 기간을 저장: valid_from, valid_to (현재 유효하면 valid_to = 없음)
기준 시점 t의 필터: valid_from ≤ t  그리고  (valid_to가 없거나 t < valid_to)
```

- 질문에 시점이 없으면 t = 오늘(현재 유효한 문서만)로 둔다. 구버전 문서 반환(F5)을 막는 기본 필터가 된다.
- 문서를 개정할 때 기존 버전을 지우지 않고 `valid_to`만 채워 두어야 과거 시점 질문에 답할 수 있다(문서마다 고정 ID와 버전을 따로 두는 규칙과 맞춘다. [03-golden-set/04-update-loop](../../03-evals/03-golden-set/04-update-loop.md) 6장).
- 프로젝트 적용 예는 [99-projects/01-lawlens](../../99-projects/01-lawlens.md) "프로젝트 선택"(기준 시점 as_of 필터) 참고

### 1.3 권한 필터는 질문에서 뽑지 않는다

- 사용자가 볼 수 있는 문서 범위(부서, 등급)는 질문 내용과 상관없이 **항상 강제로** 건다. 로그인 정보에서 가져오고, LLM 추출 결과로 바꿀 수 없게 한다.
- 질문에서 뽑은 필터와 권한 필터는 AND로 묶는다. 추출 필터를 풀 때(fallback)도 권한 필터는 풀지 않는다.
- 자세한 내용은 [06-llmops/03-security/02-access-control-pii](../../06-llmops/03-security/02-access-control-pii.md) 1장 참고

## 2. 평가: 정답이 명확한 단계

조건 추출은 정답이 분명해서 judge 없이 채점할 수 있다.

| 지표 | 계산 |
| --- | --- |
| 필드별 정확 일치 (EM) | 필드마다 추출값 = 정답값 비율 |
| 과잉 추출률 | 정답이 `null`인데 값을 만든 비율 |
| 누락률 | 정답에 값이 있는데 `null`로 둔 비율 |
| 질문 단위 완전 일치 | 모든 필드가 맞은 질문 비율 |

- 골든셋에 조건이 들어간 질문이 많지 않으면, 조건 추출 전용 평가 질문(예: 50건)을 따로 만든다.
- 문서 제목은 정식 명칭으로 정규화한 뒤 비교한다(약칭 "환불규정" → "환불 정책").

## 3. 실패 처리

| 상황 | 문제 | 대응 |
| --- | --- | --- |
| 과잉 추출 | 없는 조건으로 정답 문서가 걸러짐 | 확신도가 낮으면 필터 대신 가산점(부스트)으로 |
| 필터 후 결과 0건 | 조건이 너무 좁거나 잘못 뽑힘 | 필터를 풀고 다시 검색 (fallback) |
| 문서 제목 오추출 | 비슷한 다른 문서로 필터 | 문서 제목 사전으로 검증, 사전에 없으면 필터 생략 |

- 필터는 틀리면 정답을 **완전히** 지운다. 그래서 재작성보다 보수적으로 쓴다.

## 4. 검색 지표와 함께 보기

| 비교 | 보는 것 |
| --- | --- |
| 필터 전후 Recall@5 | 최종 효과 |
| 필터 전후 구버전 문서 반환율 | F5가 실제로 줄었나 ([05-regression-ci](../../03-evals/05-regression-ci/01-gate-design.md) L1 규칙 검사) |
| 추출 오류 질의의 Recall@5 | 추출이 틀렸을 때 얼마나 손해인가 |

- Recall이 떨어졌을 때 "검색기 문제인가, 필터를 잘못 뽑았나"를 이 표로 바로 구분한다.

## 5. 정확 조회 라우팅

질문에 문서 번호, 섹션 번호, 제품 코드처럼 **문서를 바로 가리키는 식별자**가 있으면 검색할 필요가 없다. 식별자로 DB를 직접 조회하는 쪽으로 보낸다.

```text
질문 ──▶ [식별자 탐지: 정규식·사전] ──┬─ 있음 ──▶ DB 직접 조회 ──┐
                                      │                          ├─▶ 조회 결과를 맨 앞에, 검색 결과를 뒤에
                                      └──────▶ 일반 검색 ────────┘
                                         (없음이면 일반 검색만)
```

| | 메타데이터 필터 (1~4장) | 정확 조회 라우팅 |
| --- | --- | --- |
| 하는 일 | 검색 범위를 좁힘 | 검색을 건너뛰고 해당 문서를 바로 가져옴 |
| 탐지 방법 | LLM으로 조건 추출 | 정규식, 식별자 사전 (LLM 없이도 가능) |
| 틀렸을 때 | 정답이 걸러짐 | 엉뚱한 문서가 맨 앞에 옴 |

- **조회 결과만 쓰지 않고 일반 검색 결과를 함께 붙인다.** "3.2항 말고 다른 예외도 있나요?"처럼 식별자가 있어도 다른 문서가 필요한 질문이 있다.
- 오탐에 주의한다. "3일 이내"의 "3"을 섹션 번호로 잡으면 엉뚱한 문서가 1위가 된다. 식별자 형식을 좁게 정하고, 조회 결과가 없으면 일반 검색만 쓴다.
- 평가: 식별자 탐지의 정밀도·재현율, 식별자 질문에서의 MRR(기대값 1)을 따로 잰다. 일반 질문에서 오탐으로 Recall이 떨어지지 않았는지도 본다.
- 집계형 질문("2024년에 개정된 정책은 몇 개인가?")은 문서를 찾는 문제가 아니라 DB를 세는 문제다. text-to-SQL 같은 도구 호출로 푼다([05-agents/02-tool-calling-mcp](../../05-agents/02-tool-calling-mcp/README.md)).

## 6. 질의 분류와 라우팅

정확 조회(5장)는 라우팅의 한 종류다. 질문을 먼저 분류해, 질문마다 다른 처리로 보낼 수 있다.

```text
질문 ──▶ [분류: 규칙 → 작은 모델/LLM] ──┬─ 식별자 질문        ──▶ 정확 조회 + 일반 검색 (5장)
                                        ├─ 검색이 필요 없음    ──▶ 바로 답변 (인사, 사용법 안내)
                                        ├─ 범위 밖             ──▶ 정해진 문구로 거절
                                        ├─ 집계형              ──▶ DB 조회·도구 호출
                                        └─ 일반 질문           ──▶ 검색 (유형별 설정)
```

| 분류 | 예 | 처리 | 틀렸을 때 |
| --- | --- | --- | --- |
| 검색이 필요 없음 | "안녕하세요", "이 챗봇 어떻게 써요?" | 검색 없이 정해진 답변 | 문서 근거가 필요한 질문을 검색 없이 답함 → 근거 없는 답변 |
| 범위 밖 | 서비스와 상관없는 질문 | 거절 문구 | 범위 안 질문을 거절 → 과잉 거절 |
| 집계형 | "올해 개정된 정책은 몇 개?" | DB 조회 (text-to-SQL 등) | 일반 검색으로 가면 일부 문서만 보고 틀린 개수 |
| 일반 질문의 유형 | 일상어 / 전문 용어 / 다중 근거 | 하이브리드 가중치, 변환 여부, 리랭커 사용 여부를 바꿈 | 유형별 설정이 오히려 손해 |

- **틀렸을 때 비용이 큰 쪽을 보수적으로** 둔다. "검색이 필요 없음"으로 잘못 보내면 근거 없는 답이 나가므로, 애매하면 검색하는 쪽(일반 질문)으로 보낸다.
- 범위 밖 판정은 답 없음 질의와 관련이 있다. 골든셋의 답 없음 질의([03-golden-set/01-query-sources](../../03-evals/03-golden-set/01-query-sources.md) "답 없음 질의 만들기")로 과잉 거절률과 거절 정확도를 함께 잰다.
- 유형별 검색 설정은 하이브리드의 질의별 가중치와 같은 문제다([01-hybrid-search/02-tuning-and-analysis](../01-hybrid-search/02-tuning-and-analysis.md) 2.1).

평가
| 지표 | 계산 |
| --- | --- |
| 분류 정확도 | 분류 정답을 붙인 질문 세트에서 분류별 정밀도·재현율 |
| 분류 오류의 손해 | 잘못 분류된 질문의 최종 Recall@5·Answer Correctness를 따로 집계 |
| 라우팅 전후 | 전체 지표, 과잉 거절률, 질의당 비용·지연 |

- 분류 정답 세트는 골든셋 질문에 분류 태그를 붙이고, 검색이 필요 없는 질문과 범위 밖 질문을 조금 더해 만든다.
- 분류에 LLM을 쓰면 호출이 하나 더 늘어난다. 질의 변환과 같은 호출에서 함께 하게 하면(분류 + 재작성을 한 번에) 지연이 덜 늘어난다.

## 7. 확인할 점

- 문서 쪽 메타데이터(시행일, 문서 종류)가 정확해야 필터가 의미 있다. 색인할 때 메타데이터 누락 비율을 먼저 확인한다.
- 추출 프롬프트에 오늘 날짜를 넣어야 "최근 개정", "올해" 같은 표현을 날짜로 바꿀 수 있다. 회귀 테스트에서는 날짜를 고정한다.
- 라우팅 규칙(정규식, 사전, 분류 프롬프트)과 버전을 결과와 함께 기록한다. 라우팅이 바뀌면 같은 질문이 다른 경로로 간다.

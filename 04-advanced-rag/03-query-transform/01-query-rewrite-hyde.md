# 질의 재작성과 HyDE (Query Rewrite, HyDE)

사용자 질문을 그대로 검색하지 않고, LLM이나 규칙으로 검색에 유리한 형태로 바꾼 뒤 검색하는 방법을 정리한다. 기본 RAG 실패 유형 중 F4(모호하거나 짧은 질문), F1(표현 불일치) 일부, F13(대화 맥락 누락)을 고친다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 질문에서 검색 조건을 뽑는 방법은 [02-metadata-filter](./02-metadata-filter.md) 참고

## 1. 방법

| 방법 | 하는 일 | 예 (원래 질문: "결제했는데 돈이 안 돌아와요") |
| --- | --- | --- |
| 재작성 (rewrite) | 일상어를 문서의 용어로 바꿔 하나의 검색어로 | "결제 취소 후 환불 처리 기한" |
| 다중 질의 (multi-query) | 여러 표현으로 바꿔 각각 검색 후 합침 | "환불 지연", "결제 취소 환불 기간", "카드 환불 처리 절차" |
| HyDE | 그럴듯한 **답변 문서**를 먼저 쓰게 하고 그 글로 검색 | "결제 취소 시 환불은 영업일 기준 3~5일 이내에 처리되며 …" (가상의 정책 문서 문체 글) |
| 분해 (decomposition) | 여러 조건이 섞인 질문을 하위 질문으로 쪼개 각각 검색 | "환불 처리 기한" + "기한 초과 시 문의 절차" |
| step-back | 구체적인 질문을 한 단계 일반적인 질문으로 바꿔 함께 검색 | "환불 가능 기간 규정" (원래 질문 "3월에 산 제품 환불 되나요?") |
| 키워드 확장 (BM25용) | LLM에게 검색 키워드·동의어만 뽑게 해 BM25 질의에 덧붙임 | `환불 결제취소 카드취소 환불기한` |
| 대화 맥락 재작성 | 앞 대화에 기대는 질문을 혼자서도 이해되는 질문으로 (1.1) | "그럼 예외는?" → "구매 후 7일 환불 기한이 지난 경우의 예외" |

- 다중 질의와 분해의 결과는 [하이브리드의 합치기 방법](../01-hybrid-search/01-fusion-methods.md)(RRF)으로 합친다.
- step-back은 질문이 너무 구체적이라 배경 규정 섹션을 못 찾을 때 효과가 있다. 원래 질문 결과와 함께 합친다.
- 키워드 확장은 BM25 노트의 질의 확장(RM3, [01-sparse-retrieval/02-bm25](../../02-retrieval-basics/01-sparse-retrieval/02-bm25.md) 5장)과 같은 목적이다. RM3는 1차 검색 결과에서 단어를 뽑고, 이 방법은 LLM이 뽑는다. LLM이 문서에 없는 용어를 만들 수 있으므로, 확장 단어는 색인 어휘(역색인에 있는 단어)에 있는 것만 남긴다.

### 1.1 대화 맥락을 반영한 재작성

naive RAG는 마지막 질문만 검색한다. 앞 대화에 기대는 후속 질문은 그대로 검색하면 실패한다([02-failure-modes](../../02-retrieval-basics/04-naive-rag/02-failure-modes.md) F13).

```text
턴 1  사용자: 환불 기한이 어떻게 돼요?
      답변:   구매 후 7일 이내입니다 [환불 정책 3.1].
턴 2  사용자: 그럼 예외는?

그대로 검색:  "그럼 예외는?"  → 어떤 문서의 예외인지 알 수 없음
재작성:       "구매 후 7일 환불 기한이 지난 경우의 환불 예외"  → 환불 정책 3.2를 찾음
```

| 정할 것 | 기본 선택 | 이유 |
| --- | --- | --- |
| 넣을 대화 범위 | 최근 2~3턴의 질문과 답변 요약 | 너무 길면 지연·비용이 늘고, 오래된 주제가 섞임 |
| 주제가 바뀐 경우 | 질문이 이미 혼자서 이해되면 그대로 둠 | 앞 주제를 억지로 붙이면 의도 이탈 |
| 답변의 인용 | 앞 답변이 인용한 문서 제목을 함께 넣음 | "그 규정", "아까 말한 것"을 구체적인 문서로 바꿀 수 있음 |
| 원래 질문 | 재작성 결과만 검색 (대화형에서는 원래 질문이 단독으로 의미가 없음) | 단, 재작성이 원래 질문과 같으면 한 번만 검색 |

- 평가: 골든셋 질문에서 후속 질문 세트를 만든다(앞 턴 + 짧게 줄인 후속 질문, 정답은 원래 질문의 qrels). 재작성 후 Recall@5를 단독 질문의 Recall@5와 비교하고, 재작성 결과가 혼자서 이해되는지 표본을 확인한다.
- 재작성 프롬프트에 "질문이 이미 완전하면 바꾸지 말 것"을 넣는다. 바꿀 필요가 없는 질문을 바꾼 비율도 센다.

### 1.2 분해의 두 종류

| 종류 | 예 | 동작 | 맡는 곳 |
| --- | --- | --- | --- |
| 병렬 분해 | "환불 기한과 배송비 부담 주체는?" → "환불 기한", "배송비 부담 주체" | 하위 질문을 각각 검색해 합침. 하위 질문끼리 독립 | 이 노트 (고정 파이프라인) |
| 순차 분해 | "A 제품 담당 부서의 연락처는?" → 담당 부서를 찾은 뒤 그 부서의 연락처 | 앞 질문의 답으로 다음 질문을 만듦 | 반복 검색이 필요해 에이전트 쪽 ([05-agents/01-agentic-rag](../../05-agents/01-agentic-rag/README.md)) |

- 병렬 분해는 다중 근거 질문(F11)을 고친다. 합친 결과에서 하위 질문마다 최소 1개씩 남도록 하위 질문별로 상위 몇 개를 보장하면, 한 하위 질문의 결과가 top-5를 다 채우는 것을 막는다.
- 분해가 필요 없는 단일 질문을 쪼개면 오히려 검색이 흐려진다. 분해 여부도 LLM이 판단하게 하고, 쪼갠 비율을 기록한다.

### 1.3 LLM 없는 전처리

가장 싸고 결정적인 변환이다. LLM 변환보다 먼저 적용한다.

| 처리 | 예 | 방법 |
| --- | --- | --- |
| 표기 정규화 | 전각·반각, 대소문자, 숫자 표기 | sparse 노트의 정규화와 같은 규칙 ([01-inverted-index-tfidf](../../02-retrieval-basics/01-sparse-retrieval/01-inverted-index-tfidf.md) 4장) |
| 약어·별칭 펼치기 | "환불규정" → "환불 정책", "AS" → "사후 서비스" | 문서 제목 사전, 약어 사전 |
| 동의어 | "비번" → "비밀번호" | 동의어 사전 (BM25 쪽) |
| 맞춤법·띄어쓰기 | "환불규정알려주세요" → "환불 규정 알려 주세요" | 한국어 맞춤법·띄어쓰기 교정기 |

- 사전은 질문과 문서 양쪽에 같은 규칙을 쓴다. 질문만 바꾸면 BM25에서 겹침이 깨질 수 있다.
- 교정기는 도메인 용어를 틀린 말로 고치기도 한다. 도메인 용어는 예외 목록에 넣는다.

## 2. HyDE가 동작하는 이유

```text
질문 (짧은 일상어)       ↔  정책 문서 (긴 공식 문체)  : 표현이 멀다
가상 답변 (정책 문체)    ↔  정책 문서 (긴 공식 문체)  : 표현이 가깝다
```

- 질문과 문서의 **문체 차이**를 LLM이 메워 준다. 주로 dense 검색에서 효과가 있다.
- 가상 답변의 **내용이 틀려도** 검색에는 도움이 될 수 있다. 문체와 용어가 비슷하면 가까운 섹션을 찾는다. 다만 가상 답변은 검색에만 쓰고 사용자에게 보여 주지 않는다.

## 3. 위험

| 위험 | 예 | 대응 |
| --- | --- | --- |
| 의도 이탈 (drift) | "결제 사기 신고"를 "결제 취소 절차"로 바꿈 | 원래 질문 검색 결과와 함께 합침 (원래 질문을 버리지 않음) |
| 없는 용어 생성 | 존재하지 않는 문서 제목·제품 코드를 넣음 | BM25에는 재작성 결과를 넣지 않거나, 문서 제목 사전으로 검증 |
| 정보 손실 | 질문의 조건("2024년 이후")을 빠뜨림 | 조건은 메타데이터 필터로 따로 뽑음 |
| 지연·비용 | 검색 전에 LLM 호출 1회 추가 | 짧은 출력, 작은 모델, 캐시 |

- 가장 안전한 기본값은 **원래 질문 + 변환 질의를 각각 검색해서 RRF로 합치는 것**이다. 변환이 틀려도 원래 질문의 결과가 남는다.

### 3.1 변환을 언제 할지 (조건부 적용)

모든 질문을 변환하면 비용과 지연이 늘고, 원래도 잘 찾던 질문(`expert` 말투, 식별자 질문)에서 의도 이탈로 손해를 볼 수 있다. 필요한 질문에만 적용한다.

| 조건 | 예 | 변환 |
| --- | --- | --- |
| 식별자가 있음 | 문서 번호, 제품 코드 | 하지 않음. 정확 조회 라우팅 ([02-metadata-filter](./02-metadata-filter.md) 5장) |
| 질문이 짧거나 모호함 | 3단어 이하, "환불?" | 재작성 또는 다중 질의 |
| 1차 검색 점수가 낮거나 1·2위 차이가 작음 | 확신 없는 결과 | 변환 후 다시 검색 |
| 대화의 후속 질문 | 대명사·생략 ("그럼", "그건") | 대화 맥락 재작성 (1.1) |
| 그 밖 | 충분히 구체적인 질문 | 하지 않음 |

- 조건 자체가 레버다. "항상 변환"과 "조건부 변환"을 dev 세트로 비교하고, 변환한 질문 비율과 그 안의 Recall 변화를 따로 본다.
- 점수 기반 조건(2행째)은 검색을 한 번 더 하므로 지연이 늘어난다. 그 질문에만 생기는 비용이라 전체 평균 지연은 작게 늘어난다.

## 4. 평가

| 확인 | 방법 |
| --- | --- |
| 최종 효과 | 변환 전후 Recall@5, MRR (검색 지표) |
| 질의별 변화 | 변환으로 실패 → 성공, 성공 → 실패가 된 질의 |
| 변환 품질 | 의도 이탈 비율: 변환 질의를 표본으로 사람 또는 judge가 확인 |
| 나눠 보기 | `user` 말투에서 효과가 크고 `expert`에서는 작거나 손해일 수 있음 |
| 비용 | 질의당 추가 LLM 호출, p95 지연 |

- 변환 LLM은 중간 단계라 생성 지표가 아니라 **검색 지표**로 평가한다([03-evals README](../../03-evals/README.md) 시스템 유형별 지표).

### 4.1 손계산: 다중 질의의 비용과 지연

원래 질문 + 변환 질의 3개, 각 top-20을 RRF로 합침. 작은 변환 모델, 토큰 가격은 입력 100만 토큰당 1달러, 출력 5달러로 가정

```text
변환 LLM 호출    입력 150토큰 (지시문 + 질문), 출력 60토큰 (질의 3개)     약 0.5~1초
검색 4회         질의 인코딩 + 검색 각 30 ms, 병렬이면 약 30 ms           순서대로면 약 120 ms
RRF 합치기       후보 최대 80개 → 중복 제거 후 top-20                    1 ms 미만
추가 지연        약 0.5~1초 (대부분 변환 LLM 호출)
추가 비용        150 × 1/1,000,000 + 60 × 5/1,000,000 ≈ 0.0005달러
```

- 답변 생성(질의당 약 0.005달러, 약 6초, [02-retrieval-basics/04-naive-rag/01-pipeline](../../02-retrieval-basics/04-naive-rag/01-pipeline.md) 6장)과 비교하면 비용은 약 10%, 지연은 약 10~15%가 늘어난다.
- 변환 호출은 검색보다 먼저 끝나야 해서 첫 글자가 나오는 시간에 그대로 더해진다. 작은 모델을 쓰고 출력 길이를 짧게 제한한다.
- 검색 결과가 4배가 되면 리랭커를 쓸 때 후보 수도 늘어난다. 합친 뒤 top-20만 리랭커에 넘긴다.

## 5. 확인할 점

- 변환 프롬프트와 모델 버전을 기록한다. 변환 결과가 바뀌면 검색 결과도 바뀐다.
- 같은 질문의 변환 결과를 캐시해 두면 회귀 테스트가 결정적이 된다.

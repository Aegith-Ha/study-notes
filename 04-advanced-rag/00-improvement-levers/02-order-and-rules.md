# 시도 순서와 실험 규칙 (Order and Rules)

지표 개선 레버를 어떤 순서로 시도하고, 효과를 어떻게 비교해야 믿을 수 있는지 정리한다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 레버 목록과 각 레버가 움직이는 지표는 [01-lever-map](./01-lever-map.md) 참고

## 1. 시도 순서

기본 원칙은 **싸고, 재색인이 필요 없고, 되돌리기 쉬운 것부터**다. 다만 실패 유형(F1~F13) 분포가 순서를 바꿀 수 있다.

| 순서 | 레버 | 이유 |
| --- | --- | --- |
| 1 | 실패 유형 분류 ([02-failure-modes](../../02-retrieval-basics/04-naive-rag/02-failure-modes.md)) | 가장 많은 유형에 맞는 레버를 고르기 위해. 레버가 아니라 방향 잡기 |
| 2 | 프롬프트, 컨텍스트 조립 (L10, L11) | 생성 문제(F8~F10)가 많으면 가장 싸고 빠름 |
| 3 | 결과 합치기, 후보 수 (L7, L8) | 색인 그대로, 설정값만 바꿈 |
| 4 | 리랭커 (L9) | 색인 그대로. 지연이 늘어나는 것만 확인 |
| 5 | 필터·라우팅, 질의 변환 (L6) | 색인 그대로. LLM 호출 비용이 생김 |
| 6 | 토큰화, BM25 설정, 임베딩 입력 구성 (L3, L4) | 재색인 필요하지만 모델은 그대로 |
| 7 | 청킹, 파싱 (L1, L2) | 재색인 필요. 골든셋 판정 단위와의 매핑도 확인 |
| 8 | 임베딩 모델 교체 (L4) | 재색인 필요, 문서 전체 재인코딩 |
| 9 | 파인튜닝, 그래프·요약 트리 | 데이터 준비와 색인 비용이 큼. 앞 단계로 부족할 때만 |

- 1차 검색에서 정답을 못 가져오면(Recall@50도 낮음) 리랭커는 효과가 없다. 이때는 3·4번을 건너뛰고 6~8번으로 간다.
- 반대로 Recall@50은 높은데 Recall@5가 낮으면(F3) 리랭커가 가장 효과가 크다.

## 2. 실험 규칙

| 규칙 | 이유 |
| --- | --- |
| **레버는 한 번에 하나씩** 바꾼다 | 두 개를 같이 바꾸면 어느 쪽 효과인지 알 수 없다 |
| 비교는 **dev 세트**에서만 한다 | test 세트로 조정하면 기준선이 부풀려진다 ([03-golden-set/04-update-loop](../../03-evals/03-golden-set/04-update-loop.md) 5장) |
| 청크 크기가 바뀌면 **같은 토큰 예산**으로 비교한다 | 큰 청크는 같은 k에서 내용이 많아 유리하다 |
| 생성 쪽은 **여러 번 실행**해 흔들림부터 잰다 | 차이가 흔들림보다 작으면 결론을 내지 않는다 |
| **유형별로 나눠** 본다 (말투, 답변 유형, 난이도) | 평균은 그대로인데 한 유형만 나빠지는 변경이 있다 |
| **질의별 변화**를 본다 (새로 맞은 질문, 새로 틀린 질문) | 평균에 가려진 회귀를 찾는다 |
| 품질과 함께 **비용·지연**을 기록한다 | Recall 1%p를 위해 지연이 2배가 되면 판단이 달라진다 |
| 설정 전체(모델 버전, 파라미터, 골든셋 버전)를 결과와 함께 남긴다 | 나중에 같은 결과를 재현하기 위해 |

## 3. 실험 도구

레버를 바꿔 가며 비교하는 일을 한 도구가 전부 해 주지는 않는다. 아래 네 단계에 맞는 도구를 골라 조합한다.

```text
1. 레버를 설정값으로 꺼냄       retriever: hybrid, rrf_k: 30, reranker: none   (Hydra 또는 YAML)
2. 조합 실행                    직접 만든 스크립트, AutoRAG, 연속 값은 Optuna
3. 지표 계산                    ranx, ragas, 직접 만든 지표
4. 기록·비교                    MLflow, Langfuse·Phoenix 실험 기능
```

### 3.1 파이프라인 조합을 자동으로 비교하는 도구 (RAG 전용)

| 도구 | 하는 일 | 맞는 레버 | 메모 |
| --- | --- | --- | --- |
| AutoRAG | YAML에 단계별 후보(검색 방식, 리랭커, 프롬프트 등)를 적으면 골든셋으로 조합을 돌려 단계별로 가장 좋은 것을 고름 | 검색기, 결과 합치기, 리랭커, 프롬프트 | 한국 팀이 만들어 한국어 예제가 많다. 단계별로 차례로 고르므로 단계끼리 상호작용은 일부 놓칠 수 있다 |
| DSPy | 프롬프트 지시문과 few-shot 예시를 지표 기준으로 자동 최적화 | 프롬프트(L11) | 검색 설정 비교용은 아니다 |

### 3.2 레버를 설정값으로 빼고 여러 조합을 돌리는 도구 (범용)

| 도구 | 하는 일 | 맞는 레버 |
| --- | --- | --- |
| Hydra | 레버를 설정 파일로 빼고, 명령 한 줄로 여러 값 조합을 돌림 (`retriever=bm25,dense,hybrid top_k=5,10`) | 이름으로 고르는 레버 (검색기, 리랭커 유무, 프롬프트 버전) |
| Optuna | 연속 값 레버를 탐색해 지표가 가장 좋은 값을 찾음 | 값으로 조절하는 레버 (RRF k·가중치, BM25 k1·b, top-k, 후보 수 N) |

### 3.3 실험 결과를 기록하고 비교하는 도구

| 도구 | 하는 일 |
| --- | --- |
| MLflow, Weights & Biases | 실행마다 설정과 지표를 저장하고 표·그래프로 비교 |
| Langfuse, Phoenix, LangSmith | 같은 질문 세트(데이터셋)로 설정별 결과를 질의 단위로 나란히 비교 ([06-llmops/01-tracing](../../06-llmops/01-tracing/README.md)) |
| promptfoo | 프롬프트 × 모델 조합을 표로 돌려 비교, CI에 붙이기 쉬움 |
| `ranx` | 검색 결과 여러 개의 지표 비교표와 유의성 검정 |

- 지표 계산 도구 전체 목록은 [03-evals](../../03-evals/README.md) "평가용 오픈소스 도구" 참고

### 3.4 도구를 쓸 때 주의할 점

- **자동 탐색은 dev 세트에 과적합되기 쉽다.** 조합을 많이 돌릴수록 우연히 dev에서만 좋은 설정이 뽑힌다. 시도한 조합 수를 기록하고, 고른 설정은 test 세트로 한 번만 확인한다. 1등과 2등의 차이가 유의하지 않으면 더 싸고 단순한 쪽을 고른다([02-dense-retrieval/03-model-selection](../../02-retrieval-basics/02-dense-retrieval/03-model-selection.md) 3장 "차이가 우연인지 확인").
- **"레버는 한 번에 하나씩"(2장)과 충돌하지 않게 쓴다.** 격자 탐색은 여러 레버를 동시에 바꾸는 것이다. 탐색은 후보를 좁히는 데 쓰고, 채택은 기준선 대비 레버 하나씩 바꾼 비교로 확인한다.
- **도구가 평가셋 품질을 대신하지 않는다.** pool이 한쪽 검색기에 치우치면 어떤 도구로 돌려도 그 검색기가 이긴다([01-lever-map](./01-lever-map.md) 1장 평가 점검).
- **재색인이 필요한 레버는 자동 탐색이 비싸다.** 청킹, 토큰화, 임베딩 모델은 조합마다 문서 전체를 다시 인코딩한다. 후보를 2~3개로 줄이고, 색인 결과를 캐시해 다시 쓴다.
- **생성 쪽 지표는 흔들린다.** 조합마다 여러 번 실행하지 않으면 탐색 결과가 노이즈로 정해진다. 검색 쪽 레버는 검색 지표만으로 먼저 좁히고, 생성 평가는 남은 후보에만 한다.
- 도구가 내부에서 쓰는 지표 정의(중복 제거, 미판정 처리, k)가 노트의 정의와 같은지 확인한다. 다르면 기준선과 숫자가 맞지 않는다.

## 4. 확인할 점

- 골든셋 점수만 오르고 실제 사용자 질문에서는 그대로일 수 있다(골든셋 과적합). 운영 지표와 함께 본다([06-llmops/04-feedback-loop](../../06-llmops/04-feedback-loop/README.md)).
- 채택한 레버 설정은 프로젝트의 설정 기록(예: [99-projects/01-lawlens](../../99-projects/01-lawlens.md) "프로젝트 선택")에 반영하고, 회귀 테스트 기준선을 다시 잡는다([03-evals/05-regression-ci](../../03-evals/05-regression-ci/README.md)).

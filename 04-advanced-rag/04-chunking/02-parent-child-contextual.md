# 부모-자식 청크와 contextual retrieval (Parent-Child, Contextual Retrieval)

검색은 작은 단위로 정밀하게 하고 LLM에는 큰 단위를 넘기는 부모-자식 청크, 그리고 청크마다 문서 맥락을 덧붙여 검색 품질을 올리는 contextual retrieval을 정리한다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 기본 청킹 방법은 [01-chunking-strategies](./01-chunking-strategies.md) 참고

## 1. 부모-자식 청크

```text
부모: 3. 환불 정책 전체 (3.1, 3.2, 예외 문장 포함)
  ├─ 자식 1: 3.1
  └─ 자식 2: 3.2 + 예외 문장

검색: 자식 단위로 검색 (정밀)
전달: 검색된 자식의 부모를 LLM에 전달 (맥락 보존)
```

| 항목 | 내용 |
| --- | --- |
| 해결하는 문제 | 작은 청크는 잘 찾지만 맥락이 부족, 큰 청크는 맥락은 있지만 잘 못 찾음 |
| 부모 단위 | 구조 있는 문서: 섹션, 구조 없는 문서: 고정 길이(예: 1,500 토큰) |
| 자식 단위 | 구조 있는 문서: 하위 항목, 구조 없는 문서: 문단 또는 고정 길이(예: 300 토큰) |
| 중복 처리 | 같은 부모의 자식이 여러 개 검색되면 부모는 한 번만 전달 |

- top-5를 자식 기준으로 뽑으면 부모 중복 제거 후 5개보다 적어질 수 있다. 부모 기준으로 5개가 될 때까지 자식을 더 가져온다.
- 부모가 크면 컨텍스트 토큰이 늘어난다. 질의당 토큰을 기준선과 함께 비교한다.

### 1.1 sentence-window (가벼운 변형)

```text
색인: 문장 하나씩 (가장 작은 단위)
검색: 문장 단위로 찾음
전달: 찾은 문장의 앞뒤 k문장(예: k = 2)을 붙여 넘김
```

| | 부모-자식 | sentence-window |
| --- | --- | --- |
| 넘기는 범위 | 정해진 부모(섹션 등) | 찾은 문장 주변 k문장 |
| 필요한 것 | 문서 구조 또는 부모 단위 정의 | 문장 순서(위치)만 |
| 맞는 문서 | 구조가 있는 문서 | 구조가 없는 긴 글 |

- 문장 단위 색인은 청크 수가 매우 많아진다. 앞뒤 문장을 찾으려면 청크마다 위치를 저장해야 한다([01-chunking-strategies](./01-chunking-strategies.md) 4장).
- 앞뒤 창이 겹치는 두 문장이 함께 검색되면 하나로 합쳐 넘긴다.

## 2. contextual retrieval

청크만 떼어 놓으면 "이 조항"이 무엇에 관한 것인지 사라진다. 색인 전에 청크마다 짧은 맥락을 붙인다.

```text
원래 청크:   "3.2 단, 사용 이력이 있는 상품은 3.1과 달리 환불하지 않는다."
맥락 추가:   "[환불 정책 3장(환불)의 3.2항. 사용한 상품의 환불 제한에 관한 규정]
             3.2 단, 사용 이력이 있는 상품은 3.1과 달리 환불하지 않는다."
```

| 방식 | 맥락 만드는 법 | 비용 |
| --- | --- | --- |
| 규칙 기반 | 문서 제목 + 섹션 번호 + 섹션 제목을 앞에 붙임 | 거의 없음 |
| LLM 생성 | 문서 전체와 청크를 LLM에 주고 1~2문장 맥락 요약을 생성 | 청크 수만큼 LLM 호출 (색인 때 한 번) |

- 정책·매뉴얼처럼 구조 정보가 풍부한 문서는 **규칙 기반만으로도** 효과가 클 수 있다. LLM 생성은 규칙 기반과 비교해서 차이가 클 때만 쓴다.
- 맥락은 sparse 색인과 dense 임베딩 **양쪽에** 넣는다. BM25에도 문서 제목·섹션 제목 단어가 추가되어 정확 일치가 쉬워진다.
- LLM이 만든 맥락에 틀린 내용이 들어가면 검색을 오도한다. 표본을 확인한다.

### 2.1 LLM 맥락 생성 비용

청크마다 문서 전체를 함께 넣으므로 문서 길이가 비용을 정한다.

```text
문서 1,000개 × 문서당 청크 20개 = 청크 20,000개
청크당 입력 = 문서 5,000 + 청크 300 + 지시문 100 = 5,400토큰
입력 합계 = 20,000 × 5,400 ≈ 1억 800만 토큰,  출력 = 20,000 × 50 = 100만 토큰
가정 가격 (입력 100만당 1달러, 출력 5달러) → 약 108 + 5 = 113달러
```

- 같은 문서를 청크 20번에 걸쳐 반복해서 넣는다. **프롬프트 캐시**로 문서 부분을 재사용하면, 캐시 읽기를 정가의 10%로 가정할 때 입력이 약 2,250만 토큰 상당(약 23달러)으로 줄어든다([06-llmops/02-cost-optimization/01-caching](../../06-llmops/02-cost-optimization/01-caching.md) 2장).
- 캐시를 쓰려면 프롬프트를 "문서 전체(고정) → 청크(바뀜)" 순서로 두고, 같은 문서의 청크를 연달아 처리한다.
- 색인 때 한 번 드는 비용이지만, 청킹 설정이나 문서가 바뀌면 다시 든다. 문서가 바뀐 경우에는 그 문서의 청크만 다시 만든다.
- 문서가 모델 컨텍스트보다 길면 문서 전체 대신 해당 섹션과 문서 요약을 넣는다.

## 3. 다른 방식

| 방식 | 내용 | 장점 | 단점 | 자세히 |
| --- | --- | --- | --- | --- |
| 명제 단위 (proposition) | LLM이 문서를 독립적인 사실 문장("환불은 결제일로부터 7일 이내다")으로 다시 씀 | 청크 하나에 사실 하나라 검색이 정밀 | 문서 전체를 LLM으로 다시 써야 해 비용이 큼. 다시 쓰다가 조건이 빠질 수 있음 | - |
| late chunking | 문서를 통째로 인코딩한 뒤 토큰 벡터를 청크 범위별로 평균 | 청크마다 앞뒤 문맥이 반영됨, 저장량은 그대로 | 문서가 모델 최대 길이 안에 들어가야 함 | [02-dense-retrieval/02-multi-vector](../../02-retrieval-basics/02-dense-retrieval/02-multi-vector.md) 4장 |
| 요약 트리 (RAPTOR) | 청크를 묶어 요약을 여러 층으로 쌓고 위층에서도 검색 | 문서 전체를 아우르는 질문에 강함 | 요약 생성 비용, 요약의 환각 | [07-graph-hierarchical/02-hierarchical-summary](../07-graph-hierarchical/02-hierarchical-summary.md) |

- contextual retrieval, late chunking, 부모-자식은 모두 "청크가 앞뒤 맥락을 잃는 문제"를 다른 방식으로 푼다. 하나를 고르고 기준선과 비교한 뒤 다음을 시도한다. 여러 개를 한꺼번에 넣으면 무엇이 효과인지 알 수 없다.
- 명제 단위 청킹은 원문 대신 다시 쓴 문장을 색인하므로, 인용할 때는 원래 청크로 돌아갈 수 있도록 원문 위치를 함께 저장한다.

## 4. 평가

| 비교 | 보는 지표 |
| --- | --- |
| 섹션 단위 vs 하위 항목 단위 vs 부모-자식 | Recall@5 (문서 단위 매핑), 근거 구간 포함률 (C 방식), 질의당 토큰 |
| 맥락 없음 vs 규칙 맥락 vs LLM 맥락 | Recall@5, MRR, 색인 비용 |
| 생성 쪽 | Claim Recall, Context Sufficiency, Answer Correctness (F6 해소 여부) |

- 청킹은 검색과 생성 양쪽에 영향을 준다. 검색 지표만 오르고 생성 지표가 그대로면, 맥락이 LLM에 충분히 전달되지 않은 것이다.

## 5. 확인할 점

- 부모-자식 구조에서 평가할 때 "검색 결과"를 자식으로 볼지 부모로 볼지 정한다. 기본은 LLM에 실제로 전달되는 부모 기준으로 잰다.
- 맥락을 붙이면 청크 길이가 늘어난다. 임베딩 최대 길이 초과 비율을 다시 확인한다.

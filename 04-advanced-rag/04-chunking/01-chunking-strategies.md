# 청킹 방법 (Chunking Strategies)

문서를 검색 단위(청크)로 나누는 방법과 크기의 영향을 정리한다. 기본 RAG 실패 유형 중 F6(본문과 예외 문장이 다른 청크로 나뉨)을 고친다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 작게 찾고 크게 넘기는 방법은 [02-parent-child-contextual](./02-parent-child-contextual.md) 참고

## 1. 청크 크기의 영향

| 청크 | 검색 | 생성 |
| --- | --- | --- |
| 작음 (예: 항 하나) | 내용이 한 가지라 벡터가 선명함, 정확히 찾음 | 조건·예외가 다른 청크에 있어 답이 불완전 |
| 큼 (예: 장 전체) | 여러 내용이 섞여 벡터가 흐려짐, 덜 찾음 | 맥락은 풍부하지만 잡음이 많고 토큰 비용 큼 |

- 검색에 좋은 크기와 생성에 좋은 크기가 다르다. 이 충돌을 푸는 방법이 부모-자식 청크다([02-parent-child-contextual](./02-parent-child-contextual.md)).

### 1.1 크기를 고르는 절차

```text
1. 후보 크기 정하기          128 / 256 / 512 / 1,024 토큰 (겹침은 크기의 10~20%)
2. 같은 토큰 예산으로 맞추기  LLM에 넣는 양을 예: 2,000토큰으로 고정
                             → 128토큰이면 top-15, 256이면 top-8, 512면 top-4, 1,024면 top-2
3. dev 세트로 재기           근거 구간 포함률(C 방식), 문서 단위 Recall, Claim Recall, 질의당 토큰
4. 고르기                    검색과 생성이 함께 좋은 크기. 차이가 유의하지 않으면 청크 수가 적은(큰) 쪽
```

결과 표 예시 (숫자는 예시)

| 크기 | 같은 예산의 k | 근거 구간 포함률 | Claim Recall | 청크 수 |
| --- | --- | --- | --- | --- |
| 128 | 15 | 0.78 | 0.61 | 41,000 |
| 256 | 8 | 0.84 | 0.70 | 21,000 |
| **512** | 4 | **0.86** | **0.74** | 11,000 |
| 1,024 | 2 | 0.80 | 0.72 | 6,000 |

- 같은 k(예: top-5)로 비교하면 큰 청크가 내용이 많아 유리하게 나온다. 반드시 **토큰 예산을 맞춰** 비교한다([03-evals/01-retrieval-metrics/01-reference-based](../../03-evals/01-retrieval-metrics/01-reference-based.md) 3.7).
- 크기를 바꿀 때마다 재색인이 필요하다. 후보를 3~4개로 줄이고, 1차로 검색 지표만 보고 좁힌 뒤 생성 평가를 한다.
- 구조가 있는 문서는 크기보다 구조 단위(3장)가 먼저다. 크기 비교는 구조가 없는 문서나, 구조 단위가 너무 긴 경우에 한다.

## 2. 방법

| 방법 | 나누는 기준 | 장점 | 단점 |
| --- | --- | --- | --- |
| 고정 길이 + 겹침 | N 토큰마다, 앞뒤 일부 겹침 | 단순, 어떤 문서에도 적용 | 문장·조항 중간에서 잘림 |
| 문장·문단 기준 | 문장 끝, 빈 줄 | 문장이 안 잘림 | 길이가 들쭉날쭉 |
| **문서 구조 기준** | 문서의 장 > 절 > 섹션 > 하위 항목 | 의미 단위가 그대로 유지 | 구조 파싱이 필요 |
| 의미 기준 (semantic) | 인접 문장 임베딩 유사도가 떨어지는 곳 | 주제가 바뀌는 곳에서 나눔 | 계산 비용, 결과가 불안정할 수 있음 |

### 고정 길이 손계산

```text
문서 1,000 토큰, 청크 300 토큰, 겹침 50 토큰 → 간격 250 토큰
청크 시작 위치: 0, 250, 500, 750 → 4개 (마지막 청크는 750~1,000, 250 토큰)
저장 토큰 합: 300 + 300 + 300 + 250 = 1,150 → 원문 대비 15% 증가
```

- 겹침은 경계에서 잘린 문장을 양쪽 청크에 남겨 주지만, 저장량과 중복 검색 결과가 늘어난다.

### 의미 기준 손계산

인접 문장끼리 임베딩 유사도를 구해, 유사도가 크게 떨어지는 곳에서 자른다.

```text
문장:     s1     s2     s3     s4     s5     s6
유사도:     0.82   0.79   0.41   0.77   0.74      (s1-s2, s2-s3, …)
기준:     유사도 하위 20% 지점 (또는 고정값 0.5)
자르는 곳: s3 | s4  (0.41)
청크:     [s1 s2 s3]  [s4 s5 s6]
```

- 기준을 고정값으로 두면 문서마다 잘리는 수가 크게 달라진다. 문서 안의 유사도 분포에서 하위 몇 %로 두는 방식이 더 안정적이다.
- 잘린 청크가 최대 길이를 넘으면 다시 고정 길이로 나눈다. 너무 짧은 청크(한 문장)는 이웃과 합친다.
- 임베딩 모델이 바뀌면 잘리는 곳도 바뀐다. 결과가 불안정하다는 단점이 이것이다.

### 토큰은 무엇으로 세나

"300토큰"은 어떤 토크나이저로 셌느냐에 따라 길이가 다르다. 한국어는 토크나이저마다 토큰 수 차이가 크다(같은 문장이 1.5~2배 차이 나기도 한다).

| 용도 | 세는 기준 |
| --- | --- |
| 임베딩 최대 길이를 넘는지 | **임베딩 모델의 토크나이저** |
| 리랭커 최대 길이 | 리랭커의 토크나이저 |
| 컨텍스트 토큰 예산, 비용 | 생성 LLM의 토크나이저 |

- 청크 크기는 임베딩 모델 토크나이저로 정하고, 컨텍스트 예산은 생성 LLM 기준으로 다시 센다. 둘을 같은 숫자로 가정하지 않는다.
- 글자 수로 대신 세면 편하지만 오차가 크다. 기록할 때 어떤 기준인지 함께 적는다.

## 3. 구조가 있는 문서의 구조 기준 청킹

```text
3. 환불 정책                                  ← 섹션
  3.1 환불은 결제일로부터 7일 이내에 ...        ← 하위 항목
  3.2 사용 이력이 있는 상품은 환불하지 않는다.
      단, 제품 결함인 경우에는 예외로 한다.     ← 예외 문장
```

| 단위 | 장점 | 단점 |
| --- | --- | --- |
| 섹션 | 예외 문장이 같은 청크에 남음, 골든셋 판정 단위와 같음 | 긴 섹션은 임베딩 최대 길이를 넘음 |
| 하위 항목 | 검색이 정밀 | 예외와 본문이 다른 항목이면 분리됨, 섹션 제목 맥락 손실 |

- 기본은 **섹션 단위**로 하고, 최대 길이를 넘는 섹션만 하위 항목 단위로 나눈다. 나눌 때 각 청크 앞에 `문서 제목 > 3. 환불 정책`을 붙여 맥락을 남긴다.
- 예외 문장("단, …")은 앞 문장과 떼지 않는다.

### 3.1 자르면 안 되는 블록

| 블록 | 문제 | 규칙 |
| --- | --- | --- |
| 표 | 행 중간에서 자르면 머리글(열 이름)이 없는 행이 남음 | 표는 한 청크로 두거나, 행 단위로 나누면서 행마다 머리글을 붙임 ([05-document-parsing/02-tables-images](../05-document-parsing/02-tables-images.md) 2장) |
| 목록 | 목록 제목("다음 경우는 환불하지 않는다:")과 항목이 떨어짐 | 제목과 항목을 한 청크에 두고, 길면 항목마다 제목을 붙임 |
| 코드·명령어 블록 | 반으로 잘리면 쓸 수 없음 | 블록 전체를 한 단위로 |
| 제목만 있는 줄 | 제목만 들어간 짧은 청크가 생김 | 제목은 다음 본문과 합침 |

- 파서가 블록 종류(표, 목록, 코드)를 표시해 주면 청커가 그 경계를 지킬 수 있다. 파싱 단계에서 구조를 잃으면 청킹에서 되살릴 수 없다.

### 3.2 반복되는 문구

| 문구 | 예 | 처리 |
| --- | --- | --- |
| 머리말·꼬리말 | 페이지마다 나오는 회사명, 페이지 번호 | 파싱 단계에서 제거 |
| 공통 면책·안내 문구 | 모든 섹션 끝에 붙는 "자세한 내용은 고객센터로" | 색인 텍스트에서 제거하고, 필요하면 메타데이터로만 |
| 목차 | 섹션 제목만 나열된 페이지 | 색인에서 제외 |

- 같은 문구가 수백 청크에 들어가면, 그 문구와 비슷한 질문에 엉뚱한 청크들이 동점으로 올라온다. BM25에서는 idf가 낮아 덜하지만 dense에서는 벡터를 흐린다.
- 찾는 법: 여러 문서에서 똑같이 반복되는 문장을 세어 상위 목록을 본다.

## 4. 청크 ID와 메타데이터, 다시 색인하기

청크마다 아래를 함께 저장한다.

| 필드 | 예 | 쓰는 곳 |
| --- | --- | --- |
| `chunk_id` | `DOC_0003:v2:3.2:0` (문서 ID : 버전 : 섹션 : 순번) | 골든셋 qrels, 캐시, 로그 |
| `doc_id`, `doc_version` | `DOC_0003`, `v2` | 문서 단위 매핑, 노후화 점검 |
| 위치 | 섹션 번호, 문서 안 순서, 시작·끝 위치 | 근거 구간 포함률(C 방식), 앞뒤 청크 찾기 |
| `parent_id` | `DOC_0003:v2:3` | 부모-자식 청크 ([02-parent-child-contextual](./02-parent-child-contextual.md)) |
| 청킹 설정 버전 | `chunker=section-v1, size=512` | 설정이 다른 색인끼리 섞이지 않게 |

- **ID는 내용 위치로 만들고, 실행 순서로 만들지 않는다.** 색인할 때마다 1, 2, 3 …으로 번호를 붙이면, 문서 하나만 바뀌어도 뒤의 모든 ID가 밀려 qrels와 캐시가 깨진다.
- 문서 ID와 버전을 분리해 두면, 개정 전후 청크를 함께 보관하고 기준 시점 질의([03-query-transform/02-metadata-filter](../03-query-transform/02-metadata-filter.md) 1.2)에 답할 수 있다.

문서가 바뀌었을 때

```text
1. 바뀐 문서를 찾음 (원문 해시 비교)
2. 그 문서만 다시 청킹 → 새 버전의 청크 ID 생성
3. 이전 버전 청크는 삭제하거나 유효 기간(valid_to)을 채움
4. 새 청크만 sparse·dense 색인에 추가
5. 이 문서를 정답으로 가진 골든셋 질문을 다시 검수 ([03-golden-set/04-update-loop](../../03-evals/03-golden-set/04-update-loop.md) 6장)
```

- 청킹 **설정**을 바꾸면(크기, 방법) 바뀐 문서만이 아니라 전체를 다시 색인한다. 설정 버전이 다른 청크가 한 색인에 섞이면 비교가 무의미해진다.

## 5. 평가할 때 주의

- 청크를 바꾸면 검색 결과의 단위가 바뀐다. 문서 단위로 매핑해서 비교하면 청킹이 달라도 같은 골든셋으로 잴 수 있다([01-reference-based](../../03-evals/01-retrieval-metrics/01-reference-based.md) 3.2 A 방식).
- 다만 문서 단위 매핑은 "정답 문서의 엉뚱한 부분을 가져와도 정답"으로 본다. 청킹 비교에서는 근거 구간(`evidence_span`)이 청크에 들어 있는지 보는 C 방식이 더 정확하다.
- 검색 지표만으로는 F6(조건 누락)를 못 본다. 생성 쪽 Claim Recall과 Context Sufficiency를 함께 본다.
- 겹침이 있으면 거의 같은 청크 두 개가 top-5에 함께 들어와 자리를 차지할 수 있다. 문서당 청크 수 제한이나 MMR로 줄인다([02-reranking/02-candidate-depth](../02-reranking/02-candidate-depth.md) 5장). 겹친 청크끼리는 근거 구간 포함률에서 중복으로 세지 않는다.

## 6. 확인할 점

- 청크 수, 평균·최대 토큰 길이(어떤 토크나이저 기준인지 포함), 최대 길이 초과 비율을 설정마다 기록한다.
- 청킹을 바꾸면 sparse 색인과 dense 벡터를 모두 다시 만든다.

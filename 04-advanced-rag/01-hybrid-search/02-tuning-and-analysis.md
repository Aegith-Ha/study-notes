# 하이브리드 조정과 분석 (Tuning and Analysis)

하이브리드 설정(합치기 방법, α·가중치, RRF k, 후보 수)을 골든셋으로 고르는 방법과, 하이브리드가 실제로 어떤 질의를 살렸는지 분석하는 방법을 정리한다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 합치기 방법은 [01-fusion-methods](./01-fusion-methods.md) 참고

## 1. 효과를 미리 가늠하기

하이브리드가 살릴 수 있는 질의는 **한쪽 검색기만 성공한 질의**다. [dense 검색 README](../../02-retrieval-basics/02-dense-retrieval/README.md)의 질의별 비교 표가 출발점이다.

| | dense 성공 | dense 실패 |
| --- | --- | --- |
| BM25 성공 | 둘 다 성공 | **BM25만 성공 (F2)** |
| BM25 실패 | **dense만 성공 (F1)** | 둘 다 실패 (하이브리드로는 못 살림) |

- 하이브리드 Recall@5의 대략적인 상한은 "둘 중 하나라도 성공한 질의 비율"이다.
- "둘 다 실패"가 많으면 하이브리드보다 쿼리 변환, 청킹이 먼저다([실패 유형](../../02-retrieval-basics/04-naive-rag/02-failure-modes.md)).

## 2. 조정 순서

```text
1. RRF (k = 60), 각 검색기 top-20 → 기준 하이브리드
2. 후보 수 N: 20 / 50 비교
3. 가중 RRF: dense 가중치(0.3 ~ 0.7, 0.1 간격) × k(30 / 60) 비교
4. 가중합: 정규화 방식(min-max / z-score / 분포 기반) × α(0.1 ~ 0.9, 0.1 간격) 비교
5. dev 세트 Recall@5 최고 설정과 RRF 비교 → 차이가 작으면 RRF 유지
6. (필요할 때만) 질의별 가중치, 검색기 3개 이상 결합 (2.1, 2.2)
7. test 세트로 한 번만 확인
```

- α는 dev 세트에서만 고른다. 50건 수준에서는 α를 세밀하게 맞추면 그 세트에 과적합되기 쉽다.
- 가중합이 RRF보다 확실히 낫지 않으면(유의성 검정, [05-regression-ci](../../03-evals/05-regression-ci/01-gate-design.md) 5장) 튜닝할 것이 적은 RRF를 쓴다.
- 3·4단계는 격자 탐색이라 시도한 조합 수가 많다. 조합 수를 기록하고, 1등과 2등의 차이가 유의하지 않으면 기본값에 가까운 쪽을 고른다([00-improvement-levers/02-order-and-rules](../00-improvement-levers/02-order-and-rules.md) 3.4).
- 가중 RRF와 가중합은 가중치의 의미가 다르다. 가중 RRF의 0.6은 순위 점수에 곱하는 값이고, 가중합의 α는 정규화된 점수에 곱하는 값이다. 한쪽에서 고른 값을 다른 쪽에 옮겨 쓰지 않는다.

### 2.1 질의별 가중치

모든 질의에 같은 가중치를 쓰지 않고, 질의 유형에 따라 바꾼다.

| 질의 특징 | 가중치 방향 | 판단 방법 |
| --- | --- | --- |
| 제품 코드, 번호, 문서 제목이 들어 있음 | BM25 쪽을 올림 | 정규식, 식별자 사전 |
| 일상어, 바꿔 말한 질문 | dense 쪽을 올림 | 위에 해당하지 않으면 기본값 |
| 판단이 애매함 | 기본 가중치 | - |

- 식별자가 확실하면 가중치를 바꾸기보다 정확 조회 라우팅이 낫다([03-query-transform/02-metadata-filter](../03-query-transform/02-metadata-filter.md) 5장).
- 판단 단계가 하나 더 생긴다. 판단이 틀린 질의(코드가 아닌데 코드로 본 경우 등)를 따로 세서, 질의별 가중치가 고정 가중치보다 나은지 dev 세트로 확인한다.
- LLM으로 질의 유형을 분류하면 지연과 비용이 늘어난다. 규칙으로 되는 범위부터 쓴다.

### 2.2 검색기 3개 이상, 학습 기반 결합

| 방식 | 내용 | 주의 |
| --- | --- | --- |
| 검색기 3개 | 예: dense + 학습된 sparse + BM25, 가중치 `w_dense`, `w_sparse`, `w_bm25` | 조정할 값이 늘어 과적합 위험이 커진다. 먼저 RRF(가중치 없음)로 셋째 검색기가 보태는 몫이 있는지 확인한다 |
| 같은 모델의 dense·sparse | bge-m3처럼 한 모델에서 나온 둘 | 실패가 겹치기 쉬워 보태는 몫이 작을 수 있다([01-sparse-retrieval/03-learned-sparse](../../02-retrieval-basics/01-sparse-retrieval/03-learned-sparse.md) 8장) |
| 학습 기반 결합 (learning to rank) | 각 검색기의 점수·순위와 질의 특징을 입력으로 최종 점수를 내는 작은 모델을 학습 | 가장 유연하지만 학습용 질의-정답이 수천 건 이상 필요하다. 수백 건 골든셋으로 학습하면 그 세트에 맞춰질 뿐이다 |

- 셋째 검색기는 "앞의 둘이 모두 놓친 질의를 몇 개 살리는가"로 판단한다(1장 표를 검색기 3개로 늘려 센다).

## 3. 나눠서 보기

| 나누는 기준 | 기대 | 확인할 것 |
| --- | --- | --- |
| 말투 (`user` / `expert`) | user는 dense, expert는 BM25 쪽이 강함 | 하이브리드가 두 말투 모두에서 각 단일 검색기 이상인가 |
| 질문 소스 (A / B / C) | C(상황 시나리오)에서 dense 효과가 큼 | 소스별 개선 폭 |
| 질문에 문서 제목·제품 코드 포함 여부 | 포함하면 BM25가 결정적 | 포함 질의에서 dense가 순위를 끌어내리지 않는가 |

- 평균이 올라도 특정 묶음에서 떨어질 수 있다. 특히 `expert` 질의에서 하이브리드가 BM25 단독보다 낮아지면 α나 후보 수를 다시 본다.

## 4. 질의별 변화 분석

| 기준선 → 하이브리드 | 의미 | 다음 행동 |
| --- | --- | --- |
| 실패 → 성공 | 하이브리드 효과 | 유형(F1 / F2) 기록 |
| 성공 → 실패 | **하이브리드가 망친 질의** | 원인 확인: 한쪽의 오답이 정답을 밀어냄 |
| 실패 → 실패 | 하이브리드 범위 밖 | 리랭커, 쿼리 변환 후보 |

- "성공 → 실패" 질의를 꼭 본다. 평균 개선에 가려지기 쉽고, 회귀 테스트의 질의별 회귀 기준에 걸리는 질의다.

## 5. 확인할 점

- 두 검색기가 같은 청크 단위, 같은 문서 집합을 쓰는지 확인한다. 하나라도 다르면 합칠 때 문서 ID가 어긋난다.
- 벡터 DB가 하이브리드 검색(RRF, 가중합)을 내장 지원하면 그대로 쓸 수 있다. 내장 방식의 정규화와 k 값을 확인하고 기록한다.

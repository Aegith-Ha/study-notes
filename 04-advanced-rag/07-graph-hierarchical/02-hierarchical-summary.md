# 계층 요약 검색 (Hierarchical Summary Retrieval)

비슷한 청크를 묶어 요약하고, 그 요약을 다시 묶어 요약하는 식으로 트리를 만든 뒤, 질문에 맞는 단계에서 찾는 방법을 정리한다. 대표가 RAPTOR다. 세부 사실은 아래쪽 청크에서, 전체 흐름은 위쪽 요약에서 찾는다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 연결을 따라가는 방법은 [01-graph-retrieval](./01-graph-retrieval.md) 참고

## 1. 구조

```text
단계 2 (요약의 요약)        [환불·반품 전반]
                           ╱               ╲
단계 1 (요약)       [환불 기한·절차]     [반품 비용·예외]
                    ╱     │     ╲          ╱     ╲
단계 0 (원문 청크)  c1    c2    c3       c4     c5
```

| 단계 | 담는 것 | 잘 맞는 질문 |
| --- | --- | --- |
| 0 원문 청크 | 세부 사실, 숫자, 조건 | "환불 기한은?" |
| 1 요약 | 한 주제의 정리 | "환불 절차를 설명해 줘" |
| 2 이상 | 여러 주제를 아우르는 흐름 | "환불·반품 규정 전반을 요약해 줘" |

만드는 순서
1. 원문 청크를 임베딩한다.
2. 비슷한 청크끼리 묶는다(군집화).
3. 묶음마다 LLM이 요약을 쓴다. 이 요약이 위 단계의 노드다.
4. 요약을 다시 임베딩하고 2~3을 반복한다. 노드가 충분히 적어지면 멈춘다.

## 2. 검색 방식

| 방식 | 하는 일 | 장점 | 단점 |
| --- | --- | --- | --- |
| 트리 탐색 | 맨 위에서 질문과 가까운 노드를 고르고, 그 아래로 내려가며 반복 | 비교 횟수가 적음 | 위에서 잘못 고르면 아래 정답을 못 봄 |
| 전체 펼침 (collapsed tree) | 모든 단계의 노드를 한 색인에 넣고 한 번에 검색 | 질문에 맞는 단계가 저절로 골라짐 | 색인이 커짐 |

- 보통 **전체 펼침**이 더 낫다. 단계를 고르는 판단을 검색 점수에 맡길 수 있기 때문이다.

## 3. 노드 수 손계산

원문 청크 1,000개, 묶음 크기 평균 5개

```text
단계 1:  1,000 / 5 = 200개 요약
단계 2:    200 / 5 =  40개
단계 3:     40 / 5 =   8개
단계 4:      8 / 5 ≈   2개 → 멈춤

요약 노드 합계 = 200 + 40 + 8 + 2 = 250개
LLM 요약 호출  = 250회
색인 크기      = 1,000 + 250 = 1,250개 (원문 대비 25% 증가)
```

- 요약 노드가 원문보다 적어서 색인 증가는 작다. 비용은 대부분 요약 호출에서 나온다.
- 문서 하나가 바뀌면 그 청크가 속한 묶음부터 맨 위까지 요약을 다시 써야 한다. 묶음을 다시 나누면 트리 전체가 바뀔 수 있다.

## 4. 위험

| 위험 | 내용 | 대응 |
| --- | --- | --- |
| 요약 환각 | 요약에 원문에 없는 내용이나 잘못 합친 내용이 들어감 | 요약 노드는 검색용으로만 쓰고, 답변 근거와 인용은 그 아래 원문 청크로 |
| 세부 손실 | 요약 단계에서 숫자·예외 조건이 빠짐 | 세부 질문은 단계 0에서 찾히는지 따로 확인 |
| 갱신 비용 | 문서 변경 시 위쪽 요약 재작성 | 자주 바뀌는 문서에는 쓰지 않거나 주기적으로 일괄 재구축 |
| 묶음 품질 | 다른 주제가 한 묶음에 섞이면 요약이 흐려짐 | 문서 구조(장·절)가 있으면 군집화 대신 구조로 묶음 |

- 문서에 목차 구조가 이미 있으면 군집화 대신 **목차대로 묶는 것**이 더 안정적이다. 이 경우 [04-chunking/02-parent-child-contextual](../04-chunking/02-parent-child-contextual.md)의 부모-자식 청크와 비슷해지고, 차이는 부모 자리에 원문 대신 요약을 둔다는 점이다.

## 5. 평가

| 확인 | 방법 |
| --- | --- |
| 전체 요약형 질문 | pairwise judge로 기준 설정(일반 검색)과 비교. 포괄성, Faithfulness |
| 세부 질문이 나빠지지 않았나 | 단일 근거 질문의 Recall@5, Answer Correctness |
| 어느 단계가 쓰였나 | 검색 결과 top-k의 단계 분포. 세부 질문에 요약 노드만 오면 문제 |
| 비용 | 색인 1회 요약 호출 수, 질의당 컨텍스트 토큰 |

- 검색 지표를 계산할 때 요약 노드는 골든셋 문서가 아니다. 요약 노드가 가리키는 원문 문서로 매핑하거나, 요약 노드는 빼고 계산한다. 어느 쪽인지 결과에 적는다.

## 6. 확인할 점

- 요약 프롬프트와 요약 모델 버전을 기록한다. 바뀌면 트리 전체가 바뀐다.
- 요약 노드의 Faithfulness(원문 청크 대비)를 표본으로 잰다. 요약이 틀리면 검색은 맞아도 답이 틀린다.
- GraphRAG의 커뮤니티 요약([01-graph-retrieval](./01-graph-retrieval.md) 4장)과 비슷한 역할이다. 둘을 모두 만들기보다 하나를 고른다.

# 트레이스 설계 (Trace Design)

RAG·에이전트 요청을 trace와 span으로 나누어 기록하는 구조와, 각 단계에서 남겨야 할 필드를 정리한다.

- 폴더 요약, 메인 결정, 결과는 [README](./README.md) 참고
- 도구와 모니터링은 [02-tools-and-monitoring](./02-tools-and-monitoring.md) 참고

## 1. 왜 필요한가

| 상황 | 트레이스 없이 | 트레이스가 있으면 |
| --- | --- | --- |
| "답이 틀렸다"는 피드백 | 질문만 보고 추측 | 검색 결과에 정답 문서가 있었는지 바로 확인 |
| 응답이 느림 | 전체 시간만 앎 | 어느 단계가 느린지 앎 |
| 비용 증가 | 월 청구서로 뒤늦게 앎 | 질의당 토큰, 호출 수가 늘어난 단계를 앎 |
| 배포 후 품질 변화 | 원인 불명 | 버전 필드로 배포 전후 비교 |

- 검색 실패인지 생성 실패인지 나누는 4분면 진단([03-evals/02-generation-metrics](../../03-evals/02-generation-metrics/README.md))을 운영 질의에도 할 수 있게 된다.

## 2. 구조: trace와 span

```text
trace (요청 1건, trace_id)
 ├─ span: query_transform   (LLM 호출)
 ├─ span: retrieve          (dense + sparse)
 │   ├─ span: dense_search
 │   └─ span: sparse_search
 ├─ span: rerank
 ├─ span: generate          (LLM 호출)
 └─ span: postprocess       (인용 검사, 거절 판정)
```

- 에이전트는 루프 한 번이 span 묶음 하나가 된다. 계획, 도구 호출, 검증이 모두 span으로 남아야 경로를 평가할 수 있다([05-agents/03-plan-execute-verify](../../05-agents/03-plan-execute-verify/README.md)).

## 3. 남길 필드

| 위치 | 필드 | 쓰임 |
| --- | --- | --- |
| trace | trace_id, 시각, 사용자 그룹(익명화), 세션 ID | 피드백 연결, 세션 단위 분석 |
| trace | 버전: 프롬프트, 모델, 인덱스(문서 버전), 설정 | 배포 전후 비교, 재현 |
| 검색 span | 검색어, 필터, top-k 문서 ID와 점수 | 검색 실패 진단, 골든셋 후보 |
| 리랭크 span | 입력 후보 수, 출력 순서와 점수 | 리랭커 효과 확인 |
| LLM span | 모델, 입력·출력 토큰, 캐시 읽은 토큰, 지연(첫 토큰, 전체), 종료 이유 | 비용, 지연, 잘림 확인 |
| 도구 span | 도구 이름, 인자, 결과 요약, 오류 | 도구 호출 평가 |
| 모든 span | 시작·종료 시각, 상태(성공/오류), 오류 메시지 | 지연, 오류율 |

- 문서는 원문 대신 **ID와 점수**를 남긴다. 원문은 문서 버전으로 다시 찾을 수 있고, 저장량과 개인정보 위험이 줄어든다.
- 버전 필드가 없으면 "언제부터 나빠졌나"를 알 수 없다. 가장 먼저 넣는다.

## 4. 개인정보

| 항목 | 처리 |
| --- | --- |
| 질문·답변 원문 | 저장 전 마스킹(주민번호, 전화번호, 이름 등), 보관 기간 제한 |
| 사용자 식별자 | 해시 또는 그룹 단위로만 |
| 조회 권한 | 원문을 볼 수 있는 사람을 제한하고 조회 기록을 남김 |

- 마스킹 방법은 [03-security/02-access-control-pii](../03-security/02-access-control-pii.md) 참고

## 5. 손계산 예시: 지연 분해

요청 1건의 span 기록 (가정)

```text
query_transform    150 ms
retrieve           120 ms   (dense 90, sparse 60 → 병렬이라 긴 쪽 + 합치기 30)
rerank             180 ms
generate         1,900 ms   (첫 토큰 600 + 생성 1,300)
postprocess         50 ms
──────────────────────────
합계             2,400 ms
사용자가 첫 글자를 보는 시간 = 150 + 120 + 180 + 600 = 1,050 ms
```

읽는 법
- 전체의 79%(1,900 / 2,400)가 생성이다. 검색을 줄여도 체감 개선은 작다.
- 스트리밍이면 사용자는 1,050 ms 뒤에 답을 보기 시작한다. 이때는 생성 전 단계(450 ms)의 비중이 커진다.
- 쿼리 변환(150 ms)이 효과에 비해 비싼지는 [04-advanced-rag/03-query-transform](../../04-advanced-rag/03-query-transform/README.md) 결과와 함께 본다.

## 6. 확인할 점

- 병렬 span은 합이 아니라 가장 긴 것이 전체 시간에 들어간다.
- 평균 대신 p50, p95를 본다. 느린 요청은 대개 긴 입력이나 재시도에서 나온다.
- 트레이싱 자체가 응답을 늦추면 안 된다. 기록은 비동기로 보낸다.

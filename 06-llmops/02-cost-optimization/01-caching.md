# 캐싱 (Prompt Caching, Semantic Cache)

LLM 비용을 줄이는 두 가지 캐시, 프롬프트 캐싱과 시맨틱 캐시의 원리와 차이, 쓸 때의 위험을 정리한다. 단가는 모델과 시점마다 다르므로 상대 비용으로 계산한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 라우팅과 입력 줄이기는 [02-model-routing](./02-model-routing.md) 참고

## 1. 두 캐시의 차이

| 항목 | 프롬프트 캐싱 | 시맨틱 캐시 |
| --- | --- | --- |
| 재사용하는 것 | 입력 앞부분의 처리 결과 (모델 제공자 쪽) | 이전 질문의 **답변** (앱 쪽) |
| 적중 조건 | 앞부분이 글자 그대로 같음 | 질문 임베딩이 충분히 비슷함 |
| LLM 호출 | 여전히 함 (앞부분만 싸게) | 적중하면 하지 않음 |
| 답변 | 매번 새로 생성 | 이전 답변 그대로 |
| 품질 위험 | 없음 | 다른 질문에 이전 답을 줄 수 있음 |
| 절감 폭 | 캐시된 입력 부분만 | 적중한 요청 전체 |

- 프롬프트 캐싱은 결과가 바뀌지 않으므로 먼저 적용한다. 시맨틱 캐시는 품질 위험을 감수하는 선택이다.

## 2. 프롬프트 캐싱

### 동작

```text
[시스템 프롬프트 + 도구 정의]  [검색 결과]  [질문]
 └──── 매 요청 같음 ────┘      └─ 요청마다 다름 ─┘
       캐시 적중 → 싸게 읽음        일반 단가
```

- 캐시는 앞에서부터 같은 부분까지만 맞는다. 중간에 바뀌는 값(날짜, 사용자 이름)을 넣으면 그 뒤는 모두 캐시가 깨진다.
- 처음 쓰는 요청은 캐시 쓰기 비용이 들고, 캐시는 일정 시간이 지나면 사라진다. 요청이 드물면 효과가 작다.
- 단가와 유지 시간은 모델 제공자 문서에서 실험 날짜 기준으로 확인한다.

### 손계산 예시

가정: 시스템 프롬프트 + 도구 정의 3,000토큰, 검색 결과 2,000토큰, 질문 100토큰. 캐시 읽기는 일반 입력 단가의 10%, 캐시 쓰기는 125%

```text
캐시 없음:        3,000 + 2,000 + 100                 = 5,100 (일반 입력 환산)
캐시 적중:        3,000 × 0.1 + 2,000 + 100            = 2,400 → 47%
캐시 쓰기 요청:   3,000 × 1.25 + 2,000 + 100           = 5,850

1,000 요청 중 쓰기 20번, 적중 980번이면
평균 = (20 × 5,850 + 980 × 2,400) / 1,000 = 2,469 → 캐시 없음 대비 약 48%
```

읽는 법
- 고정 앞부분이 클수록, 같은 앞부분을 쓰는 요청이 잦을수록 효과가 크다.
- 검색 결과(2,000)는 요청마다 달라 캐시되지 않는다. 남은 비용의 대부분이다. 이 부분은 top-k 조정으로 줄인다([02-model-routing](./02-model-routing.md) 3장).

## 3. 시맨틱 캐시

### 동작

```text
질문 → 임베딩 → 캐시에서 가장 비슷한 이전 질문 검색
        ├─ 유사도 ≥ 기준 → 이전 답변 반환 (LLM 호출 없음)
        └─ 미만 → 정상 RAG → 결과를 캐시에 저장
```

### 위험: 비슷하지만 다른 질문

| 질문 A (캐시됨) | 질문 B (새 질문) | 같은 답인가 |
| --- | --- | --- |
| 근로자가 연차를 쓰려면? | 근로자가 연차를 몇 일 쓸 수 있나? | 아니오 |
| 5인 이상 사업장 해고 예고 기간은? | 5인 미만 사업장 해고 예고 기간은? | 아니오 (적용 범위가 다를 수 있음) |
| 2023년 기준 최저임금은? | 2024년 기준 최저임금은? | 아니오 |

- 법령 질문은 숫자, 날짜, 조건 한 단어로 답이 바뀐다. 임베딩 유사도는 이런 차이에 둔하다.
- 법령이 개정되면 캐시된 답이 틀린 답이 된다.

### 쓴다면

| 대책 | 내용 |
| --- | --- |
| 높은 유사도 기준 | 적중률보다 잘못된 적중을 줄이는 쪽 |
| 캐시 키에 버전 포함 | 문서 버전, 프롬프트 버전이 바뀌면 다른 키 |
| 무효화 | 법령 개정 시 해당 법령을 인용한 캐시 삭제 |
| 숫자·날짜 일치 조건 | 질문의 숫자, 연도, 조건어가 다르면 적중으로 보지 않음 |
| 개인화 질문 제외 | 사용자별 권한이 다른 문서는 캐시하지 않음 ([03-security](../03-security/README.md)) |

### 손계산 예시

```text
요청 1,000건, 유사도 기준 0.95에서 적중 150건
적중 150건 중 사람이 검토해 잘못된 답 6건 → 잘못된 적중률 6 / 150 = 0.04
LLM 호출 절감 = 150 / 1,000 = 15%
(임베딩·캐시 검색 비용은 LLM 비용보다 훨씬 작다고 보고 무시)
```

- 비용 15% 절감과 틀린 답 6건(전체의 0.6%)을 맞바꾼 것이다. 법령 도메인에서는 대개 받아들이기 어렵다. 기준을 올리거나 FAQ처럼 답이 고정된 질문에만 쓴다.

## 4. 확인할 점

- 캐싱 효과는 트레이스의 캐시 읽기 토큰으로 확인한다([01-tracing](../01-tracing/01-trace-design.md)).
- 시맨틱 캐시의 잘못된 적중은 자동 지표로 잘 잡히지 않는다. 적중 사례를 표본 검토한다.

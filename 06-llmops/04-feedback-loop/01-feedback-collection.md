# 피드백 수집 (Feedback Collection)

운영에서 얻을 수 있는 피드백을 명시적 피드백과 암묵적 신호로 나누고, 각각의 신뢰도와 수집 설계를 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 모은 피드백으로 루프를 돌리는 방법은 [02-loop-operation](./02-loop-operation.md) 참고

## 1. 신호 종류

| 신호 | 예 | 양 | 신뢰도 | 쓰임 |
| --- | --- | --- | --- | --- |
| 👍/👎 | 답변 아래 버튼 | 적음 (요청의 몇 %) | 중간 | 문제 사례 수집, 비율 추이 |
| 👎 사유 | 틀림 / 근거 없음 / 못 찾음 / 기타 | 더 적음 | 중간 | 원인 분류의 첫 단서 |
| 자유 의견 | "2024년 개정 내용이 빠졌어요" | 매우 적음 | 높음 (구체적) | 정답 확인 |
| 같은 세션 재질문 | 바로 비슷한 질문을 다시 함 | 많음 | 낮음 | 실패 후보 |
| 답변 복사·인용 클릭 | 답이나 근거 링크를 씀 | 많음 | 낮음 | 성공 후보 |
| 이탈 | 답을 받고 바로 종료 | 많음 | 매우 낮음 | 만족해서 끝냈는지 실패해서 떠났는지 모름 |

- 암묵적 신호는 혼자 판단 근거로 쓰지 않는다. 검토할 후보를 고르는 데 쓴다.
- 👎에는 답이 맞아도 원하는 답이 아니어서 누른 경우(법령상 불가하다는 답 등)가 섞인다. 👎 = 틀린 답이 아니다.

## 2. 피드백의 치우침

| 치우침 | 내용 | 대응 |
| --- | --- | --- |
| 참여 편향 | 매우 불만족한 사용자가 더 많이 누름 | 비율 절대값보다 추이를 봄 |
| 유형 편향 | 특정 질문 유형·사용자 그룹에 피드백이 몰림 | 유형별로 나눠 봄 |
| 위치 편향 | 버튼이 잘 안 보이면 피드백이 적음 | UI 변경 시점을 기록 |
| 조용한 실패 | 틀린 답을 맞다고 믿은 사용자는 👎를 누르지 않음 | 정답 없는 지표 샘플링으로 보완 ([01-tracing](../01-tracing/02-tools-and-monitoring.md)) |

- 가장 위험한 실패(그럴듯하게 틀린 답)는 피드백으로 잘 잡히지 않는다. 피드백은 운영 모니터링의 한 축일 뿐이다.

## 3. 수집 설계

| 항목 | 설계 |
| --- | --- |
| 저장 필드 | trace ID, 신호 종류, 사유, 자유 의견(마스킹), 시각, 버전 |
| 사유 선택지 | 원인 분류와 맞춤: "틀린 내용" → 생성 또는 검색, "근거 없음" → 생성, "못 찾음" → 검색, "질문을 잘못 이해" → 쿼리 이해 |
| 부담 | 👎일 때만 사유를 묻고 선택은 한 번 클릭으로 |
| 개인정보 | 자유 의견은 마스킹 후 저장 ([03-security/02-access-control-pii](../03-security/02-access-control-pii.md)) |

- trace ID가 없는 피드백은 원인을 찾을 수 없다. 버튼을 붙일 때 함께 넣는다.

## 4. 확인할 점

- 👎 비율은 질문 구성이 바뀌어도 달라진다. 배포 효과를 볼 때는 같은 기간 질문 유형 분포도 함께 본다.
- 피드백 수가 적은 기간의 비율은 흔들림이 크다. 건수를 함께 표시한다.

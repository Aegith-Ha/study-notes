# 피드백 루프 운영 (Loop Operation)

모은 피드백을 분류하고, 원인별로 조치하고, 골든셋에 반영하고, 회귀 테스트로 확인하는 루프의 절차를 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 피드백 종류와 수집은 [01-feedback-collection](./01-feedback-collection.md) 참고

## 1. 루프

```text
운영 ──▶ [수집] 👎, 재질문, 샘플 judge 저점수 (trace ID 포함)
           │
           ▼
        [분류] trace를 열어 원인 판정
           │
           ├─ 검색 실패 ──▶ 검색 개선 (04-advanced-rag)
           ├─ 생성 실패 ──▶ 프롬프트·모델 개선
           ├─ 범위 밖   ──▶ 거절 문구·안내 개선, 범위 확장 검토
           └─ 사용자 오류·기타 ──▶ 기록만
           │
           ▼
        [반영] 사람이 정답·관련 문서 확인 → 골든셋 새 버전
           │
           ▼
        [확인] 회귀 테스트 통과 → 배포 → 해당 유형 👎 추이
```

- 골든셋 반영 절차(검증, 버전 관리)는 [03-evals/03-golden-set/03-update-loop](../../03-evals/03-golden-set/03-update-loop.md)를 따른다. 이 노트는 그 앞단(운영에서 사례를 고르고 분류하는 부분)을 다룬다.

## 2. 분류 기준

trace에서 검색 결과와 답변을 보고 판정한다.

| 분류 | 판정 | 조치 |
| --- | --- | --- |
| 검색 실패 | 필요한 문서가 top-k에 없음 | 검색어·청킹·하이브리드·필터 개선 |
| 생성 실패 | 필요한 문서가 있는데 답이 틀림, 근거 없는 내용 | 프롬프트, 모델, 문서 순서 |
| 범위 밖 | 색인에 없는 법령·주제 | 거절 품질 확인, 범위 확장 검토 |
| 문서 문제 | 문서가 오래됨, 파싱 오류 | 문서 갱신, 파싱 개선 ([04-advanced-rag/05-document-parsing](../../04-advanced-rag/05-document-parsing/README.md)) |
| 사용자 오류·기타 | 질문 의도 불명, 답이 맞는데 원하는 답이 아님 | 기록만 |

- 검색 실패와 생성 실패의 구분은 [03-evals/02-generation-metrics](../../03-evals/02-generation-metrics/README.md)의 4분면과 같다.
- 분류량이 많으면 judge로 1차 분류하고 사람이 확인한다. judge 분류의 정확도도 표본으로 잰다([03-evals/04-llm-judge](../../03-evals/04-llm-judge/README.md)).

## 3. 손계산 예시

```text
한 달 요청 10,000건, 👍/👎 응답 300건 (3%), 👎 90건

분류 결과 (90건):
  검색 실패        40
  생성 실패        25
  범위 밖          15
  사용자 오류·기타 10
  ─────────────────
  합계             90

골든셋 반영 후보 = 검색 실패 + 생성 실패 = 65건
  사람 확인에서 정답·관련 문서를 확정한 사례 50건
  기존 골든셋과 거의 같은 질문 8건 제외 → 신규 42건
```

읽는 법
- 👎의 44%(40 / 90)가 검색 실패다. 다음 개선은 생성보다 검색 쪽이 우선이다.
- 범위 밖 15건이 같은 법령에 몰려 있으면 색인 범위 확장을 검토한다. 흩어져 있으면 거절 문구 개선만 한다.
- 신규 42건을 골든셋에 넣기 전후의 지표는 바로 비교하지 않는다. 버전이 다르면 같은 시스템도 점수가 달라진다. 새 버전에서 기준 시스템을 다시 돌려 기준선을 갱신한다([03-evals/05-regression-ci](../../03-evals/05-regression-ci/README.md)).

## 4. 주기와 책임

| 주기 | 할 일 |
| --- | --- |
| 매일 | 대시보드 알림 확인 ([01-tracing](../01-tracing/02-tools-and-monitoring.md)) |
| 주 1회 | 👎·저점수 사례 분류, 원인별 건수 기록 |
| 월 1회 | 확인된 사례를 골든셋 새 버전으로, 기준선 갱신 |
| 개선 배포 후 | 해당 유형 지표와 👎 비율을 배포 전 기간과 비교 |

## 5. 확인할 점

- 골든셋을 👎 사례로만 채우면 어려운 질문 쪽으로 치우친다. 출처별 비율을 기록하고 균형을 본다([03-evals/03-golden-set/01-query-sources](../../03-evals/03-golden-set/01-query-sources.md)).
- 같은 질문을 dev와 test 양쪽에 넣지 않는다. 새 사례는 분할 규칙에 따라 한쪽에만 넣는다.
- 고친 사례가 다시 나빠지지 않게 해당 사례를 회귀 테스트에 남긴다.

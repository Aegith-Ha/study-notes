# 계획-실행-검증 루프 설계 (Loop Design)

여러 단계가 필요한 작업에서 에이전트가 계획을 세우고, 실행하고, 결과를 검증하며, 필요하면 계획을 고치는 루프의 구조를 정리한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 실패했을 때 복구하는 방법은 [02-failure-recovery](./02-failure-recovery.md) 참고

## 1. 패턴

| 패턴 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| ReAct | 생각 → 도구 호출 → 결과 확인을 한 단계씩 반복 | 결과를 보며 유연하게 진행 | 큰 그림 없이 헤매기 쉬움, 단계가 길어짐 |
| 계획 후 실행 (plan-and-execute) | 먼저 전체 단계 목록을 만들고 차례로 실행 | 진행 상황이 보이고, 단계별 비용 예측 가능 | 중간 결과가 예상과 다르면 계획이 틀어짐 |
| 계획-실행-검증 | 단계 실행 후 완료 기준으로 검증, 실패하면 재계획 | 틀린 결과로 계속 진행하는 것을 막음 | 검증 비용이 추가됨 |

```text
목표 ──▶ [계획] 단계 목록 + 각 단계의 완료 기준
              │
              ▼
         [실행] 단계 i 수행 (도구 호출)
              │
              ▼
         [검증] 완료 기준을 만족하나?
              ├─ 예 ──▶ 다음 단계 (모두 끝나면 최종 검증 → 답변)
              └─ 아니오 ──▶ [복구 / 재계획] (02-failure-recovery)
```

## 2. 검증을 어떻게 하나

| 방법 | 예 | 비용 | 신뢰도 |
| --- | --- | --- | --- |
| 규칙 검사 | 결과가 비어 있지 않은가, 형식이 맞나, 날짜가 범위 안인가 | 거의 없음 | 높음 (잡는 범위는 좁음) |
| 도구로 확인 | 인용한 섹션을 `get_section`으로 다시 조회해 내용 대조 | 도구 호출 | 높음 |
| LLM 검증 | 결과가 단계 목표를 달성했는지 LLM이 판정 | LLM 호출 | judge 품질에 의존 |

- 규칙과 도구로 확인할 수 있는 것은 먼저 그렇게 한다. LLM 검증은 남은 것에만 쓴다.
- LLM 검증은 평가용 judge와 같은 문제(관대함, 편향)를 가진다. 판정 기준을 [04-llm-judge](../../03-evals/04-llm-judge/README.md)의 rubric처럼 구체적으로 쓴다.

## 3. 멈추는 조건

| 조건 | 이유 |
| --- | --- |
| 최종 검증 통과 | 정상 종료 |
| 최대 단계 수 | 무한 반복 방지 |
| 토큰·비용 예산 | 비용 폭주 방지 |
| 같은 실패 반복 | 같은 단계가 같은 이유로 N번 실패하면 중단 |
| 사람 확인 필요 | 쓰기 동작, 확신이 낮은 결론 |

- 중단할 때는 **어디까지 했고 무엇이 막혔는지**를 남긴다. 빈손으로 끝내지 않는다.

## 4. 상태 관리

| 저장할 것 | 이유 |
| --- | --- |
| 원래 목표 | 단계가 길어져도 목표에서 벗어나지 않게 매 단계 다시 제시 |
| 계획과 각 단계 상태 (대기 / 완료 / 실패) | 재계획 시 완료한 단계를 다시 하지 않음 |
| 단계 결과 요약 | 전체 결과를 계속 넣으면 컨텍스트가 넘침 |
| 실패 기록 | 같은 실패 반복 감지 |

## 5. 언제 쓰나

| 작업 | 맞는 구조 |
| --- | --- |
| 질문 하나에 문서 하나 | 고정 RAG 파이프라인 |
| 다중 근거 질문 | Agentic RAG ([01-agentic-rag](../01-agentic-rag/README.md)) |
| 여러 도구를 순서대로 써야 하는 작업 ("계약서의 조항을 사내 규정과 대조해 위반 가능성 목록 작성") | 계획-실행-검증 |

- 단계가 적고 정해져 있으면 에이전트보다 고정된 워크플로가 싸고 안정적이다. 단계가 입력마다 달라질 때 에이전트 루프를 쓴다.

## 6. 확인할 점

- 계획, 각 단계, 검증 결과를 모두 기록한다(트레이싱). 실패 분석은 이 기록 없이는 불가능하다.
- 평가는 최종 결과(작업 성공률)와 과정(단계 수, 재계획 횟수, 비용)을 함께 본다([02-trajectory-evaluation](../01-agentic-rag/02-trajectory-evaluation.md)과 같은 방식).

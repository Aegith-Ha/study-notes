# 함수 호출 (Function Calling)

LLM이 정해진 도구(함수)를 골라 인자를 채워 호출하게 하는 방법과, 도구를 설계하고 평가하는 법을 정리한다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 도구를 여러 앱에서 재사용하는 표준 연결 방식은 [02-mcp](./02-mcp.md) 참고

## 1. 동작 흐름

```text
앱 ──▶ LLM: 질문 + 도구 목록 (이름, 설명, 인자 스키마)
LLM ──▶ 앱: "search_docs 도구를 {doc_title: "환불 정책", query: "환불 기한"}으로 호출"
앱: 도구 실행 (LLM은 직접 실행하지 않음)
앱 ──▶ LLM: 도구 결과
LLM ──▶ 앱: 결과를 바탕으로 답변 (또는 다른 도구 호출)
```

- LLM은 **호출할 내용을 만들 뿐**이고, 실행과 권한 확인은 앱이 한다. 그래서 위험한 동작은 앱에서 막을 수 있다.
- Agentic RAG의 검색도 이 방식으로 구현한다. 검색이 도구 하나가 된다.

## 2. 도구 정의

| 요소 | 예 | 작성 요령 |
| --- | --- | --- |
| 이름 | `search_docs` | 동사 + 대상, 하는 일이 바로 보이게 |
| 설명 | "사내 규정 문서를 검색한다. 문서 제목을 알면 doc_title에 넣는다. 공지사항은 검색하지 않는다." | **언제 쓰고 언제 쓰지 않는지**까지 적는다. LLM은 설명을 보고 고른다 |
| 인자 스키마 | `doc_title`(문자열, 선택), `query`(문자열, 필수), `top_k`(정수, 1~10) | 타입, 필수 여부, 허용값(enum), 범위를 명시 |
| 결과 형식 | `[{doc_id, doc_title, section, text}]` | 짧고 구조화. 인용에 필요한 ID 포함 |

## 3. 설계 원칙

| 원칙 | 이유 |
| --- | --- |
| 도구 수를 적게, 겹치지 않게 | 비슷한 도구가 많으면 잘못 고른다 |
| 읽기 도구와 쓰기 도구 분리 | 조회는 자동으로, 변경·삭제는 사람 확인 후 |
| 허용값은 enum으로 | 자유 문자열보다 잘못된 인자가 줄어든다 |
| 오류는 LLM이 고칠 수 있는 문장으로 | "doc_title '환불규정'을 찾을 수 없음. 정식 명칭(환불 정책)을 사용" |
| 결과는 필요한 만큼만 | 큰 결과는 컨텍스트를 낭비하고 판단을 흐린다 |
| 같은 호출은 같은 결과 (읽기 도구) | 재시도와 회귀 테스트가 안전해진다 |

## 4. 평가

정답이 분명한 단계라 judge 없이 채점할 수 있다.

| 지표 | 계산 |
| --- | --- |
| 도구 선택 정확도 | 맞는 도구를 고른 비율 (도구가 필요 없는 요청에서 호출하지 않은 것 포함) |
| 인자 정확 일치 | 맞는 도구를 고른 경우 중 인자가 정답과 같은 비율 (정규화 후) |
| 스키마 위반율 | 타입·필수값·허용값을 어긴 호출 비율 |
| 불필요 호출률 | 호출이 필요 없는 요청에서 도구를 부른 비율 |

손계산 예시: 도구 호출 평가 요청 40건

```text
도구가 필요한 요청 36건, 필요 없는 요청 4건
맞는 도구 선택 33건 + 필요 없는 요청에서 호출 안 함 3건 → 도구 선택 정확도 36 / 40 = 0.90
맞는 도구 33건 중 인자 일치 29건 → 인자 정확 일치 29 / 33 = 0.88
필요 없는 요청 4건 중 호출 1건 → 불필요 호출률 1 / 4 = 0.25
```

- 인자 오류 4건을 보면 대부분 문서 약칭이나 날짜 형식 문제인 경우가 많다. 설명과 enum을 고치면 줄어든다.

## 5. 확인할 점

- 도구 설명은 프롬프트의 일부다. 설명을 고치면 버전을 올리고 다시 평가한다.
- 도구 결과에 들어 있는 문장이 LLM에게 지시처럼 읽힐 수 있다(간접 프롬프트 인젝션). 외부 데이터를 돌려주는 도구는 [06-llmops/03-security](../../06-llmops/03-security/01-prompt-injection.md)의 대응을 따른다.

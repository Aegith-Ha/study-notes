# MCP (Model Context Protocol)

LLM 앱과 외부 도구·데이터를 연결하는 표준 프로토콜인 MCP의 구조와, 사내 DB·API를 MCP로 연결할 때의 설계 원칙을 정리한다.

- 폴더 요약, 메인 결정, 결과는 [README](./README.md) 참고
- 도구 정의와 평가는 [01-function-calling](./01-function-calling.md) 참고

## 1. 왜 표준이 필요한가

```text
표준 없이:  앱 A ─ 전용 연결 ─ DB      앱 B ─ 또 다른 전용 연결 ─ DB
MCP:        앱 A ─┐
            앱 B ─┼─ MCP ─ [MCP 서버: DB 도구] ─ DB
            앱 C ─┘
```

- 도구를 한 번 MCP 서버로 만들면 MCP를 지원하는 여러 앱(채팅 앱, IDE, 자체 에이전트)에서 같은 도구를 쓸 수 있다.
- 함수 호출이 "LLM이 도구를 부르는 방식"이라면, MCP는 "도구를 앱에 꽂는 방식"이다. 둘은 함께 쓰인다.

## 2. 구성 요소

| 구성 | 역할 | 예 |
| --- | --- | --- |
| 호스트 (host) | LLM을 쓰는 앱 | 채팅 앱, IDE, 자체 에이전트 |
| 클라이언트 (client) | 호스트 안에서 서버 하나와 연결을 유지 | 서버마다 하나 |
| 서버 (server) | 도구·데이터를 제공 | 법령 검색 서버, 사내 DB 서버 |

서버가 제공하는 것

| 종류 | 내용 | 예 |
| --- | --- | --- |
| tools | LLM이 호출하는 함수 | `search_law`, `get_article` |
| resources | 읽을 수 있는 데이터 | 법령 원문, 문서 |
| prompts | 미리 만든 프롬프트 템플릿 | "조문 비교" 템플릿 |

- 연결 방식(transport)은 로컬 프로세스로 띄우는 stdio와, 원격 서버용 HTTP 방식이 있다.
- 메시지는 JSON-RPC 형식이다.

## 3. 사내 DB·API를 MCP로 연결할 때

| 원칙 | 내용 |
| --- | --- |
| 최소 권한 | DB 계정은 읽기 전용, 필요한 테이블·뷰만. 쓰기 도구는 별도 서버로 분리 |
| 자유 SQL 금지 | "SQL 실행" 도구 대신 목적별 도구(`get_contract_by_id`) 제공 |
| 사용자 권한 전달 | 호출한 사용자의 권한으로 조회. 서버의 강한 권한으로 모든 데이터를 보여 주지 않음 |
| 결과 제한 | 반환 행 수 상한, 개인정보 필드 마스킹 |
| 감사 기록 | 누가, 어떤 도구를, 어떤 인자로 호출했는지 기록 |
| 위험 동작 확인 | 변경·삭제 도구는 사람 확인 후 실행 |

- 자유 SQL 도구는 편하지만 권한 밖 조회, 대량 조회, 실수로 인한 변경 위험이 크다. 목적별 도구가 평가하기도 쉽다(도구 선택·인자 정확도로 채점 가능).

## 4. 보안 위험

| 위험 | 내용 | 대응 |
| --- | --- | --- |
| 간접 프롬프트 인젝션 | 도구 결과(문서, DB 값) 안의 문장이 LLM에게 지시처럼 작동 | 도구 결과를 데이터로 표시, 위험 동작은 사람 확인 |
| 과도한 권한 | 서버가 필요 이상 권한을 가짐 | 최소 권한, 사용자 권한 전달 |
| 신뢰할 수 없는 서버 | 외부 MCP 서버가 도구 설명으로 LLM을 조작 | 검증한 서버만 연결, 도구 설명 검토 |
| 정보 유출 | 한 도구 결과를 다른 도구로 외부에 보냄 | 외부 전송 도구 제한, 감사 기록 |

- 상세 대응은 [06-llmops/03-security](../../06-llmops/03-security/README.md)에서 다룬다.

## 5. 확인할 점

- MCP 서버의 도구 설명과 스키마도 버전으로 관리한다. 설명이 바뀌면 도구 선택 정확도가 바뀐다.
- 도구 호출 평가 세트는 MCP로 연결해도 그대로 쓸 수 있다. 연결 방식이 바뀌어도 도구 이름·인자가 같으면 결과를 비교할 수 있다.

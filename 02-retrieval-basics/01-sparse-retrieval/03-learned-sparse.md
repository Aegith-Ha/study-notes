# 학습된 sparse 검색 (Learned Sparse Retrieval)

BM25처럼 "단어 → 가중치" 형태의 sparse 벡터를 쓰되, 가중치를 공식이 아니라 언어 모델이 매기는 검색을 정리한다. 가중치만 학습하는 방식과 문서에 없는 단어까지 덧붙이는 확장형(SPLADE)으로 나눠 보고, 대표 모델인 SPLADE를 따로 설명한다.

- 폴더 요약과 메인 결정은 [README](./README.md) 참고
- 공식 기반 sparse 검색은 [02-bm25](./02-bm25.md), 역색인은 [01-inverted-index-tfidf](./01-inverted-index-tfidf.md) 참고
- 의미 기반 검색은 [02-dense-retrieval](../02-dense-retrieval/README.md) 참고

## 1. 학습된 sparse란

BM25는 tf·idf 공식으로 단어 가중치를 계산한다. 학습된 sparse는 **언어 모델이 문맥을 보고 단어 가중치를 매긴다.** 결과는 여전히 sparse 벡터라서 BM25와 같은 역색인에 그대로 넣을 수 있고, 어떤 단어 때문에 찾았는지도 보인다. dense처럼 의미를 벡터 하나로 압축하지 않는다.

- **목적:** BM25의 빠른 역색인 검색과 설명 가능성은 유지하면서, 공식이 놓치는 단어 중요도(와 확장형이면 동의어·다른 표현)를 모델로 보완해 검색 품질을 올리는 것이다.

```text
sparse 검색
├─ 공식 기반: BM25, TF-IDF
└─ 학습된 sparse (모델이 단어 가중치를 매김)
   ├─ 가중치만 학습: DeepImpact, uniCOIL, bge-m3 sparse 등
   └─ 확장형:        SPLADE (대표), SPLADE++ 등
```

dense 임베딩과의 차이: 둘 다 같은 종류의 인코더 모델로 만들지만, 결과 벡터의 모양과 의미가 다르다.

| | dense (보통 말하는 "임베딩") | 학습된 sparse |
| --- | --- | --- |
| 차원 수 | 고정, 수백~수천 (예: 1,024) | 모델 어휘 크기 (수만~25만) |
| 값이 있는 칸 | 모든 칸 | 대부분 0, 수십~수백 칸만 |
| 칸 하나의 뜻 | 해석할 수 없음 | **단어(토큰) 하나** |
| 저장 형태 | 숫자 배열 `[0.12, -0.03, …]` | `{토큰ID: 가중치}` dict |
| 검색 | ANN 인덱스 | 역색인 |

```text
"환불은 7일 이내"
dense:   [0.12, -0.03, 0.58, ..., 0.07]     ← 1,024칸 전부 값, 뜻은 해석 불가
sparse:  {환불: 1.2, 7: 0.4, 일: 0.3, 이내: 0.3}   ← 어휘 수만 칸 중 몇 칸만 값, 칸이 곧 단어
```

- "벡터화한다"는 둘 다 맞지만, "임베딩"은 보통 dense를 가리킨다. bge-m3는 sparse 출력을 `lexical_weights`(단어 가중치)라고 부른다.

## 2. 두 종류: 가중치만 학습 / 확장형

문서에 없는 단어까지 덧붙이는지(확장)에 따라 나뉜다.

| | BM25 | 가중치만 학습 | 확장형 |
| --- | --- | --- | --- |
| 단어 가중치 | tf, idf, 문서 길이로 계산 | 모델이 문맥을 보고 예측 | 모델이 문맥을 보고 예측 |
| 가중치를 받는 단어 | 입력에 나온 단어 | **입력에 나온 토큰만** | 입력 토큰 + **어휘 전체 중 관련 단어** |
| 문서에 없는 단어 | 점수 0 | 점수 0 | 관련 단어로 확장해 점수를 줌 ("환불" 문서에 "취소") |
| 주로 고치는 것 | - | 의미 없는 단어가 자주 나와 점수가 오르는 문제 (단어 중요도) | 위 문제 + 동의어·다른 표현 (어휘 불일치) |
| 토큰 단위 | 형태소 분석기 + 사용자 사전 (직접 정함) | 모델의 서브워드 토크나이저 (고정) | 모델의 서브워드 토크나이저 (고정) |
| 학습·인코딩 | 불필요, CPU로 빠름 | 문서 전체를 모델로 인코딩 | 문서 전체를 모델로 인코딩, 색인이 더 큼 |
| 설명 가능성 | 높음 | 높음 (겹친 단어가 그대로 보임) | 중간 (확장된 단어는 보이지만 왜 확장됐는지는 모름) |
| 대표 예 | `rank_bm25`, Elasticsearch | **bge-m3의 sparse 출력** | **SPLADE** |
| 역색인에 미리 저장하는 값 | tf + 문서 길이 등 통계 (점수는 검색할 때 idf로 계산) | 모델이 매긴 최종 가중치 | 모델이 매긴 최종 가중치 |
| 문서를 추가하면 | 통계가 바뀌어 기존 문서 점수도 달라짐 | 새 문서만 인코딩, 기존 값 그대로 | 같음 |

확장의 성질 (확장형)
- **단어별 규칙이 아니라 문서 전체의 문맥으로 정한다.** 같은 "사과"라도 "가을에 수확하는 과일" 문서는 과일·열매 쪽으로, "동료에게 사과했다" 문서는 사죄·용서 쪽으로 확장된다. "애플 아이폰" 문서는 사과로 확장되지 않는다. 동의어 사전처럼 "사과 = 애플"을 항상 적용하지 않는다.
- **확장 단어가 항상 낮은 것은 아니다.** 대체로 원문 단어보다 낮지만, 가중치는 "이 문서를 찾는 데 얼마나 중요한가"로 학습된 값이다. 원문에 있어도 의미가 약한 단어(조사 등)는 0이 되고, 핵심 주제를 잘 나타내는 확장 단어는 일부 원문 단어보다 높을 수 있다.
- 확장은 문서를 역색인 목록에 더 많이 올려 줄 뿐, 검색 원리는 같다. 목록에 없는 문서는 여전히 0점이다.

## 3. 인코딩과 저장

### 3.1 문서 하나를 벡터로 바꾸는 과정

토큰화는 먼저 하지만, 모델에는 토큰을 하나씩이 아니라 **청크 단위로 통째로** 넣는다.

```text
1. 청크로 나눔        모델의 최대 입력 길이 안으로 (SPLADE 보통 512토큰, bge-m3 최대 8,192토큰)
2. 토큰화             "환불은 7일 이내" → [환불, 은, 7, 일, 이내]   (모델의 서브워드 토크나이저)
3. 모델 1회 실행      토큰 열 전체를 한 번에 넣음. 모든 토큰이 서로를 참고하며 계산됨 (셀프 어텐션)
4. 토큰마다 가중치    환불 1.2, 은 0.0, 7 0.4, 일 0.3, 이내 0.3
5. 정리               0은 버리고, 같은 토큰이 여러 번 나오면 하나로 합침 (bge-m3는 가장 큰 값)
                      → {환불: 1.2, 7: 0.4, 일: 0.3, 이내: 0.3}
```

- 통째로 넣어야 문맥이 반영된다. "환불 기한은 7일이다"의 "환불"은 1.2, "환불 문의는 고객센터로"의 "환불"은 0.5처럼 같은 단어라도 가중치가 달라진다. BM25는 토큰마다 따로 세므로 횟수가 같으면 같은 값이다.
- 사람처럼 뜻을 이해하는 것은 아니다. 학습 데이터에서 본 "이런 단어들이 함께 나오면 이 단어가 중요했다"는 패턴을 적용한다. 처음 보는 도메인 용어나 문체에서는 엉뚱한 가중치가 나올 수 있다.
- **문맥의 범위는 청크다.** 최대 길이를 넘는 부분은 잘려서 무시되고, 청크끼리는 서로 보지 못한다. 그래서 청크 앞에 문서 제목·섹션 제목을 붙여 청크 하나만으로도 무엇에 관한 내용인지 알 수 있게 한다([04-advanced-rag/04-chunking](../../04-advanced-rag/04-chunking/02-parent-child-contextual.md)).
- dense 임베딩도 1~3번은 같다. 4번에서 dense는 토큰별 결과를 벡터 하나로 합치고, sparse는 토큰별 가중치를 그대로 남긴다.

### 3.2 색인과 검색 흐름

```text
[색인할 때 — 한 번]   문서 ──▶ 모델 ──▶ {토큰ID: 가중치} ──▶ 벡터 DB의 sparse 필드 (역색인)
[검색할 때 — 매번]    질문 ──▶ 같은 모델 ──▶ {토큰ID: 가중치} ──▶ 내적으로 검색 ──▶ top-k
```

- **문서와 질문은 반드시 같은 모델, 같은 버전**으로 바꾼다. 토큰ID와 가중치의 의미가 모델마다 다르다. 모델을 바꾸면 문서 전체를 다시 인코딩한다.
- 벡터 DB는 받은 가중치를 그대로 저장하고 내적만 계산한다. 가중치의 품질은 전적으로 모델이 정한다. Milvus의 저장 방식은 [03-vector-index/02-vector-db](../03-vector-index/02-vector-db.md) 4.1 참고
- 한 문서 행에 dense 필드와 sparse 필드를 함께 둘 수 있다. bge-m3는 한 번 실행으로 둘 다 내므로 하이브리드 검색을 같은 컬렉션 안에서 할 수 있다.

## 4. 학습 방식

dense 임베딩 모델의 학습과 거의 같다. 점수를 코사인 대신 sparse 가중치 곱의 합으로 계산한다는 점만 다르다.

가중치를 내는 부분

```text
문장 ──▶ 인코더 ──▶ 토큰마다 숨은 벡터 h_i
                        │
   ┌────────────────────┴─────────────────────┐
 [가중치만, bge-m3]                      [확장형, SPLADE]
 w_i = ReLU(선형층(h_i))                 빈칸 단어 예측 층으로 어휘 전체에 점수
 → 입력 토큰마다 가중치 1개              → log(1 + ReLU(점수)), 토큰 위치마다 계산해 최댓값
                                         → 문장에 없는 단어도 점수가 생김 (확장)
```

- ReLU가 음수를 0으로 바꾸므로 대부분의 값이 0이 되고 sparse 벡터가 된다.

학습 데이터와 손실

| 단계 | 내용 |
| --- | --- |
| 데이터 | 질문, 정답 문서, 오답 문서(같은 배치의 다른 문서 + 비슷해 보이지만 정답이 아닌 하드 네거티브) |
| 대조 학습 | `−log( exp(score(q, d+)) / Σ exp(score(q, d)) )`. 정답 점수는 높이고 오답 점수는 낮춘다. 그 결과 어떤 단어가 중요한지, (확장형이면) 무엇을 덧붙여야 정답과 겹치는지를 배운다 |
| 증류 | 정답/오답 라벨 대신 cross-encoder 리랭커의 점수를 따라 하도록 학습. bge-m3는 dense·sparse·멀티 벡터 점수를 합친 값을 선생님으로 삼는 자기 증류도 한다 |
| 희소성 규제 (확장형) | `전체 손실 = 대조 손실 + λ × (0이 아닌 가중치가 많을수록 커지는 벌점)`. λ가 크면 단어 수가 줄어 빠르지만 정확도가 떨어진다. SPLADE는 FLOPS 규제를 쓴다 |

- 사람이 "취소 → 환불" 같은 규칙을 넣지 않는다. 정답 점수를 올리는 데 도움이 되는 가중치와 확장을 데이터에서 찾는다.
- 그래서 학습 데이터에 없던 도메인(사내 약어, 전문 용어)은 약하다. 도메인 질문-문서 쌍으로 추가 학습할 수 있고, 방법은 임베딩 파인튜닝과 같다([07-ml/02-embedding-finetuning](../../07-ml/02-embedding-finetuning/README.md)).

## 5. 손계산 예시

점수는 두 종류 모두 질의와 문서에 함께 있는 단어의 가중치 곱을 더한다.

```text
score(q, d) = Σ (단어 t가 q와 d 모두에 있을 때) w_q(t) × w_d(t)
```

예: 질의 "환불 지연"

```text
문서 A "결제 취소 후 환불은 3~5일 이내 처리"
문서 B "배송 지연 시 보상 기준"

[가중치만 학습]
질의:  환불 1.5, 지연 1.0
A:     환불 1.2, 취소 1.0, 결제 0.8, 처리 0.6
B:     지연 1.4, 배송 1.3, 보상 0.9
score(A) = 1.5 × 1.2 (환불)                    = 1.8
score(B) = 1.0 × 1.4 (지연)                    = 1.4

[확장형]
질의:  환불 1.5, 지연 1.0, 취소 0.5(확장)
A, B:  위와 같음 (문서 쪽 확장은 생략)
score(A) = 1.5 × 1.2 (환불) + 0.5 × 1.0 (취소) = 2.3
score(B) = 1.0 × 1.4 (지연)                    = 1.4
```

- BM25였다면 A는 "환불", B는 "지연" 한 단어씩만 겹쳐 비슷한 점수가 나온다.
- 가중치만 학습해도 모델이 "환불"을 더 중요한 단어로 보면 A가 앞선다(1.8 대 1.4). 다만 겹치는 단어 자체는 BM25와 같다.
- 확장형은 질의를 "취소"로 넓혀서 A를 더 확실히 올린다(2.3 대 1.4). 대신 확장이 틀리면(관련 없는 단어로 확장) BM25에 없던 오답이 들어온다.
- "결제했는데 돈이 안 돌아와요"처럼 겹치는 단어가 하나도 없는 질문은 가중치만 학습하는 방식으로는 못 찾는다. 이 경우는 확장형이나 dense가 맡는다.

## 6. SPLADE: 확장형의 대표 모델

"학습된 sparse"는 방식의 이름이고, SPLADE는 그 방식 중 확장형에 속하는 모델의 이름이다.

| 질문 | 답 |
| --- | --- |
| 학습된 sparse = SPLADE인가? | 아니다. SPLADE는 학습된 sparse 중 하나다 |
| 학습된 sparse는 모두 확장을 하나? | 아니다. 확장은 SPLADE 계열의 특징이다. bge-m3 sparse는 확장하지 않는다 |
| lawlens가 쓰는 것은? | bge-m3 sparse. 학습된 sparse이지만 SPLADE 계열은 아니다 |

대표로 꼽히는 이유
- 확장과 가중치 학습을 **한 모델 안에서 같이** 한다. 이전에는 둘을 따로 했다(doc2query로 문서에 질문을 생성해 덧붙이는 확장, 별도 모델로 가중치).
- 희소성 규제로 0이 아닌 단어 수를 줄여, 역색인으로 실제 검색할 수 있는 효율을 맞췄다.
- 이후 버전(SPLADE v2, SPLADE++)에서 하드 네거티브와 cross-encoder 증류를 더해 성능을 올렸다. 학습된 sparse의 기준 모델처럼 쓰인다.

변형
| 변형 | 내용 | 장단점 |
| --- | --- | --- |
| 질의·문서 모두 확장 | 질의도 모델로 인코딩해 확장 | 정확도가 높지만 질문마다 모델 호출 |
| 문서만 확장 | 문서는 색인할 때 확장, 질의는 토큰 그대로 | 검색할 때 모델 호출이 없어 빠름. 질의 쪽 확장 효과는 없음 |

- 공개된 SPLADE 모델은 주로 영어로 학습되어 있다. 한국어 문서에 쓰려면 다국어 모델이나 한국어로 추가 학습한 모델이 있는지 먼저 확인한다.

## 7. 검색 속도

두 방식 모두 역색인을 쓰지만, **질문을 벡터로 바꾸는 단계**와 **색인을 훑는 양**이 BM25와 다르다.

| 단계 | BM25 | 가중치만 학습 (bge-m3) | 확장형 (SPLADE) |
| --- | --- | --- | --- |
| 질문 → 벡터 | 토큰화만 (거의 0) | **모델 실행 1회** (수~수십 ms) | **모델 실행 1회** (수~수십 ms) |
| 질문의 단어 수 | 질문에 나온 단어 (보통 5개 안팎) | 비슷함 | 확장으로 늘어남 (수십 개 이상) |
| 문서의 단어 수 | 문서에 나온 단어 | 비슷함 | 확장으로 늘어남 |
| 색인 훑기 | 가장 빠름 | BM25와 비슷 | 훑을 목록이 많고 길어져 느려짐 |
| 색인 만들기 | CPU 토큰화, 빠름 | 문서 전체를 모델로 인코딩 (GPU) | 같음, 색인도 더 큼 |

느려지는 이유
- **질문마다 모델을 실행한다.** 보통 이 단계가 지연의 대부분이다. GPU 유무와 모델 크기에 따라 크게 달라진다.
- **확장형은 훑을 양이 늘어난다.** 질문과 문서 양쪽에 단어가 덧붙어 역색인 목록을 더 많이, 더 길게 읽는다. 최적화 없이는 BM25보다 몇 배 느릴 수 있다.
- **BM25용 가속 기법이 덜 듣는다.** 점수가 낮을 문서를 미리 건너뛰는 기법(WAND, MaxScore 등)은 BM25 점수 분포에 맞춰 발전해서, 학습된 가중치에서는 건너뛰는 효과가 줄 수 있다.

줄이는 방법
- **문서만 확장하는 변형**(6장): 질문은 토큰 그대로 써서 검색할 때 모델을 실행하지 않는다. 속도는 BM25에 가까워지고 정확도는 조금 떨어진다.
- **가지치기**: 가중치가 낮은 확장 단어를 잘라 단어 수를 줄인다.
- **dense와 함께 계산**: bge-m3는 한 번 실행으로 dense와 sparse가 함께 나온다. 하이브리드로 dense를 어차피 계산하면 sparse의 추가 인코딩 비용은 거의 없다. lawlens가 이 경우다.

- 실제 숫자는 모델 크기, 하드웨어, 검색 엔진에 따라 크게 달라진다. 같은 질문 세트로 p50·p95 지연과 색인 크기를 직접 재서 BM25와 비교한다([03-evals/05-regression-ci](../../03-evals/05-regression-ci/01-gate-design.md) 6장 품질 외 기준).

## 8. 비교할 때 주의

- **BM25와 별도의 기준선이다.** "sparse 검색"이라고 묶어서 하나만 재지 않는다. 어느 종류인지(가중치만 / 확장형)도 결과에 적는다.
- 같은 모델의 dense와 학습된 sparse는 같은 학습 데이터에서 나와서 실패하는 질문이 겹치기 쉽다. 하이브리드나 골든셋 pool에서 서로 다른 검색기로 세지 않는다([03-golden-set/02-pooling](../../03-evals/03-golden-set/02-pooling.md) 6장).
- 토크나이저가 고정이라 사용자 사전을 넣을 수 없다. 코드·고유명사가 잘게 쪼개지면 BM25보다 정확 일치가 약할 수 있다.
- 동의어 대응을 기대한다면 확장형인지 먼저 확인한다. bge-m3 sparse는 확장하지 않으므로 동의어는 dense 쪽이 맡는다.
- **품질 대부분이 모델에서 정해진다.** BM25는 토큰화만 맞으면 어느 도메인에서나 안정적이지만, 학습된 sparse는 학습 데이터의 언어·도메인, 토크나이저, 확장 품질, 희소성 정도에 크게 좌우된다. 영어 벤치마크 순위보다 자기 골든셋 dev 세트 결과를 기준으로 한다.
- **단독 점수보다 하이브리드에 보태는 몫을 본다.** 같은 모델의 dense와 실패가 겹치면 sparse 단독 점수가 BM25보다 높아도 "dense + BM25"가 "dense + 학습된 sparse"보다 나을 수 있다. dense는 틀리고 sparse가 맞힌 질의 수를 세서 비교한다([04-advanced-rag/01-hybrid-search/02-tuning-and-analysis](../../04-advanced-rag/01-hybrid-search/02-tuning-and-analysis.md) 1장).
- **유형별로 나눠 본다.** 식별자·코드 질문은 토크나이저를 고칠 수 없는 학습된 sparse가 BM25보다 약할 수 있고, 일상어 질문(`user` 말투)은 반대일 수 있다.

## 9. 확인할 점

- 모델 이름과 함께 종류(가중치만 / 확장형)와 확장 방식(질의·문서 / 문서만)을 결과에 기록한다.
- 확장형은 확장된 단어 수만큼 색인이 커진다. 문서당 0이 아닌 단어 수의 평균을 기록하고, 색인 크기와 검색 지연을 BM25와 비교한다.
- 학습 데이터에 없던 도메인 용어가 어떻게 토큰화되고 가중치를 받는지 몇 개 직접 확인한다([07-ml/01-pytorch-hf/02-huggingface](../../07-ml/01-pytorch-hf/02-huggingface.md)).

# 임베딩 모델 선택 (Model Selection)

dense 검색 품질은 임베딩 모델이 대부분을 정한다. 후보를 고르는 기준과, 공개 순위표가 아니라 우리 골든셋으로 비교하는 방법을 정리한다.

- 폴더 요약과 기본 선택은 [README](./README.md) 참고
- 임베딩 검색 원리는 [01-embedding-basics](./01-embedding-basics.md), 멀티 벡터는 [02-multi-vector](./02-multi-vector.md) 참고

## 1. 고르는 기준

| 기준 | 확인할 것 | 이유 |
| --- | --- | --- |
| 언어 | 한국어 학습 여부 (다국어 모델, 한국어 특화 모델) | 영어 중심 모델은 한국어 전문 문서에서 크게 떨어진다 |
| 최대 입력 길이 | 512 / 8192 토큰 등 | 청크 길이보다 짧으면 잘림 |
| 차원 | 384 / 768 / 1024 등 | 저장 공간, 검색 속도, 메모리 |
| 척도 | 코사인 / 내적, 정규화 여부 | 검색 설정과 맞춰야 함 |
| 접두어 규칙 | 질의·문서 접두어 필요 여부 | 빠뜨리면 성능 하락 |
| 실행 방식 | API / 로컬 실행 | 비용, 데이터 외부 전송 가능 여부 |
| 라이선스 | 상업 이용 가능 여부 | 서비스 적용 |

- 사내 문서처럼 외부로 보내기 어려운 데이터면 로컬 실행 모델이 사실상 필수다.

### 저장량과 줄이는 방법

```text
저장량 = 청크 수 × 차원 × 값 하나의 크기
100만 청크 × 1,024차원 × 4바이트(float32) ≈ 4.1GB      (HNSW 그래프는 별도로 더 필요)
```

| 방법 | 값 하나 | 100만 × 1,024 | 정확도 영향 | 메모 |
| --- | --- | --- | --- | --- |
| float32 (기본) | 4바이트 | 4.1GB | 기준 | - |
| float16 | 2바이트 | 2.0GB | 거의 없음 | 가장 먼저 해 볼 만함 |
| int8 양자화 | 1바이트 | 1.0GB | 작음 | 벡터 DB의 양자화 인덱스(IVF_SQ8 등) 사용 |
| binary 양자화 | 1비트 | 0.13GB | 큼 | 후보를 넉넉히 뽑고 원래 벡터로 다시 정렬하면 회복됨 |
| 차원 줄이기 (Matryoshka) | - | 512차원이면 절반 | 모델에 따라 작음 | **Matryoshka 방식으로 학습한 모델만** 앞쪽 차원을 잘라 써도 된다. 아닌 모델을 자르면 크게 떨어짐 |

- 줄인 뒤에는 원래 벡터 대비 ANN Recall과 골든셋 Recall@5를 같이 잰다([03-vector-index](../03-vector-index/README.md)). 두 단계 오차를 섞지 않도록, 모델 비교가 끝난 뒤에 한다.
- 문서 수가 수십만 이하면 float32 그대로도 보통 메모리에 들어간다. 저장량이 실제로 문제일 때만 줄인다.

## 2. 공개 순위표의 한계

- MTEB 같은 공개 순위표는 후보를 좁히는 데만 쓴다.
- 순위표의 데이터는 주로 영어, 일반 도메인이다. 한국어 도메인 문서 검색 순위와 다를 수 있다.
- 최종 선택은 **우리 골든셋 dev 세트의 Recall@5**로 한다.

## 3. 비교 방법

```text
후보 3~4개 선정 (순위표, 언어, 길이, 라이선스로 거름)
   ↓
같은 문서 집합, 같은 청크, 같은 인덱스 설정(Flat, 정확 검색)으로 각각 색인
   ↓
골든셋 dev 세트로 Recall@5, MRR, nDCG@10 측정
   ↓
user / expert 말투별, 질문 소스별로 나눠 보기
   ↓
지연 시간, 저장 크기와 함께 비교해서 선택
```

- 모델 비교 때는 벡터 인덱스를 **정확 검색(Flat)**으로 둔다. ANN 인덱스를 쓰면 인덱스 근사 오차가 모델 차이에 섞인다([03-vector-index](../03-vector-index/README.md)).
- sparse 기준선(BM25)을 같은 표에 넣는다. dense가 항상 이기지는 않는다. 특히 `expert` 말투 질문에서는 BM25가 이길 수 있다.

### 차이가 우연인지 확인

골든셋이 수백 질문 규모면 Recall@5가 0.02 차이 나는 것은 우연일 수 있다.

```text
질문 300개, 모델 A Recall@5 = 0.80, 모델 B = 0.82
→ 질문 6개 차이. 같은 질문에서 A만 맞힌 것 10개, B만 맞힌 것 16개라면
  McNemar 검정 p ≈ 0.33  → 우연과 구분하기 어려움
```

- 평균만 보지 말고 **같은 질문끼리 짝지어** 비교한다. 이진 결과(top-5 안에 정답 있음/없음)는 McNemar 검정, nDCG 같은 연속 점수는 paired bootstrap을 쓴다. 방법은 [03-evals/05-regression-ci/01-gate-design](../../03-evals/05-regression-ci/01-gate-design.md) 5장과 같다.
- 유의한 차이가 없으면 지연, 저장 크기, 라이선스, 운영 편의로 고른다. 작은 차이에 기대어 큰 모델을 고르지 않는다.
- 말투별·소스별로 나눠 볼 때는 질문 수가 더 적어져 차이가 우연일 가능성이 더 크다. 나눈 결과는 방향을 보는 데만 쓴다.

## 4. sparse와 dense를 함께 보는 법

| 질의별 결과 | 의미 | 다음 단계 |
| --- | --- | --- |
| BM25 성공, dense 실패 | 정확 일치가 필요한 질문 (제품 코드, 문서 제목) | 하이브리드 |
| BM25 실패, dense 성공 | 바꿔 말한 질문, 일상어 | 하이브리드 |
| 둘 다 실패 | 문서에 표현 자체가 없거나 다단계 추론 필요 | 쿼리 변환, 청킹 개선 |
| 둘 다 성공 | - | - |

- 둘 중 하나만 성공한 질의가 많을수록 하이브리드의 효과가 크다. 이 비율을 결과에 기록해 두면 [04-advanced-rag/01-hybrid-search](../../04-advanced-rag/01-hybrid-search/README.md)의 출발점이 된다.

## 5. 후보 예시

| 유형 | 예 | 메모 |
| --- | --- | --- |
| 다국어 범용 | `multilingual-e5` 계열 | 질의·문서 접두어 필요 |
| 다국어 + 긴 입력 | `bge-m3` | 최대 8192 토큰, dense·sparse·multi-vector 출력 지원 |
| 한국어 특화 | 한국어로 추가 학습한 공개 모델 | 도메인·라이선스 확인 필요 |
| API | 상용 임베딩 API | 데이터 외부 전송 가능 여부 먼저 확인 |

- 후보 목록은 시점에 따라 바뀐다. 비교할 때의 모델 이름과 버전을 함께 남긴다.

### 모델 크기 축

| | BERT급 인코더 | LLM 기반 임베딩 모델 |
| --- | --- | --- |
| 크기 | 약 1억~6억 파라미터 (예: bge-m3 약 5.7억) | 수억~수십억 (예: Qwen3-Embedding 0.6B / 4B / 8B) |
| 정확도 | 기준 | 공개 순위표에서 보통 더 높음 |
| 질의 인코딩 | GPU면 수 ms, CPU에서도 짧은 질문은 보통 수십 ms | GPU 사실상 필요. 큰 모델은 CPU로 서비스하기 어려움 |
| 문서 인코딩 | GPU 1장으로 수십만 청크를 수 시간 안 | 몇 배 이상 오래 걸림 |
| 차원 | 768~1,024 | 1,024~4,096 (Matryoshka로 줄일 수 있는 모델 많음) |
| 입력 방식 | 접두어 또는 없음 | 지시문 ([01-embedding-basics](./01-embedding-basics.md) 3장) |

- CPU만 있는 서버라면 BERT급 모델에 양자화나 ONNX 변환을 더하는 쪽이 현실적이다. 문서 인코딩은 GPU 장비에서 한 번 하고, 서비스에서는 질의 인코딩만 한다.
- 큰 모델이 순위표에서 높아도 우리 골든셋에서 유의한 차이가 없으면 작은 모델을 고른다(3장 "차이가 우연인지 확인").
- 지연 숫자는 하드웨어와 배치 크기에 따라 크게 달라진다. 같은 질문 세트로 p50·p95를 직접 잰다.

### 한국어 모델 예시

2026년 기준 Hugging Face에서 한국어 검색용으로 많이 비교되는 모델이다. 수치는 각 모델 카드가 직접 잰 값이라 평가 데이터가 서로 다르다.

| 모델 | 바탕 모델 | 특징 |
| --- | --- | --- |
| `nlpai-lab/KURE-v1` | bge-m3를 한국어 데이터로 추가 학습 | 1,024차원, 최대 8,192토큰. 모델 카드의 한국어 검색 비교에서 상위 |
| `dragonkue/BGE-m3-ko` | bge-m3를 한국어로 추가 학습 | KURE-v1과 비슷한 수준으로 보고됨 |
| `nlpai-lab/KoE5` | multilingual-e5-large를 한국어로 추가 학습 | 최대 512토큰, 접두어 필요 |
| `BAAI/bge-m3` | - | 다국어 기준선. dense·sparse·멀티 벡터 함께 출력 |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | - | 다국어. 같은 이름의 영어 중심 작은 모델(arctic-embed-m, -s)은 한국어에 약함 |

- 모델 카드끼리 1점 안팎 차이는 평가 데이터가 달라서 생길 수 있다. 후보 3~4개를 골라 우리 골든셋으로 비교한다(3장).
- bge-m3를 한국어로 추가 학습한 모델은 bge-m3의 dense 출력만 학습했을 수 있다. sparse 출력도 쓰려면 모델 카드에서 함께 학습했는지 확인한다.

## 6. 확인할 점

- 임베딩 모델을 바꾸면 문서 전체를 다시 인코딩하고 기준선을 다시 잰다.

### 모델 교체 절차

```text
1. 새 모델로 골든셋 dev 세트 비교 (3장) → 교체 결정
2. 새 collection을 만들어 문서 전체를 새 모델로 인코딩 (기존 collection은 그대로 서비스)
3. 새 collection으로 test 세트, 회귀 테스트 통과 확인
4. 질의 인코딩 모델과 검색 대상 collection을 동시에 새 것으로 바꿈 (alias 전환 등)
5. 일정 기간 기존 collection을 남겨 두고, 문제가 생기면 둘을 함께 되돌림
```

- 질의는 새 모델, 문서는 옛 모델처럼 **버전이 엇갈리면** 차원이 같아도 결과가 엉망이 된다. 차원이 같으면 오류도 나지 않는다. collection 메타데이터에 모델 이름·버전을 넣고, 검색할 때 질의 쪽 모델과 같은지 확인한다.
- 바꾸는 동안 들어온 문서 추가·수정은 두 collection에 모두 반영한다.
- 벡터 DB 운영은 [03-vector-index/02-vector-db](../03-vector-index/02-vector-db.md) 참고
- 도메인 파인튜닝은 이 비교에서 기성 모델의 한계를 확인한 뒤 [07-ml/02-embedding-finetuning](../../07-ml/02-embedding-finetuning/README.md)에서 다룬다.
